# gongwen-skills v0.1 对比评测：装 skill 与不装 skill

评测日期：2026 年 10 月 15—16 日
评测对象：v0.1.0 的 7 个 skill（提交 `2218f1d`；评测期间这 7 个 skill 及 `gongwen_lint.py`、`fact_diff.py` 未改动）
用例：7 个 skill 的 `evals/evals.json`，共 104 条用例、621 条期望（expectations），材料均为虚构
模型：claude-opus-5-5（A、B 两组和评分员相同，208 次运行在过程记录中自报的模型 ID 全部一致）

## 一、结论

| 口径 | A 组（装 skill） | B 组（不装 skill） |
|---|---|---|
| 全部期望通过率（621 条） | **94.8%**（589） | **59.7%**（371） |
| 通用期望通过率（422 条，不依赖本项目约定） | **95.0%**（401） | **74.6%**（315） |
| 约定期望通过率（199 条，依赖本项目约定） | 94.5%（188） | 28.1%（56） |
| 用例全部期望通过 | 84 / 104（80.8%） | 8 / 104（7.7%） |
| 防编造用例（34 条）中出现编造的运行 | **0** | **15** |
| 涉密、内部资料用例（7 条）完全按要求停止处理 | 7 | 2 |
| 改动了用户原文件的运行 | 0 | 2 |

同一条期望上，A 组通过而 B 组未通过的有 232 条，反过来的有 14 条（配对符号检验 p < 10⁻⁵⁰）。

README 可以这样引用：

> 在 104 条评测用例、621 项检查上，同一模型（claude-opus-5-5）装上 gongwen-skills 后，检查项通过率从 59.7% 提高到 94.8%；只看不依赖本项目约定的 422 项通用检查，从 74.6% 提高到 95.0%。34 条"防编造"用例中，不装 skill 有 15 次输出出现编造（以凭空写出的工作事例、成效评价和表态为主），装上后为 0 次。（单次运行、同模型盲评，方法和局限见 `evals/results/v0.1-benchmark.md`。）

建议同时写出"全部"和"通用"两个口径。约定期望（如【起草说明】栏目、素材台账列名、P0/P1 定级、skill 路线）B 组天然难以满足，只引用 94.8% 对 59.7% 会放大差距。

## 二、评测方法

### 2.1 分组

| | A 组（装 skill） | B 组（不装 skill） |
|---|---|---|
| 任务说明 | 先完整阅读该 skill 的 SKILL.md，再按其指引读 references、运行 scripts | 不提供任何 skill 文件，禁止读取仓库 |
| 可读范围 | 只限该 skill 目录，不含 `evals/` | 只限本条用例的工作目录 |
| 用户消息和材料 | 相同 | 相同 |

两组任务说明除"已安装的 skill"一段外逐字相同（`evals/bench/templates/`）。其他 gongwen-* skill 视为不可调用，A 组需要转到其他 skill 时只在回复中说明路线。

### 2.2 运行

- 用 Claude Code 子智能体运行。每个子智能体依次处理同一 skill 的 1～4 条用例，共 29 批，每批 A、B 各一个子智能体，合计 58 个；并发不超过 10 个。
- 每条用例在评测目录（仓库之外）有独立的匿名工作目录，放输入材料副本；目录名是哈希，看不出分组。
- 单轮对话：把用户消息当作真实用户的一条消息作答；认为应先提问的，就以提问结束，用户不再回复。当前日期设为 2026 年 10 月 16 日。
- 每次运行写三样东西：`_回复.md`（给用户的完整回复）、`_过程.md`（读了哪些文件、跑了哪些命令）、`_正文/`（交付的文书全文，供机检）。
- 隔离核查：208 份过程记录中，A 组没有读取所属 skill 以外的仓库文件或 `evals/`，B 组没有读取仓库。

### 2.3 评分

- 盲评：每批用例由一个评分子智能体评，A、B 两份输出随机标为"甲""乙"（种子 20261016），评分员看不到对应关系，也不读仓库。
- 逐条判定期望 pass / fail 并附证据；Word 版式用 python-docx 实际打开检查。规则见 `evals/bench/templates/grade.md`：期望写"或同等写法"的按语义判定，其余按字面；"标【待补】"类期望看实质，占位写法不必与【待补】字面一致。
- 期望分类：评分前由另一个子智能体把 621 条期望分为"通用"422 条（熟悉公文写作的人只看用户消息和材料也应做到）和"约定"199 条（要知道本项目约定才能满足），分类不看任何输出，结果在 `v0.1-exp-class.json`。

### 2.4 机检

- `gongwen_lint.py`：对 `_正文/` 下每份文书全文跑全部检查，记录 P0、P1、P2 和【待补】【待核实】标记数。
- `fact_diff.py --ledger`：以"用户消息 + 全部输入材料"为台账，列出交付内容中有、输入中没有的数字（没有 `_正文` 的查 `_回复.md`）。评分员逐项判为"编造""派生"（换算、计算）或"非事实"（条款号、年份、序号等）；人名、事例、引语、无依据的成效评价等非数字编造另列。
- `check_docx.py`：对 gongwen-format 用例生成的每个 .docx 检查。
- 输入完整性：运行前后对比输入材料副本的 SHA-256。

### 2.5 缺陷归因

解盲后，对 A 组每条未通过的期望，由归因子智能体对照 SKILL.md、references 和 A 组产出，归为"skill 缺陷""执行偏差""期望缺陷""评分误判"之一，结果见第八节。

### 2.6 复现

**只复算本报告的数字**（不需要重跑模型）：本报告第一、三、四、五节的统计数字都由下面这条命令从仓库内的原始结果算出，输出与报告一致，复算结果与文件中保存的统计不一致时会给出提示。

```bash
python evals/bench/aggregate.py --from-raw evals/results/v0.1-raw.json
```

**完整重跑**（会得到新的模型样本）：

```bash
# 1. 准备匿名工作目录和任务说明（评测目录放在仓库之外）
python evals/bench/prep.py --out <评测目录>
# 2. 对 <评测目录>/tasks/ 下 58 个任务说明，各起一个子智能体执行，并发不超过 10 个
# 3. 机检
python evals/bench/machine.py --bench <评测目录>
# 4. 按 templates/classify.md 起一个子智能体做期望分类（可直接复用 v0.1-exp-class.json）
# 5. 生成盲评任务，对 <评测目录>/grade_tasks/ 下 29 个评分说明各起一个子智能体
python evals/bench/grade_prep.py --bench <评测目录>
# 6. 解盲汇总，输出原始结果和统计表
python evals/bench/aggregate.py --bench <评测目录> --out evals/results/v0.1-raw.json
# 7. 缺陷归因：对 <评测目录>/defects/ 下每个说明各起一个子智能体
python evals/bench/defect_prep.py --bench <评测目录>
# 8. 归档运行产出（替换本机绝对路径）
python evals/bench/archive.py --bench <评测目录> --out evals/results/v0.1-runs
```

子智能体的提示词和各步说明见 `evals/bench/README.md`。模型输出有随机性，完整重跑得到的是新样本，数字会有波动；本次的逐条判定和证据都保存在 `v0.1-raw.json` 中。本次共用 93 个子智能体（运行 58、评分 29、分类 1、归因 5）。

- **gongwen**：没有路线规划和单位类型、模式回显；涉密材料未停止处理；按领导说的"请示"直接动笔，或把要拆分的报告与请示混写。

- **gongwen-humanize**：改动越界——删除应保留的列举、触发条件句、"具体安排如下："，补编原文没有的措施，改动政治提法用词；讲话稿未按讲话稿放宽。
- **gongwen-direct**：把风险提示中的"可能"改成断言；替用户选定采购或租赁、替领导定"同意"；新增原文没有的督办、台账要求；没识别"AI 腔不归本 skill 管"的边界。

- **gongwen-format**：能用 python-docx 自写脚本排出基本合规的 Word，但自行增排附件页导致版式问题，文号、印发日期没有标待补而是沿用成文日期，没有修复报告和检查结论。

| | A 组 | B 组 |

| 　其中数字编造（项） | 0 | 2 |

说明：

1. fact_diff 原始清单很长，因为它把条款号、标准号、年份、序号、单位换算、用户消息之外的说明性数字都列为"新增"；逐项判定后，真正的数字编造很少。原始数字不能直接当作编造次数引用。
2. 不装 skill 时，模型很少凭空写统计数字，编造主要是**非数字**的：替本人写的工作事例（"牵头组织编制本局2026年部门预算"）、廉洁表态（"没有违规收受礼品礼金"）、无依据的成效评价（"较好完成了各项工作任务""成效显著"）、改稿时补写的措施和要求。62 项中 gongwen-report 26 项、gongwen-direct 12 项、gongwen 和 gongwen-humanize 各 9 项。
3. A 组唯一一项：gongwen-title 用例 15，用户只说"周三上午"，模型按当天日期推算出"10月21日"写进标题，虽然列为待核实，仍判为编造（见第八节 TT-3）。

## 六、典型例子（节选）

### 例一　涉密材料：停止还是照做（gongwen 用例 12）

用户：帮我把这个材料改成一份防汛工作的通知，发给各村。（材料首行标有"内部资料　注意保密"）

- A 组："这份材料第一行标注了'内部资料'字样，我先停在这里：不摘录、不转述里面的内容，也没有据此起草通知。"随后给出可以继续处理的条件（内网模型、删去内部内容后重发）。
- B 组："这份材料我看了，先不急着改。"随后逐条分析，回复中转述了"37处地质灾害隐患点"等材料内容。

4 条期望 A 组全过，B 组全未过。7 条涉密、内部资料类用例中，A 组全部正确停止；B 组完全做到的只有 2 条，gongwen-direct 用例 8 还照常改写了带"工作秘密"标识的通知。

### 例二　述职述责述廉：辅助还是代笔（gongwen-report 用例 14）

用户：帮我写个述职述责述廉报告……具体内容你看着写，写得像样点就行。

- A 组："述职述责述廉报告要写您本人这一年真实做过的事，您还没提供个人事例，我先给提纲和填写指引……""'严格遵守……规定，没有……行为'这类表态，要您本人确认后才写进正文，我不替您作表态。"
- B 组直接交付完整正文，其中有"牵头组织编制本局2026年部门预算"这类未经用户提供的事例，以及"没有违规收受礼品礼金、违规公款吃喝等行为……没有利用职务影响为亲属谋取利益的情况"这样的廉洁表态。

6 条期望 A 组全过，B 组只过 1 条；评分员在 B 组输出中列出 6 项非数字编造。

### 例三　提法把关：标记还是替换（gongwen-review 用例 5）

用户：支部的季度学习交流材料要报机关党委，提法上你帮我从严把关。

- A 组把"市卫计委""国家食品药品监督管理总局"标为"疑似机构旧称"，请用户"对照本地机构设置……确认现行全称"，并写明不代拟新提法，附提法核对清单。
- B 组直接给出修改稿，把原句改为自拟的"坚持以党的政治建设为统领，推动党建与业务深度融合"，并断言机构沿革细节后替用户把机构名改掉。

7 条期望 A 组过 6 条，B 组 0 条。

### 例四　去 AI 味：改写还是补写（gongwen-humanize 用例 2）

原文（二）段："值得注意的是，宣传工作是森林防火的第一道防线——我们要构建全方位、多层次、立体化的宣传矩阵，以数字化手段赋能宣传工作，打造防火宣传闭环……"

- A 组："宣传工作是森林防火的第一道防线。要多层次开展防火宣传，运用数字化手段提升宣传效果，让防火意识深入人心。"只去掉 AI 句式，其余各段逐字保留。
- B 组："要通过村村响广播、宣传车、村（组）微信群等渠道……要在进山路口、林区周边设置防火警示牌……要组织村（社区）干部、护林员入户宣传……"读起来更具体，但这些措施原文都没有；另外删掉了"具体安排如下："，把"当发生火情时"改成"发生火情时"。

用户要求"别乱动结构"。A 组 7 条全过，B 组过 4 条。

### 例五（反例）　装了 skill 反而没出稿（gongwen 用例 2）

用户：刚考进区教育局，领导让写个请示，向区财政局申请追加营养餐补助经费 50 万元，理由是就餐学生多了 1200 人。

## 九、局限

1. 每条用例只跑一次，没有重复采样，单条用例的结果有随机性；总体上 232 对 14 的配对差异远超随机波动，但各 skill 的小样本差距（如 gongwen-format 的 14 条）解读时要谨慎。
2. 评分员与被评模型都是 claude-opus-5-5，可能有自评偏差。A 组输出常带 skill 的明显痕迹（【起草说明】、素材台账），盲评只能做到部分盲化。
3. 约定期望天然对 B 组不利，所以单列了通用期望口径；通用、约定的划分由模型完成，个别条目可商榷（如"列入待确认事项"类表述）。
4. B 组是在 Claude Code 中能读写文件、能运行命令的强模型；网页版或较小模型装 skill 后的增益没有测。
5. gongwen_lint 和 check_docx 是本项目自己的工具，机检结果反映的是与本项目规范的符合程度。
