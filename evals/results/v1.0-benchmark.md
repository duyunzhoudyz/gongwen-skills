要点：

1. **发布版本达标。** 第二轮装 skill 一组全部期望通过率 98.6%，不装 54.1%；只看不依赖本项目约定的通用期望，99.1% 对 68.7%；约定期望 97.7% 对 27.5%。

4. **防编造。** 136 条防编造用例中，A 组出现编造 0 次，B 组 66 次（数字编造 77 项、非数字编造 169 项）。全部 372 条用例中，评分员标出 A 组编造 2 次（都在 gongwen-university，共 3 个日期），复核后确认是引用工具内置资料，不算编造（4.2）；B 组 148 次。第一轮 A 组为 19 次。
5. **保密。** 21 条材料带密级或“内部资料”等标识的用例，A 组全部识别并停止处理，B 组 3 条；1 条防误触发用例（材料里只有“保密办”之类的词，不该停）A 组没有误停。
6. **触发。** 440 条说法选对 439 条（99.8%），正例 219/220，反例 220/220；第一轮（修改 description 前）435/440。
7. **成熟度（D7）。** 17 个核心 skill 通过率 97.4%～100.0%、防编造 0 次、触发达标，标 Stable；5 个行业包数字同样达标，按 D7 统一标 Beta（第八节）。
8. **仍有问题。** A 组还有 37 项期望未通过（32 条用例、16 个 skill）。其中 34 项在第一轮是通过的，2 项两轮都没通过，另 1 项的期望改了文字；这 34 项是单次运行的波动还是修复带来的回退，需要重复采样才能分清。gongwen-soe 用例 17 一条用例失败 5 项，是行业包交界处的边界判断问题（第九节）。

## 二、评测方法

### 2.1 评测内容

- 22 个 skill，每个 14～22 条用例，共 372 条；每条用例 3～13 条期望，共 2671 条（平均 7.2 条）。
- 用例按单位类型分布：基层 74、党政机关 64、公立医院 57、国有企业 55、高校 49、中小学 41、社区 32；按角色模式分布：高效 145、教学 80、转译 76、严谨 37、审稿 34。
- 带“防编造”标签的用例 136 条（1023 条期望），带“保密”标签的 57 条（366 条期望）。
- 每条期望分为“通用”（熟悉公文写作的人只看用户消息和材料也应做到的要求）和“约定”（要知道本项目约定才能满足，如【起草说明】栏目、素材台账列名、交接卡、P0/P1 定级、skill 路线）。第二轮：通用 1726 条、约定 945 条；第一轮：通用 1718 条、约定 934 条。分类不看任何输出，结果写在 `v1.0-raw.json` 每条期望的 `class` 字段。

### 2.2 分组

| | A 组（装 skill） | B 组（不装 skill） |
|---|---|---|
| 任务说明 | 先完整阅读该 skill 的 SKILL.md，再按其指引读 references、运行 scripts | 不提供任何 skill 文件，禁止读取仓库 |
| 可读范围 | 只限该 skill 目录，不含 `evals/` | 只限本条用例的工作目录 |
| 用户消息和材料 | 相同 | 相同 |

两组任务说明除“已安装的 skill”一段外逐字相同（`evals/bench/templates/`）。其他 gongwen-* skill 视为不可调用，A 组需要转到其他 skill 时只在回复中说明路线。

### 2.3 运行与两轮的关系

| | 第一轮 | 第二轮 |
|---|---|---|
| 时间 | 2026-10-16～17 | 2026-10-20 |
| 被测 skill | 修复前（基于 `cc5320c`） | 修复后的发布版本（`a1e067c`） |
| A 组 | 99 批，推理强度 high | 重跑，101 批，推理强度 max |
| B 组 | 99 批，推理强度 high | 沿用第一轮的输出；新增 3 条用例的 B 组新跑，2 批 |
| 评分 | 99 个批次，high，没有公开文件清单 | 101 个批次，A、B 全部重评，max，加公开文件清单 |
| 用例与期望 | 369 条 / 2652 条 | 372 条 / 2671 条（新增 3 条用例；25 条期望改了文字） |
| 期望分类 | 通用 1718、约定 934 | 22 个 skill 重新分类：通用 1726、约定 945 |

- 用 Claude Code 子智能体运行。每个子智能体依次处理同一 skill 的 1～4 条用例（一批）。第一轮运行 198 个子智能体（A、B 各 99 批），第二轮运行 103 个（A 101 批、B 2 批）；并发不超过 10 个。
- 每条用例在评测目录（仓库之外）有独立的匿名工作目录，放输入材料副本；目录名是哈希，看不出分组。第一轮、第二轮的目录编号相同，第二轮重建了 A 组目录。
- 单轮对话：把用户消息当作真实用户的一条消息作答；认为应先提问的，就以提问结束，用户不再回复。当前日期设为 2026 年 10 月 16 日（两轮相同）。
- 每次运行写三样东西：`_回复.md`（给用户的完整回复）、`_过程.md`（读了哪些文件、跑了哪些命令）、`_正文/`（交付的文书全文，供机检）。
- 第一轮结果出来后，对 A 组的失败项和其他问题做缺陷归因，逐个 skill 修复（第七节），修改了 8 个 skill 的 description（gongwen、rectify、title、direct、review、format、grassroots、soe），并重新跑了触发评测；之后用 `prep.py --groups A` 只重建 A 组复测。B 组的目录、输出和输入哈希保持不动，所以第一轮与第二轮的 B 组是同一批输出，两轮的差别只来自评分条件。
- 两轮评分条件的差别：推理强度（high → max）；第二轮加了公开文件清单；25 条期望改了文字；通用、约定分类重做。因此 B 组两轮数字略有差异（如全部期望 54.0% → 54.1%，有编造的运行 158 → 148），属于评分条件变化。

### 2.4 评分

- 盲评：每批用例由一个评分子智能体评，A、B 两份输出随机标为“甲”“乙”（种子 20261016），评分员看不到对应关系，只读任务说明列出的目录，不读仓库。
- 逐条判定期望 pass / fail 并附证据；Word 版式用 python-docx 实际打开检查。规则见 `evals/bench/templates/grade.md`：期望写“或同等写法”的按语义判定，其余按字面；“标【待补】”类期望看实质，占位写法不必与【待补】字面一致。
- 编造核查：对 fact_diff 列出的每个“输出中有、输入中没有”的数字，判为“编造”“派生”（正确换算、计算）或“非事实”（条款号、年份、序号等）；人名、事例、引语、无依据的成效评价等非数字编造另列。
- 公开文件清单（第二轮新增）：为每个 skill 生成一份清单，摘录其 SKILL.md 和 references 中含书名号文件名、“〔年〕N 号”文号或 GB/T 标准号的行。输出引用清单内的文件名称、文号、条款号且所述内容不矛盾的，不算编造，A、B 两组同一口径，B 组也按此重评。第一轮没有这份清单，当时 A 组的一部分编造判定是把内置资料中的文号、条款当成了“输入里没有”（见第七节）。清单只收录含文件名、文号、标准号的行，不含单独的日期行。
- 评分员也是 claude-sonnet-5-5，A、B 同一评分员、同一批次。

### 2.5 机检

- `gongwen_lint.py`：对 `_正文/` 下每份文书全文跑全部检查，记录 P0、P1、P2 和【待补】【待核实】标记数（不含 gongwen-format）。
- `fact_diff.py --ledger`：以“用户消息 + 全部输入材料”为台账，列出交付内容中有、输入中没有的数字（没有 `_正文` 的查 `_回复.md`）。
- `check_docx.py`：对 gongwen-format 用例生成的每个 .docx 检查。
- 输入完整性：运行前后对比输入材料副本的 SHA-256。
- 机检工具用评测时仓库里的版本，第一轮和第二轮之间工具有修订（第七节）。

### 2.6 触发评测

模拟 Agent 工具按 description 选 skill：给 claude-sonnet-5-5 子智能体看全部 22 个 skill 的 name 和 description，再给一批用户说法，为每条说法选一个 skill 或“无”，只依据描述判断，不读文件。说法取自各 skill 的 `evals/trigger.json`（每个 skill 10 条正例、10 条反例，共 440 条，其中 429 条文字不重复），随机打乱，分 8 批、每批 55 条。判定：正例选中来源 skill 为对；反例没有选中来源 skill 为对。

### 2.7 隔离核查

- 逐份扫描 `_过程.md` 和 `_回复.md` 中的仓库路径：A 组第二轮 3308 处、第一轮 1976 处，全部在所属 skill 目录内，没有 `evals/` 下的文件；B 组两轮均为 0 处。A 组 gongwen-format 第 3 批另自述对仓库根目录做过一次按文件名的 Glob（只看到文件名）。
- 子智能体自述有超出本批请求目录的操作（列上级目录、通配符、递归搜索），见局限 5。

## 十一、局限

评分与对比的可信度

1. **评分员与被评模型是同一个模型。** 评分员、A 组、B 组都是 claude-sonnet-5-5，可能有自评偏差。A 组输出常带 skill 的明显痕迹（【起草说明】、素材台账），盲评只能做到部分盲化。
2. **两轮推理强度不同。** 第一轮的运行和评分为 high，第二轮 A 组复测的运行和全部评分为 max，B 组输出沿用第一轮（high）。因此：第二轮 A、B 的差距包含推理强度的差异，等条件的对比只有第一轮；两轮 A 组的差异分不清有多少来自修复、有多少来自更高的推理强度；max 下的表现可能高于普通使用时的表现。新增 3 条用例的 B 组为第二轮新跑，简报未记录它们的推理强度。
3. **修复与评测同源，没有留出集。** 修复是针对第一轮的失败项做的，复测用的仍是同一批用例（另加 3 条），触发评测的 description 调整也看过同一批说法。第二轮的数字因此偏乐观，不等于在新用例上的表现。
4. **每条用例只跑一次，评分有波动。** 同一批 B 组输出在两轮各评一次（口径和推理强度不同）：2627 条文字未变的期望中，128 条的判定改变（4.9%），一升一降基本抵消（62 条由通过变未通过，66 条反过来）；编造判定的变化更大（4.1）。A 组：2627 条文字未变的期望中，34 条由通过变为未通过，54 条由未通过变为通过，2 条两轮都没通过。单个 skill 两轮之间的变化在 −1.7 到 +4.5 个百分点，每个 skill 只有 14～22 条用例，小样本差距解读时要谨慎。

运行与隔离

5. **隔离不完全。** 任务说明要求子智能体只读本批请求的工作目录，但这些目录都放在同一个上级目录下（目录名是哈希，看不出分组），收尾检查时常用的通配符、递归命令容易越界。按 `_过程.md` 的自述统计（逐份扫描后人工分级，只能发现自述了的情形，是下限）：

   | | A 第一轮 | A 第二轮 | B（两轮共用） |
   |---|---|---|---|
   | 批次总数 | 99 | 101 | 101（其中第一轮 99） |
   | 自述超出本批请求目录的批次 | 16 | 31 | 29 |
   | 　其中输出里出现其他请求文件的文字片段 | 4 | 6 | 1 |
   | 　其中读取了其他请求文件内容、但输出里没有正文文字 | 0 | 9 | 1 |
   | 　其中只看到目录名、文件名或大小 | 12 | 16 | 27 |

   “文字片段”指 Grep 或命令的输出里带出了其他请求文件中的几行文字；“读取了内容”指前几个字节、首行“模型：……”、文件类型、括号计数、编码或 BOM 检测、匹配的文件名等。例如 gongwen-report 第 1 批（A 组）自述核对脚本的通配符写得过宽，读到了其他请求目录里的正文文件，只统计了括号数量并打印路径；B 组有 27 个批次只列出了其他请求目录的目录名或文件名，未读内容。这些子智能体都自述没有使用这些信息、没有改动其他目录，运行时没有拦截，也无法独立核实“没有使用”。粗略的敏感性检查：把被标记的批次全部排除，两组批次都没被标记的 176 条用例上，A 组 98.4%（1223/1243），B 组 53.7%（668/1243），与全部用例的 98.6% 对 54.1% 相差不大；A 组被标记批次的通过率 98.9%（872/882），未标记的 98.5%（1762/1789）；B 组被标记的 56.5%（479/848），未标记的 53.0%（967/1823）。
6. **新增用例只有一轮。** gongwen-review 17、18 和 gongwen-format 17 是第二轮新增的，只有一轮结果（A 组 19/19，B 组 10/19），没有修复前后的对比，也无法看出单次波动。
7. **公开文件清单不含日期行。** 清单只收录含书名号文件名、文号、标准号的行，skill 内置资料里单独的日期（如申报系统开放日、媒体报道日期）不在其中，所以引用这些日期会被评分员判为“输入里没有”。第二轮 A 组的 2 次编造（4.2）就是这样来的，复核后不算编造，v1.1 改进清单的收录范围。
8. **输入被改动的运行：A 组 2 次、B 组 7 次**（两轮相同，4.4）。A 组 2 次是任务要求更新的画像和禁用词文件，先备份再改；B 组 7 次中 2 次是未经同意改写画像、覆盖原稿，其余 5 次是任务本身要求更新的文件。
9. **触发评测是模拟。** 只给描述、只在 22 个 skill 里选，没有真实的 Agent 环境，也没有其他无关 skill 的干扰；description 是看过误判后调整的（第六节）。
10. **A 组的 skill 目录里实际含 `evals/`**（用例和期望）。任务说明禁止读取，过程记录里没有读取其内容的自述，但多数批次列目录时看到了该子目录的名字或其中的文件名（第二轮自述提到这一点的有 82 个批次，均称未打开）。

覆盖范围

11. **没有做跨模型评测和人工盲评。** 只测了 claude-sonnet-5-5；DeepSeek、豆包、Kimi、Qwen 或内网模型上的表现没有测，提示词版也没有单独评测。测试者手册和跨模型评测说明已备好，见 `docs/评测/`。
12. **没有经过一线测试者实测。** 所有材料都是虚构的；排版效果没有在 Word、WPS 里由测试者实测，正式印发前请打印核对。行业包是否升级 Stable，要等一线反馈和人工盲评。
13. **通用、约定的划分由模型完成。** 同一批期望在两轮的分类中有 50 条（1.9%）不同。约定期望天然对 B 组不利，所以单列通用口径。
14. **机检工具是本项目自己的。** gongwen_lint 和 check_docx 衡量的是与本项目规范的符合程度，天然有利于 A 组。
15. **单轮评测。** 按 skill 设计需要多轮确认的用例，在单轮下按首轮产出判定；当前日期固定为 2026 年 10 月 16 日，部分年终总结素材写有 11、12 月的数据；A 组只加载被测的单个 skill，跨 skill 路线只评了“说明路线”这一步；同一个子智能体连续处理 1～4 条用例，后面的用例在上下文里能看到前面的对话，A、B 两组条件相同。
16. **B 组是在 Claude Code 中能读写文件、能运行命令的强模型。** 网页版或较小模型装 skill 后的增益没有测。

评测之后的变动

17. **gongwen 用例 9 评测时看到的是旧的成熟度说法。** 第二轮评测之后，`skills/gongwen/references/skill-map.md` 里的成熟度说法由“均为 Beta”改为“核心 skill 为 Stable、行业包为 Beta”，用例 9 的 `expected_output` 描述同步；这是评测之后对 skill 的唯一一处内容改动，其余只涉及各 skill 的 `manifest.json` 和 `README.md` 的成熟度标签。

# 对 <评测目录>/grade_tasks/ 下每个评分说明各起一个子智能体
python evals/bench/aggregate.py --bench <评测目录> --out evals/results/v1.0-round1-raw.json

python evals/bench/defect_prep.py --bench <评测目录>   # 缺陷归因

# 修复 skill 之后的第二轮：整个评测目录先另存一份，再只重建 A 组（新增或输入改过的用例，B 组一并重建）
python evals/bench/prep.py --out <评测目录> --groups A
# 对 tasks_written.json 列出的任务说明各起一个子智能体
python evals/bench/machine.py --bench <评测目录>
# 期望文字改过，重新分类后，重新生成盲评任务，A、B 全部重评
python evals/bench/grade_prep.py --bench <评测目录>
python evals/bench/aggregate.py --bench <评测目录> --out evals/results/v1.0-raw.json --date 2026-10-20
python evals/bench/archive.py --bench <评测目录> --out evals/results/v1.0-runs
