# 国标排版（gongwen-format）

把写好的公文正文排成符合 GB/T 9704-2012《党政机关公文格式》的 docx，检查、修复已有 docx 的格式，把 gongwen-review 的核稿意见写成 Word 批注。所有参数来自 `references/_shared/rules/gbt9704.md`。

## 适用范围

- 适用：
  - 正文（.txt、.md 或用户粘贴的文字）排成 docx：红头（文件格式）、信函、纪要、白头（无版头的公文）、材料（总结、讲话稿等，只有标题和正文）、简报（报头、各篇、报尾）。正文中的简单管道表格转成 Word 表格。
  - 检查已有 docx 是否符合国标，输出 P0/P1/P2 问题清单；修复其页面、字体字号、行距、缩进、页码。
  - 把“核稿意见.json”写成 Word 批注；告诉用户在 WPS、Word 里怎么手动设置。
  - 行业包起草的本行业专用文书，排版也归本 skill。
- 不适用：
  - 起草法定公文转 gongwen-draft，讲话稿转 gongwen-speech，总结、汇报等转 gongwen-report，其他按文种转对应起草 skill；装有行业包时，本行业专用文书的起草交对应行业包。只起标题、搭提纲，转 gongwen-title。
  - 压缩篇幅、改写内容，转 gongwen-polish；去 AI 腔，转 gongwen-humanize；去免责、对冲、态度不明，转 gongwen-direct。
  - 查错别字、提法、标点数字、行文规则等内容问题，转 gongwen-review。本 skill 只把 review 的结论写成批注，不自己核稿。
  - 用户要求排版时顺便改文字的，说明本 skill 不改内容，建议先用上述 skill 改完再排。
- 转交方式：能调用其他 skill 的环境直接调用；目标 skill 未安装或在网页环境的，按 `references/_shared/style/output-format.md` 第四部分转交（交接卡、新开对话粘贴说明、安装命令）。

## 开工检查

1. 保密：按 `references/_shared/guardrails.md` 第一条执行。材料或版式信息中出现密级标识（绝密、机密、秘密、★）或“内部资料”“工作秘密”等字样时，立即停止，建议用户在单位内网自行运行脚本；版式信息的“密级”字段只供用户在内网使用。
2. 单位画像：工作目录存在 `.gongwen/单位画像.md` 时先读取，取“发文机关标志”“发文字号格式”“红头或白头”“党政两套代字”“单位规定字体”“写作角色和默认模式”；不存在时查 `~/.gongwen/单位画像.md`，都没有时按 `references/_shared/profiles/roles.md` 第九节“无画像降级”处理，版式按第二步第2款先排，回复末尾问一句要红头、白头还是普通材料；画像没有红头设置的，同样按第二步第3款说明。
3. 运行环境：能执行命令时，先运行 `python -c "import docx; print(docx.__version__)"`。报错或低于 1.2.0 时，提示 `pip install -U python-docx`；用户不能安装的，走“没有 Python 环境时”。
4. 首轮交付：材料在手就直接排版交付，缺的要素写【待补】，不先问版式细节；提问不超过 3 个，放在回复末尾（`references/_shared/profiles/roles.md` 第十节）。仅涉密时停下。
5. 残留标记：正文中有【待补】【待核实】的，排版照做，提醒用户补齐后再定稿，不替补。
6. 起草说明：【起草说明】之后的内容不排版，脚本读到这一行自动停止。
7. 交接卡：用户粘贴了交接卡的，按卡上的单位画像、当前模式、任务和已确认事项开工，卡上已有的不再问。

## 工作流程

### 第一步　判断任务，选脚本

| 用户要什么 | 用哪个脚本 |
|---|---|
| 把正文排成 Word、套红头、出信函、纪要或简报 | `scripts/build_docx.py`，之后自动运行检查 |
| 看看这个 docx 格式对不对 | `scripts/check_docx.py` |
| 这个 docx 格式乱了，帮我改 | `scripts/fix_docx.py`，之后自动运行检查 |
| 把核稿意见写进文档 | 先把送审稿 build 成 docx，再 `scripts/annotate_docx.py`；终稿不加批注（第五步） |
| 我自己在 WPS 里改，告诉我怎么设 | 不用脚本，按 `references/manual-setup.md` 给步骤 |
| 想先看看排出来的样子 | 本机有 LibreOffice 且标准字体齐全时用 `scripts/preview_docx.py` 转成逐页图片 |
| 想知道本机标准字体装齐没有、缺的怎么装 | `scripts/gw_fonts.py` |

`scripts/gw_*.py` 是公共模块，不单独运行（`gw_fonts.py` 除外）。脚本用法均可加 `--help` 查看。

### 第二步　整理版式信息（生成 docx 时）

1. 按 `references/meta-fields.md` 整理“版式信息.json”，放在正文同目录。
2. 版式按以下顺序确定：用户本轮指定 → 单位画像 → 文种默认（函用信函；纪要有纪要版头的用纪要格式；其他法定公文用白头；总结、讲话稿等材料用材料版式；工作简报、专题简报、会议简报用简报版式）。
3. 按文种默认排白头的，在交付说明中写一句：“如需红头，请提供：发文机关标志（如‘××市××局文件’）、发文字号；请示、报告另提供签发人姓名。”教学模式附上依据 GB/T 9704-2012 7.2.4（发文机关标志）、7.2.5（发文字号）、7.2.6（签发人）。单位画像或单位类型一般不用红头的（如社区），不写这句。
4. 发文机关标志、代字从画像取；党委发文和行政发文分开，不能混用。
5. 用户要求把应发红头的正式文件改成白头或便笺、以减少发文数量的，按 `references/_shared/guardrails.md` 第六条第 3 款说明不能这样做，仍按正式文件排。
6. 发文字号的序号、成文日期、签发人、印发日期只用用户给的。序号未编的，写“代字〔年份〕【待补：序号】号”，不编号码，年份取自成文日期（日期也没有的同样写【待补】）；不拿当天日期充当成文日期；用户只说“周五”“月底”等相对时间的，日期写【待补：具体日期】，不推算。
7. 本单位制度与国标不一致的写法，按本单位制度排，检查时按第六步第3款加 `--allow`。
8. 用户没提供版式信息、正文结构规范时，可以不写 JSON，脚本会自动识别标题、主送机关、附件说明、署名和成文日期。
9. 简报：无国家标准格式，以下为常见做法，以各单位往期样式为准，需一致的在 Word 中微调。报头、各篇（一期可有多篇，同材料版式）、报尾按 `references/manual-setup.md` 第十四部分，字段见 `references/meta-fields.md`；正文里已写报头报尾的（gongwen-brief 模板）直接识别。简报名称、期号、编印单位、印发日期缺的写【待补】；报送范围、印数没给的不排，不编。篇目标题认的是不带句末标点的短行，请用户核对识别结果。

### 第三步　生成 docx

```text
python scripts/build_docx.py <正文文件> --meta <版式信息.json> -o 公文/<YYYYMMDD>-<简短标题>/成稿.docx [--layout 红头] [--allow DOCX-050]
```

1. 用户直接粘贴正文的，先存为 `公文/<YYYYMMDD>-<简短标题>/正文.txt`（已存在时加 -v2），再运行脚本。
2. 无论粘贴还是给文件，成稿一律用 `-o` 写到 `公文/<YYYYMMDD>-<简短标题>/`（日期取当天），不得省略（不写 `-o` 时脚本输出在输入文件旁，违反输出规范第2条）。文件名和同名处理见该条。
3. 读脚本报告，逐项核对：
   - “识别结果”：标题、主送、附件、署名、日期是否认对；认错的，在版式信息中写明字段后重新生成。一级标题与正文同段（“一、××。正文”）的，脚本按正文排、不设黑体（长句无法与正文句区分），告知用户拆成独占一行后重排，不自行改文字。
   - “待补事项”：脚本写入的【待补】标记，逐条转告用户。
   - “字体”：本机是否装齐标准字体；缺失或无法检测时，报告开头有醒目的“字体缺失”区块（见第 4 款）。
   - “回读检查”：P0、P1 清单。
4. 缺字体（严格模式，不降级）：文件中一律写入标准字体名，脚本没有降级开关，严禁改用或建议任何替代字体（仿宋、楷体、华文中宋、宋体加粗等都不行）。报告出现“字体缺失”或“无法检测”区块时，回复开头先醒目告知：缺哪些字体；在本机用 Word/WPS 打开会被自动换字体显示，看到的不是正式效果，不能据此核对版式或打印；再逐款转告报告中的获取途径和安装方法（也可运行 `python scripts/gw_fonts.py`），请用户自行下载安装后重新打开核对。检测的是运行脚本的电脑，用户在别的电脑上打开的，请其在那台电脑上核对。方正小标宋简体是商业字体，需单位授权；本工具不提供、不打包字体。
5. 标题超过一行（二号字每行约 20 字）时，脚本在词意完整处自动分行，上行不短于下行，并在报告中写出分行结果。断行不合适的，在版式信息“标题”中用 `\n` 指定，或在正文文件中把标题分成两行；用户分好的行不再改动。
6. 表格：正文中的 Markdown 管道表格（表头行、分隔行“|---|”、数据行）转成全框线、表头加粗、仿宋四号（版式信息可改“表格字体”“表格字号”）、与版心同宽的 Word 表格；上一行是“表1　××情况表”这类表题的，居中排在表格上方。不支持合并单元格；缺分隔行的竖线行不转换，报告会提示。
7. 单位规定字体：画像中记有“单位规定字体”，或用户明确说明本单位制度规定了字体（如正文用方正仿宋_GBK）时，各脚本加 `--unit-fonts "仿宋=方正仿宋_GBK"`（build 的版式信息可写 `"unit_fonts": {"仿宋": "方正仿宋_GBK"}`，命令行优先）。该角色改写单位字体名，严格模式不变：没装同样报“字体缺失”并引导安装（向单位信息中心或办公室索取），不回退国标或其他字体；报告写明“按单位规定使用 X（国标为 Y）”。用户只是没装字体想换字体的，不属于单位规定，不得用该参数。

### 第四步　修复已有 docx

```text
python scripts/fix_docx.py <原文件.docx> [-o <输出.docx>] [--layout 白头] [--seal 是|否] [--allow DOCX-050]
```

1. 脚本按段落文字识别角色（规则见 `references/check-items.md` 第二节），统一页面设置、字体字号、行距、缩进、页码，输出“原名-修复.docx”和“原名-修复-修复报告.md”，原文件不动。
2. 把修复报告中的“识别结果”和“修复后检查”告诉用户；报告开头有“字体缺失”区块的，按第三步第 4 款处理。识别有误的段落，用 `--layout` 指定版式，或建议用户把正文另存为 .txt 后用 build_docx.py 重排。
3. 发文字号括号、日期虚位这类要改文字才能消除的问题，脚本不改，列入报告。逐条向用户确认后，在 Word 中修改，或改正文后重新生成。

### 第五步　写入核稿批注

```text
python scripts/annotate_docx.py <送审稿.docx> <核稿意见.json> [--author gongwen-review]
```

1. 批注加在由送审稿排出的 docx 上，因为核稿意见的 excerpt 取自送审稿（JSON 的 `source_file` 指明是哪份）。先用 build_docx.py 把送审稿按与成稿相同的版式信息排成 docx（如 `python scripts/build_docx.py 送审稿.txt --meta 版式信息.json`，默认输出“送审稿.docx”），再运行上面的命令。按意见改过的终稿（成稿.docx）不加批注，excerpt 多已改掉，大部分条目会定位不到。
2. 核稿意见.json 由 gongwen-review 输出，结构为 `{"source_file": "...", "issues": [{"level", "gate", "category", "excerpt", "message", "suggestion", "basis"}]}`，其中 `excerpt` 是原文中逐字一致的连续片段，脚本靠它定位批注位置。check_docx.py 的 `--json` 输出也能直接写成批注。
3. 脚本按 excerpt 定位，输出“原名-批注.docx”和批注报告；报告中“未定位”的条目逐条告诉用户原因，请用户手工处理。
4. 只写批注，不改正文，不写修订。

### 第六步　交付前检查

1. 运行 `python scripts/check_docx.py <成稿.docx> --json`（build、fix 已自动运行的，看报告即可）。
2. P0 为 0 才能交付。P0 不为 0 时：格式类问题改版式信息或用 fix_docx.py 修好后重查；文字类问题（发文字号、成文日期写法）向用户确认后改正文重排。
3. 例外：画像或用户说明本单位制度规定了与国标不同的写法（如企业办法规定年份用方括号）的，回读和自检都加 `--allow DOCX-050`，命中项降为 P2、注明“按本单位制度保留”，不计入 `--strict`；交付说明中逐条写明与国标的差异和所允许的检查项号。检查有单位规定字体的，同样加 `--unit-fonts`。
4. P1 逐条告诉用户。残留的【待补】【待核实】标记 check_docx.py 报 P2（DOCX-080），单独计数，提醒补齐后再定稿；文档中有【起草说明】的报 P1（DOCX-082），交付前删去其及之后的内容；正文中残留 Markdown 表格行的报 P1（DOCX-100），用 build_docx.py 重新生成。其余 P2 汇总成一句。
5. 有条件时目检：本机装有 LibreOffice 时运行 `python scripts/preview_docx.py <成稿.docx>`，逐页看 PNG（没有 pymupdf 时看 PDF），核对落款是否单独成页、层次标题是否落在页末、标题回行是否匀称、署名和日期的位置、版记是否在最后一页底部。找不到 LibreOffice 时脚本只提示，不影响交付；本机缺任一标准字体时脚本拒绝渲染（退出码 3，无绕过选项），先按字体缺失提示安装字体；排版与 Word、WPS 有细微差异，以打印核对为准。

### 没有 Python 环境时

网页版大模型、内网没有 Python 的电脑，或用户不愿安装时，按文字流程完成：

1. 逐行判断用户正文中的标题、主送机关、各级层次标题、表格、附件说明、署名、成文日期、附注、版记。
2. 判断规则：首行以“关于”开头或以文种结尾的是标题；标题后以冒号结尾的是主送机关；“一、”“（一）”“1.”“（1）”开头的是一至四级标题，二至四级标题与正文同段时，第一个句号及以前是标题；“附件：”开头的是附件说明；末尾的单位名称行和日期行是署名和成文日期，日期下一行的括号行是附注。
3. 输出一份“本文排版清单”，逐项写明：选用的版式；每个要素的原文（标题、主送等写原文，层次标题列出各级各几处）及其字体、字号、对齐、缩进；署名和日期按盖章与否的排法和算出的缩进字数；版头、版记要填的内容，缺的写【待补】。
4. 清单后附 `references/manual-setup.md` 中用户用得上的步骤（页面设置、正文样式、文档网格、页码、字体准备与安装必附；红头、信函、纪要、版记、表格按版式和正文附）。
5. 说明“未运行脚本检查，请按手动设置清单第十三部分打印核对”。
6. 排版一般是路线最后一站，完成后不再输出交接卡，交付说明写“路线已完成”；路线还有下一站时，按 `references/_shared/style/output-format.md` 第四部分输出更新后的交接卡。

## 输出规范

1. 正文排版遵守 `references/_shared/style/output-format.md`，输入是按它写的纯文本正文。
2. 交付文件放在 `公文/<YYYYMMDD>-<简短标题>/`，同名加 -v2、-v3，不覆盖。默认文件名：输入“正文.txt”输出“成稿.docx”；输入“正文-××.txt”输出“成稿-××.docx”（如“正文-单位总结.txt”输出“成稿-单位总结.docx”）；其他输入输出“<输入文件名>.docx”（如“送审稿.txt”输出“送审稿.docx”，不与终稿重名）。批注版由送审稿排出，名为“送审稿-批注.docx”一类。
3. 对话中的交付说明：缺字体或无法检测字体时，字体缺失提示放在最前面（第三步第4款）；其后依次写：文件位置；版式和是否按盖章排；识别结果（请用户核对）；待补事项；检查结论（P0、P1 条数，每条一行写问题和条款号，转译模式按“角色适配”；待补、待核实标记按 P2 单独报处数）；与本次相关的已知限制。没有内容的项省略，后面依次前移。不整篇复述正文。
4. 排版不改内容。允许的格式性处理只有：去掉段首空格；主送机关末尾统一为全角冒号；版式信息中“2026-10-16”写法的日期转成“2026年10月16日”；附注加圆括号；抄送数组连成一句加句号；缺失要素写【待补】；Markdown 表格转成 Word 表格（去掉竖线和加粗记号，文字不变）。用户材料中加引号的提法、做法名称原样保留。其他文字问题只报告，不动手。

交付说明示例（高效模式）：

```text
已生成：公文/20260915-秋季消防安全检查/成稿.docx（红头，按加盖印章排）
识别结果：标题、主送机关、1 张表格、署名、成文日期、附注均已识别，请核对。
检查：P0 0 项，P1 0 项。
```

## 自检清单

- [ ] 已按保密红线检查材料，未处理涉密内容。
- [ ] 版式与画像、文种一致；党委、行政的标志和代字没有混用；排白头的，已说明改红头要补的要素。
- [ ] 发文字号、日期、签发人、印发机关都来自用户或画像，缺的写了【待补】；相对时间没有推算成具体日期。
- [ ] 识别结果已逐项核对，认错的已用版式信息纠正。
- [ ] check_docx.py 结果 P0 为 0；按本单位制度保留的项已加 `--allow` 并在交付说明中写明差异。
- [ ] 残留【待补】【待核实】已按 P2 单独计数并提醒。
- [ ] 批注加在送审稿排出的 docx 上，终稿没有加。
- [ ] 缺字体或无法检测时，已在回复开头告知并附获取、安装方法，未改用或建议替代字体；原文件未被覆盖。
- [ ] 正文文字与输入一致（只有输出规范第 4 条允许的处理），用户加引号的提法、做法名称原样保留。

有 Python 环境时运行：`python scripts/check_docx.py <文件.docx> --strict`（本单位制度保留的项加 `--allow DOCX-050`）。不能运行脚本时，按 `references/manual-setup.md` 第十三部分人工核对，并在交付说明中写明“未运行机检”。

## 已知限制

1. 版记用浮动表格固定在最后一页版心底部。WPS 部分版本可能不按底端定位；改动正文后要重新检查。版记页落在单页、需要加空白页的情况（7.5），脚本不处理，需人工调整。
2. 发文机关标志距版心上边缘 35 mm、红线在发文字号下 4 mm，由段前距和段落边框近似实现，误差约 1～2 mm，正式印发前打印核对。套印好的红头纸时，改用白头版式只排主体，先试印。
3. 不生成印章、院徽、校徽图片；加盖印章的版式只预留位置。联合行文加盖印章时，署名与印章的对应排列只做近似，需人工调整。
4. 标题自动分行按常用词表找断点，个别专有名词可能被断开，须看分行结果。
5. 为使落款不单独成页、标题不落页末，正文最后一段（或附件说明）、空行、署名、成文日期、附注依次设“与下段同页”，不带句号、独占一行的层次标题和表题同样处理；换页时至少一行正文随落款下移，末页可能留较多空白。7.3.5.5 允许空间不足时调整行距、字距，脚本不自动压缩，需要时人工微调。
6. 署名和日期：不加盖印章时用左缩进定位，日期首字比署名首字右移二字是精确的；加盖印章时二者中心对齐是精确的，日期“右空四字”按半角数字 0.5 字估算，LibreOffice 下实测约右空 3.4 字。
7. 只排附件说明，不排附件正文（附件另面编排时请单独排版）。不支持命令（令）格式。
8. 正文表格只支持简单管道表格（第三步第6款）。已有 docx 中的正文表格，fix_docx.py 不调整，check_docx.py 只查宽度和字体字号。
9. 批注只按 excerpt 文字定位，跨段、在页眉页脚或文本框中的意见无法定位；不写修订。
10. 缺标准字体的处理见第三步第4款；仿宋_GB2312 缺生僻字时，该字需单独换字体并打印核对。
11. 段落角色靠文字模式识别。没有“关于”、不以文种结尾的标题，或不按“一、（一）1.（1）”编号的层次，可能认错，须看识别结果。

## 角色适配

- 教学模式：每次交付附“这次用到的国标要素”3～5 条，写清条款号和 Word、WPS 默认设置哪里不符合国标（如默认等线字体、单倍行距、无文档网格）；用户自己操作时，按 `references/manual-setup.md` 带着一步步做。
- 高效模式：不展开讲解，直接出 docx；只报告识别有疑问的项、待补事项和 P0、P1（每条一行写问题和条款号）；多份材料一次给齐时逐份运行脚本，最后汇总一张表。
- 转译模式：接受用户直接粘贴的文字或 Word 文件，不要求先整理格式；交付时附在 WPS、Word 中打开、套用格式和另存的步骤，检查结论用业务人员听得懂的话写（如“页码格式不对”）。默认不写条款号和 DOCX 规则号，也不带入教学模式的“用到的国标要素”；有 P0、P1 时，才在该句末括注一处标准条款号。
- 审稿模式：只运行 check_docx.py，输出一页纸格式问题清单（P0 在前，每条写位置、问题、依据、改法），不修改文件；用户说“帮我改”时再运行 fix_docx.py。
- 严谨模式：另查党组织名称是否用全称、党委文件的版头和代字是否与发文主体一致、发文机关署名与标志是否一致；对外发布的材料提醒用户确认附注（如“此件公开发布”）。
