# 国标排版（gongwen-format）

把写好的公文正文排成符合 GB/T 9704-2012《党政机关公文格式》的 docx，检查、修复已有 docx 的格式，把 gongwen-review 的核稿意见写成 Word 批注。所有参数来自 `references/_shared/rules/gbt9704.md`，数值集中在 `assets/gbt9704_params.json`。

## 适用范围

- 适用：
  - 正文（.txt、.md 或用户粘贴的文字）排成 docx：红头（文件格式）、信函、纪要、白头（无版头的公文）、材料（总结、讲话稿等，只有标题和正文）。
  - 检查已有 docx 是否符合国标，输出 P0/P1/P2 问题清单。
  - 修复已有 docx 的页面、字体字号、行距、缩进、页码。
  - 把“核稿意见.json”写成 Word 批注。
  - 告诉用户在 WPS、Word 里怎么手动设置。
- 不适用：
  - 起草法定公文、讲话稿，转 gongwen；起草总结、汇报等综合文稿，转 gongwen-report；只起标题、搭提纲，转 gongwen-title。
  - 去 AI 腔，转 gongwen-humanize；去免责、对冲、态度不明，转 gongwen-direct。
  - 查错别字、提法、标点数字、行文规则等内容问题，转 gongwen-review。本 skill 只把 review 的结论写成批注，不自己核稿。
  - 用户要求“排版时顺便改改文字”的，先说明本 skill 不改内容，建议先用上述 skill 改完再排版。

## 开工检查

1. 保密：按 `references/_shared/guardrails.md` 第一条执行。材料或版式信息中出现密级标识（绝密、机密、秘密、★）或“内部资料”“工作秘密”等字样时，立即停止，告知用户涉密信息不得输入联网 AI 工具，建议在单位内网环境中自行运行脚本。版式信息中的“密级”字段只供用户在内网自行使用。
2. 单位画像：工作目录存在 `.gongwen/单位画像.md` 时先读取，取“发文机关标志”“发文字号格式”“红头或白头”“党政两套代字”“写作角色和默认模式”；不存在时查 `~/.gongwen/单位画像.md`，都没有时按 `references/_shared/profiles/roles.md` 第九节“无画像降级”处理，版式问题只问一个：要红头、白头还是普通材料。
3. 运行环境：能执行命令时，先运行 `python -c "import docx; print(docx.__version__)"`。报错或低于 1.2.0 时，提示 `pip install -U python-docx`；用户不能安装的，走“没有 Python 环境时”。
4. 残留标记：正文中有【待补】【待核实】的，排版照做，交付时提醒用户补齐后再定稿；不替用户补。
5. 起草说明：正文文件中【起草说明】之后的内容不排版，脚本读到这一行自动停止。

## 工作流程

### 第一步　判断任务，选脚本

| 用户要什么 | 用哪个脚本 |
|---|---|
| 把正文排成 Word、套红头、出信函或纪要 | `scripts/build_docx.py`，之后自动运行检查 |
| 看看这个 docx 格式对不对 | `scripts/check_docx.py` |
| 这个 docx 格式乱了，帮我改 | `scripts/fix_docx.py`，之后自动运行检查 |
| 把核稿意见写进文档 | 先把送审稿 build 成 docx，再 `scripts/annotate_docx.py`；终稿不加批注（第五步） |
| 我自己在 WPS 里改，告诉我怎么设 | 不用脚本，按 `references/manual-setup.md` 给步骤 |
| 想先看看排出来的样子 | 本机有 LibreOffice 时用 `scripts/preview_docx.py` 转成逐页图片 |

`scripts/gw_*.py` 是公共模块，不单独运行。脚本用法均可加 `--help` 查看。

### 第二步　整理版式信息（生成 docx 时）

1. 按 `references/meta-fields.md` 整理“版式信息.json”，放在正文同目录。
2. 版式按以下顺序确定：用户本轮指定 → 单位画像 → 文种默认（函用信函；纪要有纪要版头的用纪要格式；其他法定公文用白头；总结、讲话稿等材料用材料版式）。
3. 发文机关标志、代字从画像取；党委发文和行政发文分开，不能混用。
4. 用户要求把应发红头的正式文件改成白头或便笺、以减少发文数量的，按 `references/_shared/guardrails.md` 第六条第 3 款说明不能这样做，仍按正式文件排。
5. 发文字号的序号、成文日期、签发人、印发日期只用用户给的。画像只有代字格式时，序号写【待补】，不编号码，不拿当天日期充当成文日期。
6. 用户没提供版式信息、正文结构规范时，可以不写 JSON，脚本会自动识别标题、主送机关、附件说明、署名和成文日期。

### 第三步　生成 docx

```text
python scripts/build_docx.py <正文文件> --meta <版式信息.json> -o <输出.docx> [--layout 红头] [--font-fallback]
```

1. 用户直接粘贴正文的，先存为 `公文/<YYYYMMDD>-<简短标题>/正文.txt`（已存在时加 -v2），再运行脚本。
2. 输出路径按 `references/_shared/style/output-format.md`：`公文/<YYYYMMDD>-<简短标题>/成稿.docx`。不写 `-o` 时输出到输入文件同目录，文件名按输入定：输入“正文.txt”输出“成稿.docx”；输入“正文-××.txt”输出“成稿-××.docx”（如“正文-单位总结.txt”输出“成稿-单位总结.docx”）；其他输入输出“<输入文件名>.docx”（如“送审稿.txt”输出“送审稿.docx”，不与终稿重名）。文件已存在时自动加 -v2、-v3，不覆盖。
3. 读脚本报告，逐项核对：
   - “识别结果”：标题、主送、附件、署名、日期是否认对。认错时，在版式信息中写明对应字段后重新生成。
   - “待补事项”：脚本写入的【待补】标记，逐条转告用户。
   - “字体”：本机缺标准字体时的警告。
   - “回读检查”：P0、P1 清单。
4. 缺字体：默认写入标准字体名（仿宋_GB2312、楷体_GB2312、黑体、方正小标宋简体），用户在装了这些字体的电脑上打开即可正常显示。用户要在本机看效果，或单位没有授权字体的，加 `--font-fallback`，脚本改用本机已有的仿宋、楷体、黑体，标题用华文中宋或宋体加粗，并在报告中列明。不打包、不下载任何字体文件。
5. 标题超过一行（二号字每行约 20 字）时，脚本在词意完整处自动分行，上行不短于下行，并在报告中写出分行结果。断行不合适的，在版式信息“标题”中用 `\n` 指定，或在正文文件中把标题分成两行；用户分好的行不再改动。

### 第四步　修复已有 docx

```text
python scripts/fix_docx.py <原文件.docx> [-o <输出.docx>] [--layout 白头] [--seal 是|否] [--font-fallback]
```

1. 脚本按段落文字识别角色（规则见 `references/check-items.md` 第二节），统一页面设置、字体字号、行距、缩进、页码，输出“原名-修复.docx”和“原名-修复-修复报告.md”，原文件不动。
2. 把修复报告中的“识别结果”和“修复后检查”告诉用户。识别有误的段落，用 `--layout` 指定版式，或建议用户把正文另存为 .txt 后用 build_docx.py 重排。
3. 发文字号括号、日期虚位这类要改文字才能消除的问题，脚本不改，列入报告。逐条向用户确认后，在 Word 中修改，或改正文后重新生成。

### 第五步　写入核稿批注

```text
python scripts/annotate_docx.py <送审稿.docx> <核稿意见.json> [--author gongwen-review]
```

1. 批注写在哪一版：批注加在由送审稿排出的 docx 上，因为核稿意见的 excerpt 取自送审稿（JSON 的 `source_file` 指明是哪份）。先用 build_docx.py 把送审稿按与成稿相同的版式信息排成 docx（如 `python scripts/build_docx.py 送审稿.txt --meta 版式信息.json`，默认输出“送审稿.docx”），再运行上面的命令。按核稿意见改过的终稿（成稿.docx）不加批注：excerpt 在终稿里多已改掉，大部分条目会定位不到。
2. 核稿意见.json 由 gongwen-review 输出，结构为 `{"source_file": "...", "issues": [{"level", "gate", "category", "excerpt", "message", "suggestion", "basis"}]}`，其中 `excerpt` 是原文中逐字一致的连续片段，脚本靠它定位批注位置。check_docx.py 的 `--json` 输出也能直接写成批注。
3. 脚本按 excerpt 定位，输出“原名-批注.docx”（如“送审稿-批注.docx”）和批注报告。报告中“未定位”的条目逐条告诉用户位置原因，请用户手工处理。
4. 只写批注，不改正文，不写修订。

### 第六步　交付前检查

1. 运行 `python scripts/check_docx.py <成稿.docx> --json`（build、fix 已自动运行的，看报告即可）。
2. P0 为 0 才能交付。P0 不为 0 时：格式类问题改版式信息或用 fix_docx.py 修好后重查；文字类问题（发文字号、成文日期写法）向用户确认后改正文重排。
3. 例外：本单位制度与国标不一致造成的 P0（如企业办法规定年份用方括号），按本单位制度保留，在交付说明中逐条写明与国标的差异。
4. P1 逐条告诉用户。残留的【待补】【待核实】标记 check_docx.py 报 P2（DOCX-080），单独计数，提醒补齐后再定稿；文档中有【起草说明】的报 P1（DOCX-082），交付前删去【起草说明】及其后的内容。其余 P2 汇总成一句。
5. 有条件时目检：本机装有 LibreOffice 时运行 `python scripts/preview_docx.py <成稿.docx>`，逐页看生成的 PNG（没有 pymupdf 时看 PDF）：落款是否单独成页、标题回行是否匀称、署名和日期的位置、版记是否在最后一页底部。找不到 LibreOffice 时脚本只提示，不影响交付。LibreOffice 与 Word、WPS 的排版有细微差异，以打印核对为准。

### 没有 Python 环境时

网页版大模型、内网没有 Python 的电脑，或用户不愿安装时，按文字流程完成：

1. 逐行判断用户正文中的标题、主送机关、各级层次标题、附件说明、署名、成文日期、附注、版记。
2. 判断规则：首行以“关于”开头或以文种结尾的是标题；标题后以冒号结尾的是主送机关；“一、”“（一）”“1.”“（1）”开头的是一至四级标题，二至四级标题与正文同段时，第一个句号及以前是标题；“附件：”开头的是附件说明；末尾的单位名称行和日期行是署名和成文日期，日期下一行的括号行是附注。
3. 输出一份“本文排版清单”，逐项写明：选用的版式；每个要素的原文（标题、主送等写原文，层次标题列出各级各几处）；每个要素对应的字体、字号、对齐、缩进；署名和日期按盖章与否的排法和计算出的缩进字数；版头、版记要填的内容，缺的写【待补】。
4. 清单后附 `references/manual-setup.md` 中用户用得上的步骤（页面设置、正文样式、文档网格、页码必附；红头、信函、纪要、版记按版式附）。
5. 说明“未运行脚本检查，请按手动设置清单第十二部分打印核对”。
6. 用户粘贴了交接卡的，按交接卡确定单位画像和角色模式，不再重复提问。排版一般是路线最后一站，完成后不再输出交接卡；路线还有下一站时，按 `references/_shared/style/output-format.md` 第四节输出更新后的交接卡。

## 输出规范

1. 正文排版遵守 `references/_shared/style/output-format.md`：输入就是按它写的纯文本正文。
2. 交付文件放在 `公文/<YYYYMMDD>-<简短标题>/`，同名加 -v2、-v3，不覆盖。默认文件名：输入“正文.txt”输出“成稿.docx”；输入“正文-××.txt”输出“成稿-××.docx”；其他输入输出“<输入文件名>.docx”。批注版由送审稿排出，名为“送审稿-批注.docx”一类，终稿不加批注。
3. 对话中的交付说明依次写：文件位置；版式和是否按盖章排；识别结果（请用户核对）；待补事项；字体提示；检查结论（P0、P1 条数及内容；待补、待核实标记按 P2 单独报处数）；与本次相关的已知限制。不整篇复述正文。
4. 排版不改内容。允许的格式性处理只有：去掉段首空格；主送机关末尾统一为全角冒号；版式信息中“2026-10-16”写法的日期转成“2026年10月16日”；附注加圆括号；抄送数组连成一句加句号；缺失要素写【待补】。其他文字问题只报告，不动手。

交付说明示例（高效模式）：

```text
已生成：公文/20261028-冬季安全生产大检查/成稿.docx（红头，按加盖印章排）
识别结果：标题、主送机关、2 个附件、署名、成文日期、附注均已识别，请核对。
待补：无。
字体：本机缺仿宋_GB2312、方正小标宋简体，已写入标准字体名；在装有这两种字体的电脑上打开即可。
检查：P0 0 项，P1 0 项。
提醒：版记在第 3 页（单页），双面印刷时按单位规定处理。
```

## 自检清单

- [ ] 已按保密红线检查材料，未处理涉密内容。
- [ ] 版式与画像、文种一致；党委、行政的标志和代字没有混用。
- [ ] 发文字号、日期、签发人、印发机关都来自用户或画像，缺的写了【待补】。
- [ ] 识别结果已逐项核对，认错的已用版式信息纠正。
- [ ] check_docx.py 结果 P0 为 0，或 P0 均为“按本单位制度保留”并已说明。
- [ ] 残留【待补】【待核实】已按 P2 单独计数并提醒用户。
- [ ] 写批注时，批注加在由送审稿排出的 docx 上，终稿没有加批注。
- [ ] 缺字体的警告已转告用户。
- [ ] 原文件未被覆盖。
- [ ] 正文文字与输入一致（只有上面“输出规范”第 4 条允许的处理）。

有 Python 环境时运行：`python scripts/check_docx.py <文件.docx> --strict`。不能运行脚本时，按 `references/manual-setup.md` 第十二部分人工核对，并在交付说明中写明“未运行机检”。

## 已知限制

1. 版记用浮动表格固定在最后一页版心底部。WPS 部分版本可能不按底端定位；改动正文后要重新检查。版记页落在单页、需要加空白页的情况（7.5），脚本不处理，需人工调整。
2. 发文机关标志距版心上边缘 35 mm、红线在发文字号下 4 mm，是用段前距和段落边框实现的近似位置，误差约 1～2 mm，正式印发前打印核对。用印好的红头纸套打时，改用白头版式只排主体，再对着红头纸试印。
3. 不生成印章、院徽、校徽图片；加盖印章的版式只预留位置。联合行文加盖印章时，署名与印章的对应排列只做近似，需人工调整。
4. 标题自动分行按常用词表找断点，个别专有名词可能被断开，要看一眼分行结果。
5. 落款不单独成页：正文最后一段（或附件说明）、空行、署名、成文日期、附注依次设“与下段同页”，换页时至少一行正文随落款下移，最后一页可能留出较多空白。GB/T 9704-2012 7.3.5.5 规定空间不足时可调整行距、字距，脚本不自动压缩，需要时人工微调。
6. 署名和日期的位置：不加盖印章时用左缩进定位，日期首字比署名首字右移二字是精确的；加盖印章时署名和日期中心对齐是精确的，日期“右空四字”按半角数字 0.5 字估算，LibreOffice 下实测约右空 3.4 字。
7. 只排附件说明，不排附件正文（附件另面编排时请单独排版）。不支持命令（令）格式。
8. 正文中的表格不调整字体字号；脚本只处理版记表格。
9. 批注只按 excerpt 文字定位，跨段、在页眉页脚或文本框中的意见无法定位；不写修订。
10. 不打包字体。打开文档的电脑缺字体时会显示为其他字体；仿宋_GB2312 缺生僻字时，该字需单独换字体并打印核对。
11. 段落角色靠文字模式识别。没有“关于”、不以文种结尾的标题，或不按“一、（一）1.（1）”编号的层次，可能认错，须看识别结果。

## 角色适配

- 教学模式：每次交付附“这次用到的国标要素”3～5 条，写清条款号和 Word、WPS 默认设置哪里不符合国标（如默认等线字体、单倍行距、无文档网格）；用户自己操作时，按 `references/manual-setup.md` 一步一步带着做。
- 高效模式：不解释，直接出 docx；只报告识别有疑问的项、待补事项和 P0、P1；多份材料一次给齐时逐份运行脚本，最后汇总一张表。
- 转译模式：接受用户直接粘贴的文字或 Word 文件，不要求先整理格式；交付时附在 WPS、Word 中打开、套用格式和另存的操作步骤，检查结论用业务人员听得懂的话写，如写“页码格式不对”，不写规则号。
- 审稿模式：只运行 check_docx.py，输出一页纸格式问题清单（P0 在前，每条写位置、问题、依据、改法），不修改文件；用户说“帮我改”时再运行 fix_docx.py。
- 严谨模式：另查党组织名称是否用全称、党委文件的版头和代字是否与发文主体一致、发文机关署名与标志是否一致；对外发布的材料提醒用户确认附注（如“此件公开发布”）。
