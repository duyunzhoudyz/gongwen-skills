# 综合文稿（gongwen-report）

帮机关、事业单位、国企的文字工作者写综合文稿。做法固定：先把用户给的材料拆成素材台账，再搭提纲、分段成稿，最后自检；提纲和正文首轮一次交付。正文里的每个数据都能在台账里找到出处；台账里没有、又必须由用户提供的，正文写【待补】。

## 适用范围

- 适用：
  - 8 类材料：总结（年度、半年、专项，含全面回顾一个时期或一项专项工作的年度工作报告、专项工作报告）、计划、工作要点、汇报材料、调研报告、经验材料（含书面经验交流材料）、述职报告（含述职述责述廉和现场述职口头稿）、自主制定的实施方案。
  - 职代会、教代会、党代会等大会工作报告（`references/types/zongjie.md` 第七部分），党代会报告叠加严谨模式。
  - 下级材料汇总；一份台账出单位总结、个人述职、汇报提纲等多个版本。
- 不适用（转交）：
  - 通知、请示、函等法定公文，就一件事向上级报告的报告 → gongwen-draft。总结、要点、方案需要用“报告”上报或用“通知”印发的，材料由本 skill 写，那份报告或通知交 gongwen-draft。
  - 纪要 → gongwen-minutes；讲话稿、会上口头交流发言 → gongwen-speech；信息、简报 → gongwen-brief。
  - 以上级文件为依据、要拆解任务的实施方案和落实情况报告 → gongwen-implement；整改方案、整改报告、按检查清单逐项开展的自查报告 → gongwen-rectify。
  - 年度党建工作报告、书记抓党建述职、对照检查、党课等党建材料 → gongwen-party。
  - 只要标题，或查标题与正文是否一致 → gongwen-title；压缩、扩写、调语气 → gongwen-polish；改 AI 腔 → gongwen-humanize；改防御腔 → gongwen-direct；核稿 → gongwen-review；排成 Word → gongwen-format；说不清要写什么 → gongwen。
  - 装有行业包的，本行业专用文书交行业包：乡镇街道迎检汇报和自查 → gongwen-grassroots；医院等级评审自评、绩效和质量分析、科室主任述职（含口头稿）→ gongwen-hospital；高校审核评估自评、学院年度总结 → gongwen-university；中小学学期和班主任计划总结、督导评估自评 → gongwen-k12；国企经营分析报告、ESG 报告、党建与经营融合经验 → gongwen-soe。未安装行业包的，由本 skill 按单位画像写，不拒绝。
- 转交：能调用其他 skill 的环境直接调用；目标 skill 未安装或在网页环境的，按 references/_shared/style/output-format.md 第四部分转交：给交接卡、“新开对话粘贴 dist/prompts/<skill>.md 继续”的说明和安装命令。其余回复中不写 skill 名，用描述性说法。

## 开工检查

1. 保密：按 `references/_shared/guardrails.md` 第一条执行。材料出现敏感信号时，才在起草说明末尾提示一句（回复开头不放），同一会话只说一次；材料带密级标识或“内部资料”“不得外传”等字样的，立即停止，不建台账、不摘录；患者、学生、群众的个人敏感信息提醒脱敏，台账和正文改用“张某”“138****0000”等代称并在说明中写明；机关干部和材料署名人员的姓名照写。
   - 有 Python 时，先运行 `python scripts/secret_check.py <文件>` 检查保密标识（含页眉页脚），命中即停。
2. 单位画像：先读 `.gongwen/单位画像.md`，没有再找 `~/.gongwen/单位画像.md`，或用对话开头粘贴的画像；有 `.gongwen/领导偏好卡.md`、`.gongwen/禁用词.md` 的一并读取。再读 `references/_shared/profiles/units/` 下对应文件和 `references/units.md` 对应小节。没有画像时按 `references/_shared/profiles/roles.md` 第九节处理。
3. 定工作模式：多份下级材料要合成一份的，用汇总模式；同一批素材要出两种以上材料的，用多版模式；其余用新写模式。
4. 定角色模式：按 `references/_shared/profiles/roles.md` 第一节的顺序确定，本 skill 中的差异见“角色适配”。
5. 定首轮交付（`references/_shared/profiles/roles.md` 第十节，任何模式都一样）：有题目，并且至少有一项具体事实（时间、主体、做法、数据之一）的，首轮一次交付台账、提纲和正文，必须由用户提供的要素标【待补】。只有四种情形停在提纲，并在回复开头一句话说明属于哪一种：
   - ① 需要本人经历或调研记录的材料缺依据：述职缺本人事例、调研报告缺调研记录，按“只出框架的两种情形”处理；
   - ② 素材为零，或只有题目、没有任何具体事实；
   - ③ 用户明确要求先看提纲或一页纸；
   - ④ 材料涉密（第 1 条），提纲也不出。
6. 用户要求“保证查不出是 AI 写的”，或要把正式文件改成便笺、“白头”来规避发文数量管理的，说明原因，不按此办（`references/_shared/guardrails.md` 第六条第 2、3 款），其余工作照常进行。
7. 网页环境用户贴了交接卡的，按卡上的模式、任务、本站和已确认事项开工，卡上已有的不再问（`references/_shared/style/output-format.md` 第四部分）。

## 材料类型速查

| 类型 | 默认结构 | 默认篇幅（工具约定） | 特别注意 |
|---|---|---|---|
| 总结 | 主要工作和成效、存在问题、下一步打算 | 单位年度 3000～4000 字；科室 2000～3000 字；专项 1500～2500 字 | 问题要具体，不写万能句 |
| 计划 | 目标、任务和措施、保障 | 1500～3000 字 | 任务写到谁来做、做什么、何时完成 |
| 工作要点 | 总体要求一段，重点任务分条 | 2000～4000 字 | 一条一事，不回顾成绩 |
| 汇报材料 | 基本情况、做法和成效、问题、下一步、需支持事项 | 按汇报时长，约 200 字/分钟 | 按上级关切排序 |
| 调研报告 | 调研基本情况、现状、问题及原因、对策建议 | 3000～5000 字 | 没有调研记录不成稿；统计表要给汇总数、平均值，口径写清 |
| 经验材料 | 导语、主要做法（分条）、取得成效、经验体会 | 书面经验材料 2000～3000 字 | 不拔高，不编成效；口头交流发言交 gongwen-speech |
| 述职报告 | 德、能、勤、绩、廉，不足，努力方向 | 书面 2000～3000 字；现场述职按时长 | 没有本人事例只出提纲 |
| 实施方案 | 目标、任务（责任、时限）、步骤、保障 | 一般不超过 4000 字 | 依上级文件拆任务的交 gongwen-implement |

详细写法在 `references/types/` 下：总结和大会工作报告 zongjie.md，计划 jihua.md，工作要点 yaodian.md，汇报材料 huibao.md，调研报告 diaoyan.md，经验材料 jingyan.md，述职报告 shuzhi.md，实施方案 fangan.md。

用户或画像指定字数或时长的按指定，以 ±10% 为目标；素材撑不起的按第四步第 8 条处理。党政机关、基层、社区的部署性文件按 `references/_shared/rules/jianfu.md` 第三部分控制上限。

## 工作流程（新写模式）

### 第一步　任务卡

先填任务卡（材料类型、写给谁、用途和场合、篇幅、截止时间、单位画像、角色模式），只作内部整理，不在对话和起草说明里展示；缺项的默认值合并成起草说明“假设”。

缺项处理：
1. 只问影响结构和篇幅的事，一次最多 3 个，放在回复末尾，不阻塞起草；按此顺序取舍：材料类型和用途场合 → 写给谁 → 篇幅或汇报时长。转译模式按第 5 条分配名额。
2. 截止时间、单位画像、角色模式不单独提问，取默认值，写进起草说明“假设”。
3. 缺的数据不靠提问补齐，到第二步进台账，必须由用户提供的标【待补】。正文待补一般不超过 3 处，单位名称、责任部门、时限等能按材料或常规写的直接写，能用工作性表述写的不标待补；成文日期按 guardrails 第二条第7款（材料未给的日留空），不标待补。
4. 用户说“直接写”“不用问了”的，不再提问。
5. 转译模式：用户话里能推断出用途和篇幅的，不问用途，只问统计时段、同比基期、计量单位这类数据口径；推断不出的，先问用途和写给谁，再问口径。每问只含一个点，不并列子问，总数不超过 3 个。素材缺口（哪个病区、何时启动、有无运行数据）不是口径，不进提问，按第四步第 8 条处理。

### 第二步　素材台账

把用户给的全部材料拆成一条一条，整理成 `素材台账.md`。格式和判定规则见 `references/ledger.md`。

| 序号 | 类别 | 内容 | 来源 | 状态 |
|---|---|---|---|---|
| 1 | 数据 | 全年康复治疗46120人次 | 《康复医学科2026年工作记录》第 2 段 | 已确认 |

1. 类别只用五种：工作事项、数据、案例、问题、下步打算。一条只记一件事或一个数，数字与单位连写；来源写到文件名和段落，或写“用户消息”“单位画像”。
2. 状态只有“已确认”“待核实”两种。原话带“大概”“约”“多”的，没有口径或时间范围的，几份材料说法不一的，记“待核实”。算出的增幅、占比另起一行，写明算式。台账同样脱敏。
3. 用户一条素材都没给的（情形②），交付提纲和素材收集清单（`references/frameworks.md` 第三部分）。用户坚持要稿的，出框架稿，所有事实位置标【待补】。

### 第三步　提纲与标题备选

1. 已有 gongwen-title 搭出的 `提纲.md`、`标题方案.md`，或用户给了提纲的，以它为准，只补台账序号和字数分配；标题用用户选定的那套，没选的用标“推荐”的一套，写进起草说明“假设”。
2. 提纲写到二级标题。每个要点后注明依据的台账序号和计划字数，例如“（二）开展床旁早期康复（台账 5、6、11，约 400 字）”。
3. 标题给 1～2 套（高效模式给 3 套）：一套平实式；一套主副标题式，主标题只概括台账里有的成效。默认套按材料类型定：经验材料、调研报告默认主副标题式，总结、计划、工作要点、汇报材料、述职默认平实式。提纲中在默认那套后标“（推荐）”，正文用这一套；用户另选的按用户。要对仗式、数字概括式小标题，或多套风格比较的，可建议用户继续让我拟标题。
4. 小标题写成“动作加对象”，管得住下面的内容。
   - 例：（一）开设床旁早期康复，缩短患者卧床时间
5. 提纲与正文首轮一次交付（开工检查第 5 条），不等用户确认。

### 第四步　分段成稿

按提纲逐部分写，每写完一部分对照台账核一次。

1. 开门见山。首段一到三句，写时期、总体情况，引出下文。不写“在……的正确领导下”一类铺垫（画像或领导偏好卡要求保留的，压缩成一句）；计划、实施方案、调研报告可按惯例写不超过一段的简短形势或背景，不空泛。
   - 例：2026年，康复医学科完成康复治疗46120人次，开展床旁早期康复400多例。现将全年工作总结如下。
2. 成效按“做了什么、数据或事例、结果”写。台账没有数据的只写做了什么，不改写成“明显提升”“大幅增长”，确需数据的才写【待补：说明】。材料是统计表的，除逐项列数外，写出汇总数、平均值等派生数，分母口径写清，算式记入台账，正文只写结果。
3. 做完不等于见效：系统上线、制度出台只能写已完成，写成效要有台账里的运行数据或反馈。
4. 四类内容只能来自台账：成效数字、排名名次、获奖荣誉、群众评价（满意度、感谢信、锦旗、“广受好评”）。台账没有的不写；结构上确需这一项的，标【待补】。
5. 存在问题写具体（哪项工作、差在哪里、什么影响），只用台账“问题”类条目。只有一句笼统话的（如“更新慢”），照写，不自行补充，起草说明待补一行请用户补充具体表现；台账没有问题的，写【待补：存在的问题】，起草说明待补一行附 3 个启发提问。
   - 例（台账第 14 条）：治疗师只有9人，周末床旁康复排不开班。
6. 下一步只写台账“下步打算”有的，并与问题对应。台账没有的：总结只写一句原则性表述，不列具体事项；经验材料、信息等不设此部分。部署性文书的措施按文种常规写，不夹带新数字、项目名；责任部门只用台账已有的，时限等必须由用户定的才标【待补】。
7. 状态不升级：计划中的写“将”“拟”，不写成“已”；建议不写成决定；用户说“还在论证”的照原样保留。
   - 材料写明“还没定”“暂无打算”的做法、责任、程序，只写原话，不自拟提出、研究、审定、协商流程和责任分工，也不增设“明确未定事项”一类条目；确需建议的，写进起草说明的备选，不进正文。
8. 篇幅按 `references/_shared/guardrails.md` 第四条第 2 款：字数按提纲分配，以目标 ±10% 为准，超了先删铺垫和重复表态。素材不足的，用工作性表述补足常规板块（回顾性文书不补下一步计划），不新增事实，不注水；起草说明一句话说明哪几部分是常规表述；“不超过”“以内”只设上限，不扩写；【待补】不计入字数。
9. 主语按单位类型：我局、我院、我校、公司、我镇、社区居委会（`references/units.md`）。
10. 用户提供了上级文件的，逐条转化为本单位的具体措施，不照抄原文；本单位措施缺失的，按上级要求和文种常规写出可执行措施，责任主体只用材料已有的单位、部门（`references/_shared/rules/jianfu.md` JF-04）。
11. 避开 AI 腔和防御腔（`references/_shared/style/ai-tone.md`、`references/_shared/style/defensive.md`）；“一是……二是……”、四字格、排比式小标题照常使用。
12. 引号内的做法名称、本单位提法原样使用；“周五”“下周一”等相对日期和成文日期的写法，按 `references/_shared/guardrails.md` 第二条第 7、8 款。

### 第五步　自检

1. 台账对账（必做）：按 `references/ledger.md` 第七部分，把正文中每个统计数、金额、百分比、次数、人数、名次逐个在台账里找；有 Python 环境时先运行 `python scripts/fact_diff.py 素材台账.md 正文.txt --ledger` 辅助查找。
2. 机检：有 Python 环境时运行 `python scripts/gongwen_lint.py 正文.txt --doc-type 总结`。`--doc-type` 按实际填：总结、计划、工作要点、汇报材料、调研报告、经验材料、述职报告、实施方案（大会工作报告填总结）。P0 必改，P1 逐条判断，P2 酌情处理；公文白名单写法（`references/_shared/style/ai-tone.md` 第二部分）和【待补】标记照常保留。ELM 要素缺失的，能确定的补写，不能确定的标【待补】；EVD 强评价缺数据的，补用户材料中的数据或改用不带强评价的写法，不得编造数据。
3. 没有 Python、脚本报错或输出“未执行检查”的，按 `references/checklist.md` 逐项人工检查，在起草说明写“未运行机检，已按人工清单检查”。
4. 篇幅、层次、开头结语可对照 `references/_shared/style/baseline.md` 中该文种的典型参数（参照，不是硬规则；用户指定篇幅时以用户为准）；机检加 `--baseline` 会对偏离基线的篇幅、一级标题数、“一是”组数、顿号密度给 P2 提示。
5. 最后过一遍本文“自检清单”。

### 第六步　交付

按 `references/_shared/style/output-format.md` 交付。
1. 能写文件的，在当前工作目录建 `公文/<YYYYMMDD>-<简短标题>/`，写入 `正文.txt`（只含正文）、`素材台账.md`、`提纲.md`。对话中放文件位置、一段话概述、【起草说明】、至多 3 问；台账、提纲、标题备选和逐条判断留在文件里，不复述到对话。
2. 网页对话环境：依次输出正文、`【起草说明】`，素材台账放在起草说明之后，标题为“附：素材台账”。回复开头直接交付正文，不加引导语；停在提纲的，开头一句话说明属于哪种情形。路线还有下一站的，在起草说明之后输出更新后的交接卡（`references/_shared/style/output-format.md` 第四部分）。
3. 起草说明只在对话中给出，不超过 5 行、每行一句，不写内部术语、规则号、工具名、模式名：假设、待补、待核实各汇总一行并注明正文位置，修改说明、保密提示各一行，不写过程说明；教学模式的写作要点另列“附：写作要点”。附表标题依次为“附：口径冲突表”“附：提法核对清单”“附：填写指引”“附：素材台账”，按需选用，不计入 5 行。

## 模式二　下级材料汇总

多份科室或下级单位材料合成一份时，按 `references/merge-and-versions.md` 第一部分登记材料、拆条、合并去重、统一口径。要点：
1. 同一件事台账只记一条，来源列全；次数、人数不重复相加；牵头单位写成主体，其他单位写“配合”。
2. 统计口径、时间范围、计量单位比不齐的，不加总、不取平均、不挑大的，正文并列写明各家数据（或采用最可靠的一家），列进起草说明之后的“附：口径冲突表”。
3. 按工作板块用单位整体的口气（“我镇”）成稿，不按科室逐个拼接；应报未报的单位列入起草说明“待补”一行。

## 模式三　一份台账多版输出

同一份素材台账，分别出单位总结（主语我局、我院等，按工作板块）、个人述职（主语本人，按德、能、勤、绩、廉）、汇报提纲（按上级关切排序，每条一句话带关键数据）。台账只建一份，同一数据在各版本中的数值和口径一致。细则见 `references/merge-and-versions.md` 第二部分。
1. 单位总结转述职：把“我局完成……”改成“本人牵头（分管、具体承办）……”。本人角色只取用户原话，建台账时在内容栏开头标“（本人：牵头）”之类的标记；台账没写本人做了什么的，写【待补：本人在此项工作中的职责和做法】。
   - 例（台账只写了本局全年办结47件）：本人负责人大代表建议办理的督办，本局全年办结47件。（台账写明本人负责督办）
2. 述职“绩”占一半以上篇幅。德、勤、廉只写用户提供的事实；没有的给填写指引，不替用户写“严守纪律、无违规违纪”之类的表态。
3. 出完后按 merge-and-versions.md 第二部分（六）交叉核对。
4. 正文按版本分文件（如 `正文-个人述职.txt`），共用一份 `素材台账.md`；起草说明一份，各行注明出自哪个版本。

## 只出框架的两种情形

依据 `references/_shared/guardrails.md` 第六条第 4、5 款，属于开工检查第 5 条情形①。先用一句话向用户说明原因，再交付框架，不拒绝整个任务。

1. 述职报告（含述职述责述廉）缺本人事例。本人事例指本人亲自做的具体事情，至少有事项、本人角色和结果。用户只给了单位或部门材料，或什么都没给的，只出提纲和填写指引（`references/frameworks.md` 第一部分），不生成完整正文。部分方面有事例的，有事例的部分成稿，缺的部分在正文写【待补：本人……的具体事例】，对应的填写指引放进“附：填写指引”。
2. 调研报告缺调研记录。调研记录指访谈或座谈记录、问卷结果、实地察看记录、调研数据表。没有记录的，只出调研提纲和调研报告框架（`references/frameworks.md` 第二部分），不写任何调研发现和结论。用户说“领导要先看稿”的，照样只交框架，说明调研后发来记录即可成稿。用户提供 Excel/xlsx 等电子表格作为调研数据表的，先确认能读出其中的数值（列出表头和至少一行数据）；读不出的，在回复开头说明"未读到附件数据表内容，请把数据粘贴为文本后继续"，不进入成稿，不凭想象补数据。

## 输出规范

- 正文、起草说明、交付位置按 `references/_shared/style/output-format.md`：纯文本，层次序数依次为 一、（一）1.（1），只允许【待补：说明】一种提示，不写【待核实】；数字用法按 `references/_shared/rules/gbt15835.md`。
- 素材台账、提纲、口径冲突表是工作底稿，可以用 Markdown 表格。
- 引用内置资料：写“依据”只引 `references/_shared/rules/jianfu.md` 条款表里有的条号和要点，不扩写条款内容；表外的做法是调研组自己的安排，不写条号，需要时在起草说明请用户对照原文。上级文件名称、文号用户没给的不写；引单位画像里的文号，起草说明注明“来自工具内置资料，请核对原文”。

- [ ] 首轮交付了正文；停在提纲的，属于开工检查第 5 条的四种情形之一，并在回复开头说明。
- [ ] 正文每个统计数、金额、百分比、次数、名次都能在台账找到；没有自行写入成效数字、排名、获奖、群众评价；没有把计划写成已完成、建议写成决定；没有为未定事项自拟提出、研究、审定、协商流程。

- [ ] 篇幅在目标 ±10% 以内；低于目标下限的，已用工作性表述补足常规板块并在起草说明说明哪几部分是常规表述，没有新增事实和注水；部署性文件未超过 `references/_shared/rules/jianfu.md` 的上限。

## 角色适配

- 教学模式：同样首轮交付正文；“附：写作要点”写清结构为什么这样搭、问题怎么写才具体（用本稿的一处正误对照）、每项【待补】一般到哪里找。
- 高效模式：台账、提纲、正文一次交付；标题给 3 套；可同时给全文和压缩版两个篇幅；多份下级材料可批量汇总。少解释，但篇幅上限、数字写法、文种等判断，每条仍写一行问题类型和依据条款。
- 转译模式：接受流水账、数据表、口语描述；提问按第一步缺项处理第 5 条；台账来源写到原表的行或列，计算写出算式；业务术语照用，不替用户拔高定性。
- 审稿模式：被要求起草的，按开工检查第 5 条首轮成稿；领导明确要先看框架的（情形③），交一页纸（提纲、核心数据、主要问题、待补清单）供拍板；用户拿来的是成稿、要挑问题的，转 gongwen-review。
- 严谨模式：用于述职述责述廉、党代会工作报告、党建板块和对外报送的材料。政治性提法只用用户提供的原文，没有原文的用通用、稳定的表述，起草说明“待核实”一行请对照最新原文，照常首轮出稿；增加提法核对清单；用户给了往年稿的，标出雷同段落。
