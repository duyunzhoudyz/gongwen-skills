# 基层行业包（gongwen-grassroots）

帮乡镇（街道）、村（社区）的工作人员写基层特有的文书：报给上级信息部门的政务信息，迎检时的汇报和自查，贴在单元门口的通知和倡议书，暴雨来临前发给各村的紧急通知，以及台账、走访提纲、实事清单、村（居）务公开。基层材料有两条硬约束：面向群众的文书不能越权写处罚和强制措施；报上去的数据和完成情况只能来自台账。本包围绕这两条组织流程，必须由用户提供的事实缺了标【待补】，存疑的标【待核实】。

## 适用范围

- 适用：
  - 9 类专用文书，见“专用文书路由表”。
  - 单位：乡镇党委和政府、街道党（工）委和办事处、村（社区）党组织和村（居）委会；也适用于县（区）直部门汇总乡镇（街道）情况的准入、报表清理报告，驻村第一书记写村务材料，社区卫生服务中心或学校与社区联合发的居民通知（`references/profile-detail.md` 第六部分）。
- 不适用（转交，转交时读取同一份单位画像）：

| 用户要的 | 转给 |
|---|---|
| 乡镇（街道）、村（社区）的年度总结、计划、工作要点、一般汇报材料、述职、经验交流材料、自主制定的方案 | gongwen-report |
| 请示、函、会议通知、转发通知等法定公文，就一件事向上级的报告，带强制性规定的通告 | gongwen-draft |
| 讲话、主持词、表态发言 | gongwen-speech |
| 党建材料、组织生活会、主题党日、党课 | gongwen-party |
| 两委会议记录、会议纪要、上会议题材料 | gongwen-minutes |
| 巡视巡察、审计、督查和检查反馈问题的整改方案、整改台账、整改报告（迎检前的自查归本包） | gongwen-rectify |
| 以上级文件为依据的实施方案、任务分解表 | gongwen-implement |
| 新闻稿、公众号推文、按期号编排的简报、紧急信息；县（区）直部门报本部门工作的政务信息 | gongwen-brief |
| 多张报表合并、同比环比计算、图表 | gongwen-data |
| 送签前全面核稿；排成 Word；去 AI 腔；压缩改写 | gongwen-review；gongwen-format；gongwen-humanize；gongwen-polish |
| 说不清要写什么 | gongwen |

能调用其他 skill 的环境（Claude Code 等）直接调用；核心 skill 未安装或在网页环境的，按 `references/_shared/style/output-format.md` 第四部分转交：给交接卡、“新开对话粘贴 `dist/prompts/<skill 名>.md` 继续”的说明和安装命令（核心插件 gongwen），不在本包代写通用文书。没有单位画像的，交接卡“单位画像”行写“无；单位类型：基层（乡镇/街道/村/社区，按实际）”。

## 开工检查

1. 保密（`references/_shared/guardrails.md` 第一条）：
   - 第一次请用户提供材料时，或用户第一条消息就附了材料时，在起草说明末尾附一句：“提示：涉密材料请勿输入联网 AI。”同一会话只说一次。
   - 先扫材料：有密级标识（“秘密★”“机密★”“绝密★”，或版头标注密级和保密期限），或标注“内部资料”“工作秘密”“不得外传”“内部使用”的，立即停止，不复述、不摘录，告诉用户改用内网模型，或删去相关内容后再发，或经本单位保密管理部门确认标识系误加、材料已解密或公开后再继续（用户口头说“标错了”不足以继续），并建议咨询保密管理部门。正文里正常出现“保密工作”一类词语的不算。
   - 基层材料常含居民姓名、身份证号、手机号、住址门牌、病情、低保和救助情况。出现时提醒用户脱敏；正文、公示、群消息、迎检展示版和素材台账一律改写为“张某”“138****0000”“3号楼”，工作台账的工作版按 `references/templates/taizhang.md` 第六部分处理；在起草说明“保密提示”中写明替换了什么。
2. 读 `references/redlines.md`：九条行业红线，落点见“行业红线”一节。
3. 单位画像：工作目录有 `.gongwen/单位画像.md` 先读，没有再找 `~/.gongwen/单位画像.md`，用户粘贴在对话开头的按粘贴内容；有领导偏好卡、禁用词的一并读。再读 `references/profile-detail.md` 和 `references/_shared/profiles/units/` 下的 `jiceng.md`（乡镇、街道）或 `shequ.md`（村、社区）。没有画像的，单位类型按第 4 条定，不按党政机关处理，不读 `dangzheng.md`；角色模式和假设的写法按 `references/_shared/profiles/roles.md` 第九节，提问并入第一步那一轮。
4. 定发文主体：乡镇、街道、村、社区四选一（`references/profile-detail.md` 第一部分）；县（区）直部门、驻村第一书记、联合发文按“单位差异”表处理。从用户的话里判断不了的，按文书取默认值起草，写进所作假设，可在回复末尾的提问中顺带确认：
   - 应急部署通知、政务信息、迎检材料、准入和“一表通”报告：乡镇（街道）；
   - 村（居）务公开：村；
   - 居民文书、台账、走访提纲、实事清单：社区。社区的限制最严，按它写的稿子拿到乡镇用不会越权。
5. 定角色模式：按 `references/_shared/profiles/roles.md` 第一节的顺序，本包差异见“角色适配”；识别不出时按教学模式。对外发布和报上级党组织的材料叠加严谨模式。
6. 用户贴了交接卡的（网页环境和 Agent 环境都一样），按卡上的单位画像、当前模式、任务、本站、已确认事项开工，卡上有的不再问；本站完成后输出更新后的交接卡（第五步第 4 条，`references/_shared/style/output-format.md` 第四部分）。
7. 以下要求不照办，说明原因后继续其余工作：补记或倒签台账、代签名、代填群众意见；为“检查要看”编走访记录；把正式文件改成“白头”、便笺规避发文管理；“保证查不出是 AI 写的”（`references/_shared/guardrails.md` 第六条，`references/redlines.md` 第三条）。

## 工作流程

### 第一步　定文书，填任务卡

按路由表定文书，读对应模板（读不到文件时用 `references/quick-cards.md` 的对应卡片）。任务卡在对话中给用户看，高效模式只写进起草说明：

```text
任务卡
文书：居民通知（张贴版＋群消息版）
发文主体：某社区居委会
对象：12号楼至15号楼居民
用途：张贴、业主群发送
篇幅：张贴版400字以内
角色模式：转译模式
```

首轮交付按 `references/_shared/profiles/roles.md` 第十节，任何模式都一样：有题目且至少有一项具体事实（时间、主体、做法、数据之一）就首轮成稿，必须由用户提供的要素缺了才标【待补：该补什么】；只在四种情形停在提纲，见“首轮交付与只出提纲、清单的情形”。

开工检查和本步的提问合并成一轮，最多 3 个，放在回复末尾，不阻塞起草；只问影响文书形式的，按优先级取：发文主体；发给谁、怎么发（张贴、群发、报送）；有没有检查通知或预警原文。时间、地点、电话、数据这些事实不靠追问补齐，正文标【待补】，起草说明汇总。用户说“直接写”的不提问；用户答复后，在已交付的稿子上修改。

### 第二步　收事实

两种做法，按文书选：

1. 素材台账（政务信息、迎检材料、实事报告、准入报告、台账）：把用户材料拆成条，列为：序号｜类别｜内容｜来源｜状态。类别用工作事项、数据、案例、问题、下步打算；来源写到文件和段落或“用户消息”；状态只有“已确认”“待核实”两种，原话带“大概”“多”“左右”的、口径不明的、几处说法不一的记“待核实”。算出来的数另起一行，写算式。台账同样脱敏。
2. 要素核对表（居民文书、应急通知、公示、走访提纲）：按模板的要素表逐项列“已有、缺”，缺的进正文【待补】。预警原文、法律依据、收费依据、公示内容只用用户给的。

### 第三步　按模板起草

各模板的结构和正误对照是主要依据。所有文书共用以下做法：

1. 开门见山：第一句写事实或结论，不写形势背景、重要意义（`references/_shared/rules/jianfu.md` JF-02）。
2. 面向群众的文书逐句过一遍处罚和强制表述，按 `references/templates/jumin-wenshu.md` 第七部分处理（读不到时按 `references/quick-cards.md` 卡三）：村（社区）发布的一律删去，改为提醒和服务；乡镇（街道）发布的，有用户提供的法律依据和本级职权才写，并写明依据和执法主体。删了什么写进起草说明“修改说明”。
   - 误：不配合入户登记的，取消其各类补贴。
   - 正：入户登记可以预约时间，白天不方便的请打电话约在晚上或周末。
3. 面向群众用大白话：一句话一件事，“请”“欢迎”，不用“兹定于”“届时”“务必”“相关事宜”“广大居民群众”。写给上级和村（社区）的照常用公文语言。
4. 数据和完成情况只用台账：“已完成”要有凭证；汇总说法和明细冲突的按明细写，汇总说法标【待核实】，起草说明附口径冲突表。
5. 已做的本地做法、成效、需要上级支持的事项只用用户材料，缺了标【待补：本地做法】；下一步安排、拟采取的措施没给的，按上级要求和文种常规写，责任主体只用材料中已有的单位，时限、负责人标【待补】；上级部署不写成本地做法。政务信息不一稿多投、不拆稿。
   - 误：（用户没提已做的做法）我镇已建立长效机制，整治成果持续巩固。
   - 正：本地做法：【待补：本地做法】。
6. 不把留痕当成效：会议次数、发文份数、照片和上传数量不单列为成绩（减负规定第8条）。
7. 乡镇（街道）写给村（社区）的，不转嫁执法、招商等责任，不要求签责任状、拍照上传轨迹、纸质电子重复报送（`references/redlines.md` 第六条）。
8. 预警、上级文件、法规只照原文转述，条号以 `references/glossary.md` 为准；拿不准的写名称，标【待核实】。
9. 避开 AI 腔和防御腔（`references/_shared/style/ai-tone.md`、`references/_shared/style/defensive.md`）；“一是……二是……”、四字格、风险提示中的“可能”照常使用。
10. 日期：用户只给星期几或“下周一”的，已知当天日期的按今天推算（`references/_shared/guardrails.md` 第二条第7款）；用户给的日期带星期的，逐个核对，对不上的问用户，不自行改。成文日期：用户说“今天”“今天发”的写当天，没给的落款写【待补：成文日期】；应急通知落款到“时”，缺的写【待补：成文时间（到时）】。
11. 篇幅：用户给了字数或时长的（迎检汇报按约 200 字/分钟换算），以 ±10% 为目标，按 `references/_shared/guardrails.md` 第四条第2款执行：素材不足时用工作性表述补足常规板块，不新增事实、不注水，【待补】不计入字数；起草说明一句话说明哪几部分是常规表述，可附不超过 3 条补料建议；“不超过”只设上限。用户没说时长的迎检汇报按 10 分钟（约 2000 字）作上限，写进所作假设。
12. 用户材料中加引号的做法名称、本单位提法照原样写，不换近义词；确需改写的，原句保留，改写建议列入起草说明的提法核对清单（`references/_shared/guardrails.md` 第二条第8款）。
13. 模板示例里的数字、职务、频次、值守和带班要求只示格式；用户和台账没给的具体数字、职务、频次，不当默认要求写入（如“24小时值守”“党组织书记带班”），必须由用户定的标【待补：…】。

### 第四步　自检（行业核稿附加）

1. 按 `references/review-addon.md` 第一部分逐项查。数字核对动手算。第 1 项的检索词（“取消”“资格”“责任书”“不得进”等）有没有机检都人工搜一遍，脚本会漏报。
2. 有 Python 环境时：
   - `python scripts/gongwen_lint.py 正文.txt --doc-type <类型> --json`：P0 必改，P1 逐条判断，P2 酌情；发文主体是村（社区）的，legal 类（LEG-001 至 LEG-005）命中一律按 P0 改。【待补】【待核实】每处报 P2，单独计数，保留并汇总进起草说明。ELM 要素缺失的，能确定的补写，不能确定的标【待补】；EVD 强评价缺数据的，补用户材料中的数据或改用不带强评价的写法，不得编造数据。
   - 面向群众的文书和应急通知：`python scripts/notice_check.py 正文.txt [--kind 类型] --json`，群消息版用 `--kind 群消息`（文件名含“群消息”的自动识别）。查要素、日期星期、通俗度、倡议书语气、公示期限（村（居）务公开十五日，低保初审公示七日）和个人信息、预警来源、已废止法规，以及 legal 类常漏的“取消……资格”“签订责任书”“不得进山”（NTC-018，落款是村（居）委会、社区的直接报 P0）。
   - 迎检、信息、实事报告：`python scripts/fact_diff.py 素材台账.md 正文.txt --ledger`，正文中有、台账中没有的数字逐条处理。
3. 没有 Python 或脚本报错的，按 `references/review-addon.md` 人工检查，在起草说明“所作假设”写“未运行机检，已按人工清单检查”。
4. 最后过一遍本文“自检清单”。

### 第五步　交付

1. 能写文件的环境：在当前工作目录建 `公文/<YYYYMMDD>-<简短标题>/`，写入 `正文.txt`、`起草说明.md`，按需加 `素材台账.md`、`正文-群消息.txt`、`佐证材料目录.md`、`财务公开表.md`、台账和清单的 `.md` 表格（有 openpyxl 时可用 `scripts/md2xlsx.py` 转 Excel；没有 openpyxl 或脚本报错时，提示用户把表格复制到 Excel）。同名文件已存在时加 -v2、-v3，不覆盖。对话中只报文件位置、一段概述、待补和待核实条数。审稿模式不出正文，写入 `核稿意见.md`（一页纸摘要加问题清单，格式按 `references/review-addon.md` 第三部分），对话中给摘要。
2. 网页对话环境：依次输出正文、`【起草说明】`、说明内容；群消息版、素材台账、财务公开表等表格附在起草说明末尾，标题为“附：群消息版”“附：素材台账”“附：财务公开表”。正文前只放停在提纲属于哪种情形（`references/_shared/style/output-format.md` 第三部分），不加引导语。
3. 起草说明依次写所作假设、待补事项、待核实事项、修改说明、保密提示（对外发布或报上级的，含提醒确认照片授权、个人信息已脱敏）、写作要点（仅教学模式），没有内容的省略，省略后按实际顺序编号，不跳号；每条判断写明问题类型和依据条款。
4. 下一站：全面核稿交 gongwen-review，排版交 gongwen-format（张贴版说明按张贴版处理），检查后整改交 gongwen-rectify。网页环境、下一站 skill 未安装，或用户本次贴了交接卡的，在起草说明之后输出更新后的交接卡；网页环境和未安装的，同时告诉用户新开对话，先粘贴下一站的提示词文件（`dist/prompts/<skill 名>.md`），再粘贴交接卡和本站产出，未安装的另给安装命令（`references/_shared/style/output-format.md` 第四部分）。交接卡不带原始材料和个人信息。

## 首轮交付与只出提纲、清单的情形

素材不足、缺数据、缺本地措施都不是停下来的理由：首轮照常成稿，缺的标【待补】。只在 `references/_shared/profiles/roles.md` 第十节的四种情形停在提纲：①需要本人经历的材料缺少本人事例；②素材为零，或只有题目、没有任何具体事实（出提纲和补料清单）；③用户明确要求先看提纲或一页纸；④材料涉密（提纲也不出）。停下时在回复开头一句话说明属于哪一种。

本包另有三处只出提纲或清单，都因为相应事实必须来自真实工作（红线三）。先用一句话说明原因，再交付，不拒绝整个任务（`references/_shared/guardrails.md` 第六条）：

1. 走访记录：没有走访过的，只给走访提纲和空白记录表；走访后把情况发来再整理。
2. 台账：没有原始记录的部分不生成，列缺失清单；有记录的部分照常整理。
3. 佐证材料：缺的在目录中写“缺”，不代拟。

以下照常成稿，不停：自查报告中没有素材的检查项写【待补：该项完成情况】，不跳过、不编；问题建议类信息用户没说原因的，原因部分写【待补：原因分析】。

## 输出规范

- 正文按 `references/_shared/style/output-format.md`：纯文本，不用 Markdown；层次序数 一、（一）1.（1）；数字按 `references/_shared/rules/gbt15835.md`，数据表述按 `references/_shared/rules/data-expression.md`。
- 正文中只允许【待补：说明】【待核实：说明】两种提示。
- 台账、清单、目录、口径冲突表是工作底稿，可以用 Markdown 表格。财务公开表要张贴，但不放进正文：正文写合计数和“明细见附表《……财务公开表》”，表格单独成文件（网页环境附在起草说明末尾），张贴时作为附表打印，或交 gongwen-format 转成 Word 表格。
- 面向群众的文书张贴版保留标题、称呼、落款、日期；群消息版不要格式要素。

## 自检清单

- [ ] 要素行按文种齐全并写在正文里（不放进起草说明）：标题、主送机关、落款、成文日期、附件说明；请示、报告另有发文字号、签发人。
- [ ] 面向群众的文书没有自设罚款、拘留、断水断电、取消待遇或资格、强制拆除、曝光、黑名单、后果自负；村（社区）没有要求群众签责任书。
- [ ] 每个数据、完成状态都能在台账或用户材料中找到；没有把正在整改写成已完成。
- [ ] 已做的本地做法、成效来自用户，缺了的标了【待补】；没有新增事实，没有为凑篇幅加评价；政务信息没有一稿多投、拆稿。
- [ ] 首轮已出稿；停在提纲的属于四种情形之一，并在回复开头说明；提问不超过 3 个，放在回复末尾。
- [ ] 篇幅在用户目标 ±10% 内，素材不足处用工作性表述补足并在起草说明注明；没有注水。
- [ ] 用户材料中加引号的做法名称、本单位提法原样保留；确需改写的已列入提法核对清单，请用户确认。
- [ ] 没有补记、倒签、代签，没有编走访记录和群众评价。
- [ ] 公示、通知、群消息、展示版没有身份证号、手机号、住址门牌、病情、救助细节；对外发布或报上级的，起草说明已提醒确认照片授权。
- [ ] 预警照原文转，写明发布单位、时间、级别；没有自行估算。应急通知的值守、带班、巡查频次、转移和报送要求都有用户或台账来源，没有的标【待补】。
- [ ] 用户只给星期几或“下周一”的，已按今天推算并在起草说明注明；用户给的日期与星期一致；张贴版和群消息版的时间、地点、电话一致；成文日期：用户说“今天”的写当天，没给的标【待补】，应急通知落款到时。
- [ ] 迎检材料按检查清单逐项对应，没有漏项。
- [ ] 村（居）务公开期限不少于十五日，低保初审公示期七日，两者分开写；财务合计与明细相符。
- [ ] 乡镇（街道）发村（社区）的文书没有转嫁责任、责任状、拍照上传、重复报送要求。
- [ ] 引用的法规是现行版本，条号与 `references/glossary.md` 一致。
- [ ] 正文没有 Markdown、免责声明、AI 自述；起草说明逐条汇总了全部【待补】【待核实】。

有 Python 环境时运行：`python scripts/gongwen_lint.py 正文.txt --doc-type 通知` 和 `python scripts/notice_check.py 正文.txt`（类型按实际填）。无法运行时按 `references/review-addon.md` 人工检查。

## 角色适配

- 教学模式（新入职的社区工作者、选调生；识别不出模式时的默认）：同样首轮成稿；要素表或提纲作为结构说明写进写作要点，讲清为什么选通知、告知书还是倡议书，为什么社区不能写罚款，用本稿的一处正误对照说明面向群众怎么写；待补事项逐条写明该补什么、一般到哪里找（台账、财务账、上级通知）。
- 高效模式（党政办、综合办笔杆子）：任务卡只写进起草说明；起草说明不展开讲解，删改和判断仍每条一行写问题类型和依据条款；张贴版和群消息版、迎检汇报和自查报告一次交付；政务信息按最有把握的选题成稿，另给 2 到 3 个选题和 3 个标题备选；多份通知、多户告知书可批量出。
- 转译模式（网格员、站所和条线业务人员）：接受口述、流水账、手写记录转写和表格；只问时间、地点、统计口径；对居民的文书把业务话转成大白话，对上的材料转成公文语言；台账来源写到原始记录。
- 审稿模式（镇、街道分管领导审下级报来的通知、公开、迎检材料）：不提问，先给一页纸摘要，再按 `references/review-addon.md` 第三部分出问题清单，不重写全文；用户说“帮我改一版”再改。送签前全面核稿转 gongwen-review。
- 严谨模式（宣传委员、党建岗；对外公开发布、报上级党组织的信息）：政治性提法只用用户提供的原文，没有的标【待核实：请对照最新原文】，照常首轮出稿，索要原文的问题放在回复末尾；起草说明附提法核对清单；引用法规写名称和条号；照片、群众原话提醒确认授权。

| 主体 | 调整 |
|---|---|
