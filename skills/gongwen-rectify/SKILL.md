# 整改材料（gongwen-rectify）

巡视巡察、审计、督查、考核反馈问题后，整改材料一般要写三样：整改方案、整改台账、整改报告。本 skill 先把反馈意见拆成编号的问题清单，再建台账（问题、任务、责任三清单合一），方案和报告都从台账取材。报告里每条问题的状态、完成数和完成率必须与台账一致，"未完成写成已完成"属于虚假整改，会被问责。

## 适用范围

- 适用：
  - 整改方案：针对反馈问题制定的方案，附整改任务清单（高校审核评估、中小学督导评估等反馈问题的整改也在此列，编号沿用反馈的问题清单）；
  - 整改台账：问题、任务、责任三清单，可转 Excel；
  - 整改进展报告（月报、阶段报告）和整改情况报告；
  - 自查报告：上级发了检查清单（自查表、评分细则），逐项自查；
  - 对账：核对已有的整改报告与台账是否一致。
- 不适用（转交）：

| 用户要的 | 转给 |
|---|---|
| 没有检查清单的一般工作总结、专项工作总结、迎检汇报材料 | gongwen-report |
| 以上级文件为依据的实施方案、贯彻落实方案和任务分解表 | gongwen-implement |
| 整改专题民主生活会对照检查材料、个人检视剖析材料 | gongwen-party |
| 民主生活会、组织生活会查摆问题的整改措施和整改清单 | gongwen-party |
| 印发整改方案的通知、报送整改报告的请示或函 | gongwen-draft |
| 会议纪要、会议督办清单 | gongwen-minutes |
| 报表体检、多表合并、指标计算 | gongwen-data |
| 成稿全面核稿 / 排成 Word | gongwen-review / gongwen-format |
| 等级评审自评、院感与安全检查整改、九项准则（行风）自查（医院），审核评估自评报告（高校），督导评估自评报告（中小学），乡镇街道迎检汇报和迎检自查 | 已安装的对应行业包；没装的按本表其他行或本 skill 通用流程处理 |
| 说不清要写什么 | gongwen |

## 开工检查

1. 保密（`references/_shared/guardrails.md` 第一条）：
   - 第一次请用户提供材料时，或用户第一条消息就附了材料时，在本次回复开头附一句："请勿输入涉密信息和内部敏感信息；材料涉密的，请使用单位内网部署的模型。"同一会话只说一次。
   - 巡视巡察反馈意见、审计报告常带密级或"内部资料""注意保密""不得外传"等标识。读材料前先看版头和页眉：有这类标识的，立即停止，不建台账、不复述、不摘录，告诉用户涉密和内部材料不得输入联网 AI 工具；用户说明正在用单位内网部署、允许处理此类材料的模型，或已删去相关内容，或标识系误加、材料已公开的，再继续。正文只是提到"保密工作""涉密人员管理"的不算。
   - 问题线索、信访件、被处理人员、举报人、患者、学生的个人信息不进台账和正文：被反映人、被处理人写"张某"，举报人信息一律不写；身份证号、手机号、病案号、学号删去或写成"138****0000"；在起草说明"保密提示"中写明已替换。
2. 单位画像：读 `.gongwen/单位画像.md`，没有再找 `~/.gongwen/单位画像.md`，用户粘贴了画像的按粘贴内容；再读 `references/_shared/profiles/units/` 下对应文件和 `references/units.md`。没有画像的按 `references/_shared/profiles/roles.md` 第九节"无画像降级"。
3. 角色模式：按 roles.md 第一节确定。巡视巡察整改材料要报上级党组织，一律叠加严谨模式；要对外公开的整改情况也叠加严谨模式。
4. 交接卡：网页环境用户贴了【交接卡】的，按卡上的画像、模式、任务、本站和已确认事项开工，卡上有的不再问（`references/_shared/style/output-format.md` 第四部分）。
5. 不办的事：用户要求倒签日期、补记台账、把未完成写成已完成、编成效数字、把问题"写轻一点"、要"保证查不出是 AI 写的"的，说明原因（虚假整改会被追责，见 `references/sources.md` 第一部分；guardrails 第二、六条），不照办，其余工作照常进行。

## 材料速查

| 材料 | 结构 | 篇幅（工具约定） | 关键点 | 详细写法 |
|---|---|---|---|---|
| 整改方案 | 开头一段；整改目标、整改任务、工作安排、保障措施；附整改任务清单 | 正文不超过4000字，附件另计 | 问题照录，措施、责任、时限、成效标准逐条落实 | `references/plan.md` |
| 整改台账 | 编号、问题来源、问题表现、原因、措施、责任领导、责任部门、时限、成效标准、状态、进展、佐证 | 不限 | 唯一事实源；缺项写【待补】不留空 | `references/ledger.md` |
| 进展报告 | 统计句；本期进展；未完成问题；下一步 | 1000～2000字 | 先更新台账；超期如实写 | `references/writing.md` 第一部分 |
| 情况报告 | 统计句；开展情况；逐条整改情况；长效机制；未完成和下一步 | 问题10个以内约3000字 | 逐条状态与台账一致 | `references/writing.md` 第二部分 |
| 自查报告 | 自查基本情况；逐项自查；问题和原因；整改措施；附自查表 | 按清单项数 | 清单逐项对应，无记录不写"符合" | `references/writing.md` 第三部分 |

整改状态只用四种口径：已完成、立行立改、持续推进、长期坚持（临时可用"未启动"），认定标准见 `references/status.md`。

## 五条硬规则

1. 问题照录原文。台账"问题表现"和正文引用的问题，与反馈意见一字不差，限定词、数字、对象都保留；只把直引号等标点改成规范的全角写法。
   - 原文：部分科室高值耗材领用登记不全，账实不符，2025年盘亏金额12.6万元。
   - 误：耗材管理工作有待进一步规范。
   - 正：照录原文；要短名的另设"问题简称"。
2. 台账是唯一事实源。方案的任务、报告的状态、统计数和完成率，全部从台账取；报告与台账不一致时改报告，台账状态只凭用户提供的新进展和佐证更新。
3. 状态不升级。开会、发部署通知、印发方案只算启动（成效标准就是制度印发的，印发后有文号即可记已完成）；没有佐证不算完成；"基本完成"不是状态；长期坚持不计入完成数。
   - 误（台账为持续推进）：已召开专题会议研究部署，该问题已完成整改。
   - 正：已于10月12日召开专题会议部署，制度修订正在推进，预计11月30日前完成。
4. 成效和措施只来自用户。追回金额、处理人数、制度文号、整改措施，用户没给的标【待补：说明】，存疑的标【待核实：说明】；不写"取得明显成效""群众满意度大幅提升"。
5. 日期写实。进展日期写实际发生日，用户没给的标【待补：日期】；"11月中旬""年底"之类折算成具体日期的，写进起草说明"所作假设"请用户确认。

## 工作流程

### 第一步　定任务

先填任务卡，在对话中给用户看（高效模式只写进起草说明）：

```text
任务卡
材料：整改方案（附整改任务清单）
整改来源：区委第二巡察组反馈意见，9月26日反馈，12个问题
发文主体：中共某街道工作委员会
报送对象：【待补：主送机关】
期限：集中整改期至2027年3月26日（按反馈之日起6个月推算）
单位：基层（无画像，按用户所述）
角色模式：高效模式（叠加严谨模式）
```

缺项处理：一次最多问 3 个，顺序是：反馈意见原文 → 要写哪种材料、报给谁 → 措施和分工有没有初步打算。期限、画像、模式取默认值写进"所作假设"；缺的措施、时限、数据不靠追问补齐，进台账标【待补】。用户说"直接写"的不再提问。没有反馈原文、只有口头转述的，照转述写，每条加【待核实：请对照反馈原文】。

改已有稿：用户拿来已写好的方案或报告要修改的，不从头重写。

1. 先按反馈原文建台账：问题表现照录原文，措施、责任、时限、状态取自原稿，原稿没有的标【待补】。
2. 只改问题表述、状态说法和统计句；原稿的措施、责任领导、责任部门、时限、日期保持不变，确需改动的写进修改说明请用户确认。
3. 修改说明逐条列"问题N：原表述／改后表述／理由（如照录反馈原文、按台账口径）"。
4. 有 Python 时，改完运行 rectify_check（加 `--feedback`，方案加 `--plan`）和 `python scripts/fact_diff.py 原稿.txt 正文.txt`："原稿有而改稿没有"应为空，"改稿新增"只能是恢复的反馈原文中的数字和引号内容。

### 第二步　拆问题清单

1. 按反馈意见的顺序和分类逐条拆，一条一个问题，从 1 编号；反馈原文有编号的沿用。一条里含几个问题的拆成子项 4-1、4-2。
2. 问题表现照录原文（硬规则 1）。
3. 核对条数：拆出的条数与反馈意见列明的问题数一致；不一致的在起草说明写明怎样拆的。
4. 问题线索、信访件只记件数，不记人名和案情（开工检查第 1 条）。

### 第三步　建台账

按 `references/ledger.md` 建 `整改台账.md`，三清单合在一张表里，列名照用（"编号""整改状态"两列供脚本对账）。

1. 原因、措施、责任领导（写职务）、责任部门、时限、成效标准只用用户给的；缺的写【待补：说明】，不留空。
2. 用户没给措施的，起草说明附"措施提示"（`references/ledger.md` 第四部分第1条）；没给原因的，附"原因分析提示"（`references/plan.md` 第四部分），由用户选择后补入。
3. 时限写具体日期；巡视整改的时限不晚于集中整改期结束，期限依据见 `references/sources.md`。
4. 成效标准写成可检验的样子（制度印发、系统上线、资金退回、账实相符），数值目标没给的标【待补：目标值】。
5. 状态按 `references/status.md` 第二部分判定：没动手的记"未启动"，已动手未完成的记"持续推进"，检查期间或方案印发前已改完并有佐证的记"立行立改"（没有整改方案的，以检查期间为限）。
6. 写进展报告、情况报告前，先按用户给的新进展更新台账（ledger.md 第六部分），另存新版本，再动笔。台账是 xlsx 的，按 ledger.md 第六部分第6条先转成 md。

### 第四步　起草

按材料类型读对应文件：整改方案读 `references/plan.md`；进展报告、情况报告、自查报告读 `references/writing.md`。共同要求：

1. 开门见山：开头写何时收到哪个检查组的反馈、共几个问题，不写重要意义和"极端重要性"之类的表态。
2. 报告开头用统计句，数字从台账算：巡察反馈的12个问题，已完成整改8个（其中立行立改3个），持续推进3个，需长期坚持1个，整改完成率66.7%。
3. 逐条写到某个问题时用"问题3"指称，编号与台账一致；段末写状态句，用台账口径（writing.md 第四部分）。
4. 没有全部完成的，不写"全部完成整改""全面整改到位"；"将于……前完成整改"只能用于计划。
5. 措施用要求式措辞（"要""于……前完成"），不用"建议""可以考虑"；保障措施只写有主体、有动作的两三条。
6. 避开 AI 腔和防御腔（`references/_shared/style/ai-tone.md`、`references/_shared/style/defensive.md`）；"一是……二是……"、四字格照常使用。
7. 用户要对外公开的版本，按 writing.md 第六部分删减。

### 第五步　对账与自检

1. 对账：有 Python 环境时运行 `python scripts/rectify_check.py 整改台账.md 正文.txt --json`；正文是整改方案的加 `--plan`（不要求每条写状态）；有反馈原文的加 `--feedback 反馈意见.txt` 核对问题是否照录；要查超期的加 `--date 2026-10-31`。只给台账时只做台账自检。P0（报告写成已完成而台账未完成、完成数或完成率高于台账、未全部完成却写"全部完成"）必须改报告；P1 逐条处理；P2 人工判断。不靠改台账状态来消除差异。
2. 机检：运行 `python scripts/gongwen_lint.py 正文.txt --doc-type 整改方案`，进展报告和情况报告用 `整改报告`，自查报告用 `自查报告`（扩充类型，引擎暂时只提示不报错）。P0 必改，P1 逐条判断；【待补】【待核实】机检报 P2，保留并汇总进起草说明。
3. 不能运行脚本（网页版、无 Python、脚本报错）时，按 `references/checklist.md` 人工对账和检查，在起草说明写"未运行机检和对账脚本，已按人工清单检查"。
4. 最后过一遍本文"自检清单"。

### 第六步　交付

按 `references/_shared/style/output-format.md` 交付。

1. 能写文件的：在 `公文/<YYYYMMDD>-<简短标题>/` 下写 `正文.txt`、`起草说明.md`、`整改台账.md`；有 Python 时运行 `python scripts/md2xlsx.py 整改台账.md 整改台账.xlsx --title <台账表题>` 出 Excel。更新台账另存 `整改台账-v2.md`，同名文件已存在时加后缀，不覆盖。对话中只报文件位置、一段话概述、对账结果和待补、待核实条数。
2. 网页环境：依次输出正文、`【起草说明】`、说明内容；台账放在起草说明最后，标题为"附：整改台账"。只要台账的，正文就是台账，起草说明照常写。路线还有下一站的（如转 review 核稿、format 排版），在起草说明之后输出更新后的交接卡，告诉用户新开对话，先粘贴下一站的提示词文件，再粘贴交接卡和本站产出。
3. 起草说明依次写：所作假设、待补事项、待核实事项、修改说明（台账状态变化写在这里）、保密提示、写作要点（仅教学模式）；末尾按需附"附：对账结果""附：原因分析提示""附：措施提示""附：提法核对清单""附：整改台账"。

## 输出规范

- 正文按 `references/_shared/style/output-format.md`：纯文本，不用 Markdown；层次序数 一、（一）1.（1）；数字按 `references/_shared/rules/gbt15835.md`。
- 正文只允许【待补：说明】和【待核实：说明】两种提示。
- 台账、三清单、自查表、对账结果是工作底稿，可以用 Markdown 表格；交付 Excel 用 md2xlsx。

## 自检清单

- [ ] 读材料前看过密级和"内部资料"等标识；人名、举报人、证件号已处理。
- [ ] 台账每条"问题表现"与反馈原文一致，没有弱化、删数字。
- [ ] 措施、责任、时限、成效标准没有空栏，缺的写了【待补】；没有自编措施。
- [ ] 状态按口径认定；已完成、立行立改都有佐证；没有"基本完成"。
- [ ] 报告的统计句、每条状态句、完成率与台账一致；长期坚持没有算进完成数。
- [ ] 台账未全部完成时，正文没有"全部完成整改""全面整改到位"。
- [ ] 成效数字、金额、处理人数都能在台账找到；没有无依据的评价。
- [ ] 开头没有意义铺垫，保障措施没有空表态，部署措施没有"建议""可以考虑"。
- [ ] 正文没有 Markdown 符号、免责声明；起草说明汇总了全部【待补】【待核实】。
- [ ] 已运行 rectify_check 和 gongwen_lint，或已写明按人工清单检查。

有 Python 环境时运行第五步的 rectify_check 和 `python scripts/gongwen_lint.py 正文.txt --doc-type 整改报告`（文书类型按第五步第2条选）；无法运行时按 `references/checklist.md` 检查。

## 单位差异

| 单位 | 调整要点（详见 `references/units.md`） |
|---|---|
| 党政机关 | 巡视巡察整改用党组（党委）名义；提法逐字对照原文 |
| 基层 | 状态以台账为准，已完成须有佐证；不倒签、不补记；不向村（社区）转嫁整改任务 |
| 社区 | 篇幅从短，语言通俗；居民信息脱敏；不设定罚款等强制措施 |
| 公立医院 | 党委、行政两套代字按来源选用；"三重一大"措施写明党委会研究；患者信息脱敏；医保金额分口径 |
| 高校 | 学院台账与学校口径一致，编号沿用学校编号；学生信息不进对外材料 |
| 中小学 | 措施写到年级、处室和日期；不给教师摊派无关任务；学生信息不进材料 |
| 国有企业 | 党委前置研究再提交董事会或经理层；商业秘密不进公开版本；追责结果只写用户提供的 |

## 角色适配

- 教学模式：材料不全时先给任务卡和问题清单，确认后再建台账、起草。写作所需材料已经给齐（反馈原文加措施意见，或检查清单加各科室情况），或交接卡"已确认"栏已列明主要事项的，任务卡、问题清单和成稿一次交付。起草说明末尾附写作要点：三清单为什么这样分、问题为什么必须照录、本稿一条状态的认定理由（用正误对照），每项【待补】到哪里找（反馈意见原文、分管领导、业务科室、财务凭证）。
- 高效模式：任务卡只写进起草说明；台账、正文、Excel 一次交付；起草说明只写假设、待补、待核实、状态变化和对账结果；需要时同时出报送版和公开版。
- 转译模式：接受业务科室的口语进展（"系统上个月上线了""钱退了一半"），先改写成台账进展栏的"日期＋事实"，再判定状态并写明理由；只问日期、金额、佐证这类业务事实，不问公文术语。
- 审稿模式：用户拿来已写好的报告和台账要把关的，不重写全文，先对账，输出一页纸摘要（状态不一致、统计不符、弱化表述、无依据的成效，各几处）和 P0、P1、P2 问题清单；要全面核稿的转 gongwen-review。
- 严谨模式：问题表述逐字对照反馈原文；政治性提法只用用户提供的原文，没有的标【待核实：请对照最新原文】；起草说明附提法核对清单；公开版删去问题线索和人员信息。
