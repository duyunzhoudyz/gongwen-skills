# 改稿润色（gongwen-polish）

在用户已有的稿子上做七种修改：压缩、扩写、调语气、转译、口语化或书面化、按领导批注改稿、多稿合并。只动表达和取舍，不加事实：改后稿里的每个数字、案例、表态，都能在原稿或用户给的材料里找到；缺的标【待补】，几稿说法不一的列出来由用户定。每次交付都附修改说明，写清改了什么、为什么改。

## 适用范围

- 适用：已经有一稿（哪怕是大白话、流水账式的成稿），要按下表改。

| 任务 | 用户常说 |
|---|---|
| 压缩 | 压到3000字、太长了砍一半、按减负规定压一压、讲话控制在15分钟 |
| 扩写 | 太单薄了扩一扩、写到2000字 |
| 调语气（新文种和受文对象已定） | 报告改成发给下面的通知、领导定了请示改成函发、下发的改成向上汇报的口气 |
| 转译 | 科室写的大白话改成公文、业务说法改得像公文 |
| 口语化或书面化 | 讲话稿改得好讲一点、把领导讲话录音整理稿改成书面材料 |
| 按批注改稿 | 领导批了“太虚”“数据呢”、按批注改、领导在 Word 里批了意见 |
| 多稿合并 | 两稿合成一稿、甲乙两个版本取长补短 |

- 不适用（转交）：

| 用户要的 | 转给 |
|---|---|
| 通篇去 AI 腔：“值得注意的是”、翻案句、新八股词 | gongwen-humanize |
| 专门去免责声明、对冲、平衡腔；同一份下行文“像在商量”，改成要求口气 | gongwen-direct |
| 全面核稿，查格式、标点、数字、提法 | gongwen-review |
| 重拟标题、小标题 | gongwen-title |
| 只有素材、记录、数据表，还没有稿子 | 起草 skill：总结汇报 gongwen-report，法定公文 gongwen-draft，讲话 gongwen-speech，党建 gongwen-party |
| 判断该用什么文种（“这个请示是不是该用函”），或文种用错、行文规则有问题要改 | gongwen-draft 模式二 |
| 要推倒结构重写：换文种后结构全变（如报告改实施方案、拆任务分工）、提纲重搭 | 原起草 skill；以上级文件为依据拆任务的交 gongwen-implement |
| 长材料压成政务信息、简报、新闻稿 | gongwen-brief |
| 拿原稿和领导改过的稿子，总结领导的改稿习惯 | gongwen-profile |
| 排成 Word | gongwen-format |

一稿兼有几种问题时，本 skill 只做本节第一张表中的任务。正文里的免责声明、AI 自述、对话引导语按红线三直接删除；其他 AI 腔、对冲语气、格式错误不顺手改，列入修改说明的“转交事项”。用户同时要求“顺便去 AI 味”之类的，先完成本 skill 的任务，再交 gongwen-humanize：能调用其他 skill 的环境接着调用，网页环境在起草说明之后给出交接卡。

## 开工检查

1. 保密（`references/_shared/guardrails.md` 第一条）：
   - 第一次请用户给稿子时，或用户第一条消息就附了稿子时，在本次回复开头附一句：“请勿输入涉密信息和内部敏感信息；材料涉密的，请使用单位内网部署的模型。”同一会话只说一次。
   - 先扫一遍再改：带密级标识（“秘密★”“机密★”“绝密★”，或版头标注密级和保密期限），或标注“内部资料”“工作秘密”“不得外传”“内部使用”的，立即停止，不改写、不复述原文，告诉用户涉密信息不得输入联网 AI 工具；用户说明以下情况之一后再继续：（1）当前用的是单位内网部署、允许处理此类材料的模型（带密级标识的国家秘密只能在经批准的涉密信息系统中处理）；（2）已删除相关内容；（3）标识系误加，或材料已经公开。正文中正常出现“保密工作”之类的词语不算。
   - 有身份证号、手机号、病案号、住院号、学号、银行卡号、家庭住址、患者或学生真实姓名的，提醒用户脱敏；改稿中一律写成“张某”“138****0000”。这是本 skill 唯一允许改动的事实。“保密提示”按位置和信息类型列出，不复述原值。
     - 误：将“刘××”改为“刘某”，删去身份证号“3301……”。（复述了原值）
     - 正：第一部分第1条：姓名、身份证号、手机号、住址已脱敏。
2. 留底：Agent 环境下，用户贴的文字原样存为当前工作目录下的 `公文/<YYYYMMDD>-<简短标题>/原稿.txt`（多稿存 `原稿-甲.txt`、`原稿-乙.txt`，批注存 `批注.txt`）。用户给的文件不改动：.docx 先运行 `python scripts/polish_stat.py body 原文件.docx --out <上述目录>/原稿.txt` 转成文字稿（有修订痕迹的按接受全部修订导出，在说明中写明）；正文之后混有批注转述、修改说明的，正文另存为 `原稿.txt`，批注另存为 `批注.txt`；其他文件直接作原稿。下文的 `原稿.txt` 都指这份原稿。
3. 单位画像：读 `.gongwen/单位画像.md`，没有再找 `~/.gongwen/单位画像.md`，用户粘贴在对话开头的按粘贴内容处理；同目录有 `领导偏好卡.md`、`禁用词.md`、`文风参数.md` 的一并读取。偏好卡里的篇幅、用词、数据呈现偏好，优先于本 skill 的默认做法。没有画像时按 `references/_shared/profiles/roles.md` 第九节“无画像降级”处理，单位类型从稿件判断。
4. 定任务：按“适用范围”第一张表识别。一次可叠加几项（如“按批注改，再压到2000字”），按“合并 → 批注 → 调语气、转译、口语化或书面化 → 压缩或扩写”的顺序做，篇幅最后定。
5. 定角色模式：按 roles.md 第一节的顺序；本 skill 中的差异见“角色适配”。党建、组织、纪检材料和对外发布的材料叠加严谨模式。
6. 提问：最多 3 个，只问下表中的缺项，其余用默认值写进“所作假设”。用户说“直接改”或高效模式时不问，调语气缺发文主体、受文对象或文种的除外：这一项照问，用户仍不答的只出措辞对照建议。

| 任务 | 只问 | 不回答时的默认 |
|---|---|---|
| 压缩、扩写 | 目标字数或讲话时长 | 压缩：下行文件按减负规定上限，已在上限以内的和其他材料压到原稿的七成；扩写：不定目标，展开到素材用完为止 |
| 调语气 | 新的发文主体、受文对象和文种 | 不猜，必须问清；用户不答的只出措辞对照建议，不改全文；要本 skill 判断用什么文种的，转 gongwen-draft |
| 按批注改稿 | 批注原话和对应位置 | 位置看不出的那条列为“未落实，请确认位置” |
| 多稿合并 | 以哪一稿为底稿 | 最新的一稿；分不出新旧的，用结构最完整的一稿 |

7. 守住两条底线（`references/_shared/guardrails.md` 第六条）：要求“改得查不出是 AI 写的”，或把正式文件改成便笺、“白头”规避发文管理的，说明原因，不按此办，其余照常改；对照检查、述职、心得体会、研讨发言、交流发言、谈心谈话记录要扩写而缺本人事例的，只在相应位置标【待补：本人具体事例】，不代拟，在起草说明中给出填写指引（写本岗位做过的哪件事、学习后工作有什么改变）。党建个人材料素材不足、需要先出提纲的，转 gongwen-party。
8. 交接卡：网页环境用户贴了交接卡的，按卡上的单位画像、当前模式、任务、本站和已确认事项开工，卡上有的不再问（`references/_shared/style/output-format.md` 第四部分）。

## 工作流程

### 第一步　读稿，冻结事实

1. 读到单独一行的【起草说明】为止。原稿已有起草说明的，其中的待补、待核实事项继承下来。
2. 判定文书类型（用统一词表：总结、汇报材料、讲话稿、通知、报告、请示、函……）、行文方向、单位类型、当前字数。有 Python 时运行 `python scripts/polish_stat.py count 原稿.txt`；没有时按“一段约多少字”估算，在说明中写“字数为估算”。
3. 列事实清单（供自己对照，不必输出）：
   - 数字、日期、金额、百分数、发文字号、书名号和引号内的内容；
   - 人名、职务、单位名、责任分工、完成时限；
   - 状态和强度：已、正在、拟、将；必须、应当、要、可以、力争；
   - 政治性提法、上级文件原文、领导原话（指稿中引用的上级领导讲话和他人原话，不含本次要口语化、书面化的讲话人本人的讲话）；
   - 【待补】【待核实】标记。
4. 改稿全程对照清单：清单上的内容只能原样保留，或在下列四种情形整句删去：压缩；合并（去重）；按删减类批注删去批注所指内容；调语气时删去新方向不适用的事项（如向上请求的事项）。删去的都写进修改说明“删去的数据”并写明理由。不能改值、不能升级状态、不能换说法。例外只有四种，都写进修改说明：
   1. 脱敏替换；
   2. 调语气时按 `references/tone.md` 对照表调整称谓和要求措辞；
   3. 批注明确要求调语气强度的（如“语气太软”），按 `references/_shared/style/defensive.md` 第六部分调整“必须、要、可以”，写进批注落实对照表；
   4. 讲话人本人的讲话稿、录音整理稿口语化或书面化时，可以改表达，观点、表态、要求和数据不变。
   - 误：原稿“拟于11月启动”，改稿写成“11月已启动”。
   - 正：保持“拟于11月启动”。
5. 局部修改（按批注改、调语气）时，修改范围以外的原文逐字保留。

### 第二步　按任务改

各任务的细则和对照表见参考资料，这里是每项必做的动作。Agent 环境改完先把正文写入当前工作目录下的 `公文/<YYYYMMDD>-<简短标题>/正文.txt`（同名已存在时加 `-v2`，此后各步都用这份），复核中的修改直接改这份文件，第四步不再另写。

**压缩**（细则 `references/length.md` 第一至五部分）
1. 定目标：用户给的 > 偏好卡、画像 > 默认值（见开工检查第 6 条表）。讲话按时长乘每分钟约 200 字（画像另有语速的按画像）。目标两种口径：用户说“以内”“不超过”的为上限口径，不超过上限即可，超 1 字也不行；改后低于上限七成的，复查是否删了必保内容，不为凑够七成加字。其余允许±10%。
2. 算账：删减量＝当前字数－目标。有 Python 时运行 `python scripts/polish_stat.py count 原稿.txt --target 3000`（上限口径加 `--max`），看各部分占比。
3. 按顺序删，删完一级算一次字数，够了就停：
   1. 铺垫：形势背景、重要意义、“在……的正确领导下”；
   2. 复述：照抄上级文件、重复前文、段末小结；
   3. 空泛表态：“高度重视”“切实加强”之类后面没有具体动作的句子；
   4. 重复举例：同类事例只留数据最全的一两个。
4. 还不够，再做句内压缩：合并同类项、删修饰语、长句改短句（`references/length.md` 第四部分）。
5. 必保内容：事实和数据、措施、责任主体、时限、需要上级支持的事项、【待补】【待核实】。删到只剩必保内容仍超目标的，停下来告诉用户现在多少字、还差多少，请用户选：放宽目标；指定可删的部分；把某部分转为附件。不为达标删事实，也不把估算的字数说成已达标。
   - 误：为压到3000字，删去“全年排查隐患218处、整改210处”。
   - 正：先删首段形势背景和三处重复表态；仍超出时停下，列出可选办法。

**扩写**（细则 `references/length.md` 第六部分）
1. 只展开已有事实：把一句话的做法按材料展开成步骤；补上材料里有、原稿没写的时间、主体、数据；把材料里有、原稿漏掉的事项补进来。
2. 不加形势背景、重要意义、表态，不编案例、数据、成效，不从结果倒推过程（材料没有调研记录，就不写“经过深入调研”）。
3. 素材撑不起目标字数的，按实际篇幅交付，说明中写明目标和实际字数，列出补哪几样材料就能写足；结构上确需而缺事实的位置标【待补】。
   - 误：“开展了安全培训”扩成“组织专题培训12场，覆盖职工600余人次，参训人员安全意识显著提升”（材料无此数据）。
   - 正：“组织安全培训【待补：场次】场，覆盖【待补：人次】人次”，并在说明中请用户提供培训台账。

**调语气（行文方向互转）**（对照表 `references/tone.md` 第一、二部分）
1. 先定关系：新的发文主体是谁，写给谁，用什么文种，由用户定。本 skill 按 `references/_shared/rules/doc-types.md` 第六节决策表核对方向和文种是否匹配；不匹配的，向用户说明并建议转 gongwen-draft 模式二，不自行改定文种。
2. 改五处：称谓、开头语、请求或要求的措辞、期望语、结语；标题中的文种随之改。内容和事实不变。
3. 新方向必需而原稿没有的要素标【待补】：改下行文缺责任单位、完成时限、联系方式（原稿已有报送安排的才写报送方式）；改请示缺请示事项、倾向性意见。只标【待补】，不新拟任务和报送要求。
4. 新方向不适用的事项整句删去：上行文中向上请求的事项，在下行文中没有承受方，不改写成对下级的任务。删去的写进修改说明，建议另行请示。
5. 分清谁来做：原稿中由下级执行的事项（“我局将督促各卫生院于……前完成”）改成对下级的要求（“各卫生院要于……前完成”）；本机关自己做的事项保留主体（“县卫生健康局将会同……开展督查”），不转给下级。
6. 部门以自己名义面向下级党委、政府的（如县直部门发各乡镇人民政府），不写“必须”“务必”“要”之类的指令性要求（`references/_shared/rules/jianfu.md` JF-16），改用“请各乡镇……”的商洽口吻，或建议由县政府办公室行文；在修改说明中写明依据。
7. 换文种后结构要整体重搭的（报告改实施方案、要拆任务分工），本 skill 只改语气，并建议转 gongwen-draft 或 gongwen-implement。
   - 误：县卫生健康局给县政府的报告改发各乡镇卫生院，原句“恳请县政府协调解决急救车辆缺口”只删去“恳请”，或改成“各卫生院要完成急救车辆清点，缺口情况报县卫生健康局”（原稿没有的任务和报送要求）。
   - 正：整句删去，修改说明写明“原稿向上请求事项不适用于下行文，已删去，建议另行请示”；原稿中由卫生院执行的措施改成对卫生院的要求，时限缺的标【待补：完成时限】。受文对象是乡镇人民政府的，按第 6 条处理。

**转译（业务语言改公文语言）**（词表 `references/tone.md` 第三部分）
1. 逐句改：口语词换公文词；一句话写一件事；主语换成单位（我科、我院、公司）；按原稿顺序加层次序号，不调整结构。
2. 业务术语、指标名称照用；首次出现的缩写写全称，全称拿不准的标【待核实：全称】。
3. 不拔高：“还行”不改成“成效显著”，“差不多完成”不改成“全面完成”；带“大概”“差不多”“好像”的数字，正文写原数并标【待核实：说明】。
4. 修改说明按“业务原话→公文表述”对照列出典型几处。
   - 误：“今年手术量涨了不少，大概多了两百台”改成“手术量大幅攀升，同比增长显著”。
   - 正：“手术量较上年增加约200台【待核实：准确台数】。”需要写全年总量而原话没有的，写“全年完成手术【待补：全年手术台数】台”。

**口语化或书面化**（`references/tone.md` 第四部分）
1. 讲话稿口语化：长句拆短，一句一般不超过 30 字；长定语拆开；加称谓和过渡语，前后呼应；精确数据保留，书面括注、顿号长串改成说得出口的句子。不加金句，不加引文。
2. 书面化（讲话录音整理稿、发言改成材料）：删口头禅、现场称呼、重复，补全句子，口语词换书面词，加层次序号。
3. 讲话稿改完按每分钟约 200 字核算时长，写进说明。

**按领导批注改稿**（对照表 `references/annotations.md`）
1. 收齐批注：原话和位置。Agent 环境下用户给的是带批注的 docx，运行 `python scripts/polish_stat.py comments 批注稿.docx` 提取；输出显示有修订痕迹的，按开工检查第 2 条用 body 转成 `原稿.txt`（领导改过的字按改后的算），不接受某处修订的请用户先在 Word 中处理。手写、截图批注，或网页环境上传 docx 而读不出批注的，请用户逐条转述“位置｜原文片段｜批注原话”；有修订痕迹的，请用户在 Word 中接受修订后再粘贴正文。
2. 逐条按 `references/annotations.md` 第二部分对照表改；一条批注有两个意思的（“太虚，数据呢”）拆成两项。
3. 补事实类先在原稿和用户材料里找；找不到的标【待补：说明】，对照表状态写“待补材料”，在说明里请用户提供。
   - 误：批注“数据呢”，改成“居民满意度达98%”（材料里没有）。
   - 正：“居民满意度【待补：测评结果及测评机构】”，对照表写“待补材料：满意度测评结果”。
4. 批注与红线冲突的（如“写成全市第一”而材料没有依据），按红线处理，在对照表中写明原因，请用户提供依据。
5. 批注以外不顺手改；看到的其他问题写进修改说明“批注以外的建议”。
6. 出“批注落实对照表”，列为：序号｜位置｜批注原话｜落实方式｜状态（已落实、部分落实、待补材料、未落实请确认）。
7. 偏好卡：从本轮批注归纳一至三条可能的偏好，按 `references/annotations.md` 第四部分写成“历次改稿记录”的一行，标“观察中”。Agent 环境征得用户同意后按该部分追加到 `.gongwen/领导偏好卡.md`（先备份，只动改稿记录和维护记录，没有偏好卡的不新建）；网页环境把这一行给用户自己保存。

**多稿合并**（`references/merge.md`）
1. 编号定底稿：甲稿、乙稿……写明各稿来源；底稿按开工检查第 6 条表确定，结构以底稿为准。领导改过的稿子与原稿合并的，以领导稿为底稿，措辞以领导稿为准；原稿有、领导稿没有的数据和事项补回，注明“领导稿未保留，已补回，请确认”；领导稿删去的评价和表态不补回。
2. 按部分对齐，同一事项取事实更全、表述更准的说法；两稿各有的事实都保留，去掉重复。
3. 冲突不替用户选，不平均、不相加：数字、口径、时限、措施不一致的，正文写底稿说法；状态、结论不一致的（如“基本完成”与“全面完成”），正文一律写较保守的说法。两种都标【待核实：甲稿为……，乙稿为……】，不把两种说法揉成第三种，整理进“合并冲突清单”（序号｜位置｜各稿说法｜本稿处理｜请谁确认）；提法不一致的都不改，标【待核实：请对照最新原文】。
4. 出“合并说明”：部分｜采用｜理由；舍弃的句子也写一句理由。Agent 环境运行 `python scripts/polish_stat.py trace 正文.txt 原稿-甲.txt 原稿-乙.txt`，“未找到来源”的句子和“句内找不到来源的小句”逐条核对，属新增事实的删去或改为【待补】。

### 第三步　复核

1. 事实比对（必做）：
   - 有 Python 时运行 `python scripts/fact_diff.py 原稿.txt 正文.txt --json`。“改稿新增”每一项都必须是新增的【待补】【待核实】或脱敏替换，否则恢复原稿写法。“原稿有而改稿没有”只允许第一步第 4 条的四种删除情形，逐项确认删的不是成效数据、责任、时限、需上级支持的事项（调语气删去的上行请求除外），并写进修改说明“删去的数据”；其他的一律恢复。
   - 用了用户补充材料，或合并多稿的，用脚本拼参照文件，不手工拼接（手工拼接时原稿的【起草说明】会把后面的材料截掉）：`python scripts/polish_stat.py body 原稿.txt 材料.txt --out 参照合并.txt`（合并时依次列各稿；同名文件已存在时脚本改写为 `-v2`，以它打印的“已写入”路径为准），再运行 `python scripts/fact_diff.py 参照合并.txt 正文.txt --ledger`，输出的每一项同样只能是新增标记或脱敏替换。
   - fact_diff 不比对人名、单位名、分工、时限和义务强度，对照第一步清单人工核一遍。
2. 改动范围：运行 `python scripts/polish_stat.py compare 原稿.txt 正文.txt`，逐段列出修改、移动、拆分、删除、新增。每处改动都能对应到本次任务；按批注改稿时，每处改动都能对应到某条批注，对应不上的恢复原文。“新增”段落和“修改”项下列出的“多出的文字”逐条核对：只能是措辞调整、新增标记或脱敏替换，带新数字、荣誉、评价、排名的删去或改为【待补】。
3. 篇幅：上限口径运行 `python scripts/polish_stat.py count 正文.txt --target <目标> --max`，确认没有超过上限；其余去掉 `--max`，确认在±10% 以内。超出的继续删，或已按压缩第 5 条告知用户。
4. 机检：`python scripts/gongwen_lint.py 正文.txt --doc-type <文书类型> --json`。本次改动带进来的问题必须改掉；原稿就有、又不在本次任务内的（如发文字号格式），列入“转交事项”，建议用 gongwen-review。命中公文白名单的保留（`references/_shared/style/ai-tone.md` 第二部分）。
5. 没有 Python 或脚本出错的，按 `references/checklist.md` 逐项人工核对（读不到时按本节和自检清单核对）：字数逐段估算（标题和【起草说明】之后不算），写“约N字（估算）”，上限口径按上限的九成五控制；数字、日期、文号、书名号和引号内的内容逐项对照原稿和材料；状态词、义务强度词逐处对照。在说明中写“未运行机检和事实比对，已人工逐段核对”。

### 第四步　交付

1. Agent 环境：正文已在第二步写入 `正文.txt` 并在复核中改定；在同一目录写入 `起草说明.md`，同名文件已存在时加 `-v2`、`-v3`，不覆盖。对话中只报文件位置、字数变化（原稿→改稿）、修改处数、待补和待核实各几条。
2. 网页环境：依次输出改后正文、单独一行【起草说明】、说明内容。正文前不加“以下是修改后的稿子”之类的引导语。路线还有下一站的，在起草说明之后输出更新后的交接卡，告诉用户新开对话，先粘贴下一站的提示词文件，再粘贴交接卡和改后正文。
3. 审稿模式只给修改建议、不改全文时，按“角色适配”输出建议清单，不输出正文。

## 输出规范

正文、起草说明、交付位置按 `references/_shared/style/output-format.md`：正文纯文本，不用 Markdown，层次序数依次为 一、（一）1.（1），正文中只允许【待补：说明】和【待核实：说明】两种提示。起草说明按需包含：

一、所作假设：任务、目标字数、底稿、单位类型、角色模式。
二、待补事项：原有和新增的，逐条写位置和要补什么。
三、待核实事项。
四、修改说明：开头写“字数：原稿约 N 字，改后约 M 字”和“共修改 K 处”；按任务写改了什么、为什么改，写法见“角色适配”；“删去的数据”（有删除时，逐项写理由）；“转交事项”；“事实核对：fact_diff 比对无差异”或差异项及处理。
五、保密提示：按位置和信息类型列出脱敏处，不复述原值。
六、写作要点：仅教学模式。

附表按需放在说明末尾，标题依次为“附：批注落实对照表”“附：合并说明”“附：合并冲突清单”“附：领导偏好卡改稿记录（待保存）”“附：提法核对清单”。附表可以用表格。

## 自检清单

- [ ] 保密扫描在改稿之前做了；脱敏替换都写进了保密提示。
- [ ] 改后稿没有原稿和用户材料里都没有的数字、案例、成效、排名、引语；fact_diff 清单为空或每项都有说明。
- [ ] 没有升级状态（拟、将写成已），没有改动责任分工、时限；义务强度只在第一步第 4 条的例外情形下调整，并已写进修改说明。
- [ ] 【待补】【待核实】一个不少；新增的都写进待补、待核实事项。
- [ ] 压缩：按铺垫、复述、空泛表态、重复举例的顺序删；必保内容都在；“以内”“不超过”的没有超过上限，其余在目标±10% 以内，或已向用户说明。
- [ ] 扩写：没有背景、意义、表态和编造的事实；素材不够时按实际篇幅交付并说明。
- [ ] 调语气：称谓、开头语、措辞、期望语、结语和标题文种一致；新方向缺的要素已标【待补】。
- [ ] 按批注改：每条批注都在对照表中，有状态；批注以外没有顺手改。
- [ ] 合并：冲突都列入冲突清单，没有悄悄挑一个；每句都能找到来源。
- [ ] 政治性提法、上级文件原文、领导原话没有被改写或截断。
- [ ] 正文无 Markdown、无免责声明、无“以下是”之类的引导语。

有 Python 环境时运行：`python scripts/gongwen_lint.py 正文.txt --doc-type <文书类型>`，以及第三步的 fact_diff、compare、count。无法运行时按第三步第 5 条人工核对。

## 角色适配

- 教学模式：压缩、扩写、调语气先给修改计划（删哪几处、加哪几处、改哪五处措辞）请用户确认，用户说“直接改”的除外；修改说明逐条列“原文｜改后｜理由”三栏，理由落到删减顺序、措辞对照表或规则条款；附写作要点：本稿最该学的三处。
- 高效模式：不提问直接改（调语气缺受文对象或文种的照问，见开工检查第 6 条）；修改说明不超过 5 条，“删去的数据”算一条，条内逐项列出；可同时给两个篇幅（如3000字版和1500字版）；可一次处理多份稿件，逐份输出。
- 转译模式：只问业务口径（统计时段、计量单位、指标名称）；术语、指标、口径一字不动；修改说明按“业务原话→公文表述”对照，用业务人员听得懂的话写理由。
- 审稿模式：默认不改全文，先给一页纸：主要问题三至五条、建议删改的段落和预计改后字数、需要补的材料；用户说“那你改一版”时按高效模式改。
- 严谨模式：政治性提法、上级文件原文、领导原话一律不改写、不截断，压缩时只能整句保留或整句删去并在说明中列出；附提法核对清单（提法｜位置｜出处｜是否改动）。

## 单位差异

| 单位类型 | 主语和称谓 | 改稿时特别注意 |
|---|---|---|
| 党政机关 | 我局、我委；你局、各区县 | 下行文件压缩按减负规定上限，超限为 P1；提法最密，改前先圈出 |
| 基层 | 我镇、我街道；各村（社区） | 面向群众的稿子转大白话时写清时间、地点、要求、咨询电话；不向村（社区）转嫁责任 |
| 社区 | 社区居委会；各位居民 | 对居民用服务和提醒的口气，不用命令口吻；居民信息一律脱敏 |
| 公立医院 | 我院、我科 | 指标名称照用原稿，不改成通俗说法；缩写首次写全称；患者信息脱敏 |
| 高校 | 我校、学院 | 校级与学院两级发文语气不同；学术材料保留学术用语；学生信息脱敏 |
| 中小学 | 我校、各班；各位家长 | 致家长的稿子通俗、具体，写清需要家长配合的事 |
| 国有企业 | 公司、集团 | 经营数据、专业术语照用；商业秘密提醒脱敏；党委前置研究等程序表述不删 |

表中要“写清”的要素，原稿和材料没有的标【待补】，不自拟。医院、学校、国企的内部材料不受减负规定字数条款直接约束，超限只作提示。详见 `references/units.md`。
