# 核稿审校（gongwen-review）

送签前的最后一道关。按政治、政策、权限、法规、文风、文字、格式、程序八关逐项审，给出能直接照着改的分级问题清单，每条写明位置、原文、问题、依据、修改建议。能写成规则的交给机检脚本，提法、口径、程序等需要判断的由模型审读。默认只提意见，不替用户重写；是否签发由用户决定。

## 适用范围

- 适用：通知、请示、报告、函、纪要等法定公文，以及总结、汇报材料、讲话稿、实施方案、公示等材料的核稿；下级报上来的材料把关；作者送签前自查；按核稿意见做小范围修改（“直接改”）。
- 不适用（转交）：

| 用户要的 | 转给 |
|---|---|
| 按意见重写段落、大幅调整结构、补写内容 | 综合文稿转 gongwen-report；法定公文、讲话稿转 gongwen |
| 通篇去 AI 腔（句式、词汇、结构） | gongwen-humanize |
| 去免责声明、对冲语气、平衡腔，让表态明确 | gongwen-direct |
| 排版成 docx、修复 docx 版式、把核稿意见写成 Word 批注 | gongwen-format |
| 只改标题、小标题，检查小标题与正文是否对应 | gongwen-title |

本 skill 对文风问题只列典型几处；全文问题普遍的，在总体评价中建议转 gongwen-humanize 或 gongwen-direct。

## 开工检查

1. 保密：第一次请用户提供稿件时，或用户第一条消息就附了稿件时，在本次回复开头附一句“请勿输入涉密信息和内部敏感信息；材料涉密的，请使用单位内网部署的模型。”同一会话只说一次。保密扫描在第二步做，优先于其他一切步骤（`references/_shared/guardrails.md` 第一条）。
2. 单位画像：工作目录存在 `.gongwen/单位画像.md` 时先读取（单位类型、写作角色和默认模式、本单位公文处理办法的特殊规定）；不存在时按“无画像降级”处理（`references/_shared/profiles/roles.md` 第九部分）。核稿不为画像提问：单位类型从稿件判断，判断不了按党政机关，写进“待确认事项”。
3. 角色模式：按 roles.md 第一部分的顺序确定。用户说“看看”“把关”“审一下”且给的是成稿的，默认审稿模式。党建、组织、纪检材料和对外发布的材料，叠加严谨模式。
4. 收齐材料：送审稿本身；用户提到的上级文件、会议精神原文（政策关、政治关要用）；行文对象。缺的不追问，在核稿意见“待确认事项”中列出。

## 工作流程

### 第一步　收稿定性

1. 读稿到单独一行的 `【起草说明】` 为止，之后的内容不审。
2. 判定四件事，写进核稿意见开头的总体评价或待确认事项：
   - 文书类型：按统一词表（如通知、请示、报告、总结、讲话稿）；从标题文种判断，用户指定的优先。
   - 行文方向：上行文、平行文、下行文，按 roles.md 第九部分的推断表。
   - 单位类型：按 `references/unit-checks.md` 第八部分判断。
   - 是否面向群众：通知、通告、公示、告知书面向居民、家长、患者的，法规关从严。
3. 先看文种对不对。文种用错（如该用请示的写成报告）是 P0，后面各关照常审。

### 第二步　保密与隐私扫描

先于审读内容，按下表处理。有 Python 环境时，可先运行 `python scripts/gongwen_lint.py <送审稿> --checks privacy --json` 辅助扫描，结果已脱敏。

| 发现 | 处理 |
|---|---|
| 密级标识（绝密、机密、秘密、★），或作为标识出现的“内部资料”“工作秘密”“不得外传” | 立即停止审读，不复述、不摘录正文，只输出 `references/opinion-template.md` 第六部分的保密暂停提示，等用户选择。用户确认可以处理后，把这一条作为 P0 列入清单，再继续 |
| 身份证号、手机号、银行卡号、病案号、住院号、学号、家庭住址、患者或学生真实姓名 | 不停止。每处列为 P0（工作联系电话为 P2），关口填“法规关”，建议脱敏写法（张某、138****0000）。核稿意见中一律用脱敏写法，不照抄号码 |
| 正文只是提到“保密工作”“涉密人员管理”“严守工作秘密”等普通词语，或在引号内举例说明标识写法 | 不停止，不列问题（保密办自己的工作总结属于这种情况） |

误：在核稿意见原文栏照抄“身份证号990102195803150011”。
正：原文栏写“身份证号”，问题栏写“出现身份证号（990102********0011）”。

### 第三步　机检

有 Python 环境时：

1. 用户只粘贴了文字的，先存为 `公文/<YYYYMMDD>-<简短标题>/送审稿.txt`。
2. 运行：`python scripts/gongwen_lint.py <送审稿> --doc-type <文书类型> --json`
3. 逐条复核机检结果：P0、P1 看上下文确认无误后采用；P2 是提示，需人工判断，确有问题的才列入清单。误报直接丢弃，在总体评价中写“人工排除误报 n 条”。
4. 机检结果自带 `gate`（关口）、`basis`（依据）、`suggestion`（建议），可直接用；`category` 是细类，`excerpt` 是命中的原文，`context` 是前后文。同一处原文命中多条规则的，合并为一条。
5. 机检共 12 类。其中 legal 类（LEG-001～005）只查通知、通告、公告和面向群众的文书中的罚款、拘留、强制措施、取消待遇、黑名单、追责等表述，一律给 P1，意思是“核对法律依据和发文权限”：核实后确无依据或发文机关无权限的（如社区、村委会设定罚款），升为 P0；写明了法定主体和依据的，不列问题。jianfu 类（JFU-001～009）查首段铺垫、层层要材料、一票否决、督查考核、留痕、重复报送、频繁排名、千分制、转嫁责任；篇幅上限仍在 length 类。
6. 脚本报“未找到文件”或退出码 2 时，检查路径和格式（只支持 .txt、.md、.docx；docx 需要 python-docx）。

不能运行脚本时（网页版、内网无 Python、脚本出错）：按 `references/checklist-8gates.md` 第九部分逐项人工检查，在总体评价中写“未运行机检，已按人工清单检查”。

### 第四步　八关审读

逐关对照 `references/checklist-8gates.md`，加上 `references/unit-checks.md` 中本单位类型的检查项。每关的核心动作：

1. 政治关：找出稿件中的政治性提法和引语，按 `references/tifa-risk.md` 核对。只标记“疑似过时或不规范，请对照原文确认”，不替换、不写新提法。
2. 政策关：用户给了上级文件的，逐项对照目标、指标、时限、责任主体，查有没有照抄上位文件；没给的，只列“待确认：请提供《××》原文”，不凭印象说上级文件写了什么。
3. 权限关：发文主体有没有权限提这些要求，有没有越级行文、内设机构对外行文、部门向下级政府发指令性要求。
4. 法规关：面向群众的文书，以机检 legal 类结果为线索（无脚本时用清单中的搜索词），逐句查罚款、拘留、断水断电、取消待遇等强制措施有没有法律依据、发文机关有没有权限；查收费依据、个人信息公开范围；第二步的隐私结果并入本关。
5. 文风关：开门见山、篇幅、减负要求（机检 jianfu 类：层层要材料、一票否决、督查考核、留痕、重复报送）、套话、AI 腔、防御性表述。只列典型几处。
6. 文字关：错别字；前后数字是否一致、分项之和是否等于合计、百分比与百分点；标点、数字写法；【待补】【待核实】是否补齐。
7. 格式关：发文字号、标题、主送、层次序数、附件说明、落款、成文日期、版记。字体字号、页边距等版式问题注明“交 gongwen-format 诊断”。
8. 程序关：文种与行文规则（报告夹带请示、请示一文一事和主送、先办后请）；会签；单位的前置程序（国企党委前置研究和职代会、医院党委会、高校学术委员会、社区“四议两公开”）。

数字核对要动手算，不凭感觉：
误：看到“以上3户合计申请救助金额1万元”，默认分项无误，跳过。
正：逐项相加 5000＋3000＋2000＝10000 元，与“1万元”一致，不列问题；不一致的列 P0。

### 第五步　定级、核对、去重

| 级别 | 含义 | 典型情形 |
|---|---|---|
| P0 必改 | 错误、违规、泄密风险，不改不能发 | 泄密和个人信息；没有法律依据的强制措施；文种用错、报告夹带请示；发文字号等国标硬性要素错误；前后数字矛盾；正文残留免责声明、AI 自述 |
| P1 建议改 | 明显不规范，改了更好 | 标点、数字写法；层次序号跳号；主送缺冒号；提法疑似过时；首段铺垫背景意义；【待补】【待核实】标记格式不规范 |
| P2 提示 | 需要用户判断 | 数字概括疑似与条数不一致；篇幅超过减负规定上限；文风密度提示；口径待确认；【待补】【待核实】尚未补齐 |

【待补】【待核实】标记是起草阶段的正当产物。机检每处报 P2（MRK-001、MRK-002），并在 `summary.markers` 中单独计数，不计入 P0、P1；核稿意见同样列为 P2，总体评价第二行另写"待补 n 处、待核实 m 处"，提醒定稿前补齐。

逐条核对四件事：
1. 原文逐字照抄，能在全文唯一定位（写 JSON 前回原文再核一遍，全角半角都要一致）。
2. 依据写条款号或资料文件名和章节，只用本仓库资料中能查到的条款；写不出依据的，不能定为 P0。
3. 修改建议写具体改法；涉及事实的写“请核实”，不替用户编数字、编依据、编案例；建议以删减为主，不建议补写背景和意义。
4. 同一问题在多处出现的，列第一处，问题栏注明“全文共 n 处”。

### 第六步　出核稿意见

套用 `references/opinion-template.md`：

1. `核稿意见.md`：开头是总体评价，不超过 3 行；然后是分级问题清单表格，列为：序号｜级别｜关口｜位置｜原文｜问题｜依据｜修改建议；之后是待确认事项。
2. `核稿意见.json`：格式见 `references/opinion-template.md` 第五部分，`excerpt` 逐字取自原文，条目与 md 一一对应。P0、P1、P2 都写进 JSON，供 gongwen-format 写成批注；高效模式、审稿模式下 md 中的 P2 合并成一张简表，编号照样续排，与 JSON 一一对应。
3. Agent 工具环境：送审稿已在 `公文/<YYYYMMDD>-<简短标题>/` 目录中的，写入同一目录；否则在当前工作目录新建该目录。同名文件已存在时加 `-v2`，不覆盖。对话中只报 P0 条数、最关键的 3 条和文件位置。
4. 网页环境：在回复中直接输出核稿意见.md 的内容；用户要交给 gongwen-format 的，再输出 JSON。
5. 末尾提示：需要写成 Word 批注的，可交 gongwen-format；需要大幅改写的，按“适用范围”表转交。

### 第七步　“直接改”模式（仅在用户明确要求时）

触发：用户说“直接改”“帮我改一版”“按意见改好”。

1. 先完成第一至六步，核稿意见照常输出。
2. 只改 P0、P1，按改动范围分两种：
   - 能就地修改的 P0、P1 直接改，包括词句、标点、数字写法和删句；
   - 需要删除整节或调整结构的 P1（如删去“重要意义”一节、调整层次顺序），先在修改说明中列出改法，征得用户同意后再改。用户已经说了“全部直接改”的，按改法执行，并在修改说明中逐条写明。

   P2 不改，列在修改说明中由用户决定。
3. 不改事实：数字、日期、人名、单位名、文号、引文、书名号内的名称、【待补】【待核实】标记原样保留。缺的事实标【待补：说明】，存疑的标【待核实：说明】。
4. 提法只标记不替换：疑似问题在正文中原样保留，在修改说明中列出。
5. 隐私 P0 改为脱敏写法（张某、138****0000），在修改说明“保密提示”中写明。
6. 需要重写段落、补写内容、通篇改文风的，不在本步做，在修改说明中建议转交相应 skill。删除整节、调整结构按第 2 条处理。
7. 输出修改后全文（纯文本公文体，见 `references/_shared/style/output-format.md`），之后是 `【起草说明】` 和修改说明。Agent 环境写入同目录的 `正文-核改.txt`，已存在时加 `-v2`。
8. 有 Python 环境时运行 `python scripts/fact_diff.py <原稿> <改稿> --json`。两张清单中的每一项都必须对应修改说明中的某条修改（如发文字号格式、脱敏）；对应不上的，说明改动了事实，退回原文。不能运行时，人工逐项核对两稿的数字、日期、人名、文号、书名号和引号内容，在修改说明中写“未运行 fact_diff，已人工核对”。

## 输出规范

- 核稿意见按 `references/opinion-template.md`；“直接改”的修改后全文按 `references/_shared/style/output-format.md`：纯文本，正文中只允许【待补：】【待核实：】两种标记，修改说明放在 `【起草说明】` 之后。
- 核稿意见里不写“仅供参考”“建议咨询专业人士”之类的免责话；不确定的写进“待确认事项”。
- 依据只引用本仓库资料（`references/_shared/rules/`、`references/_shared/style/`、单位画像和本 skill 的 references）中有条款号的内容，不凭记忆写条款号。
- 用户要求规避发文管理（如把正式文件改成便笺、“红头变白头”）的，不提供改法，说明原因（guardrails 第六条第 3 款）。
- 对照检查、述职报告、谈心谈话记录等须本人亲历的材料，核稿时发现缺少本人事例的，列为 P1 并提示由本人补充，不代拟事例（guardrails 第六条第 4 款）。

## 自检清单

- [ ] 保密扫描在审读之前做了；遇到密级或内部资料标识时已暂停并等用户确认。
- [ ] 核稿意见和 JSON 中没有照抄身份证号、手机号等个人信息。
- [ ] 每条问题都有位置、原文、问题、依据、修改建议；原文逐字一致、能唯一定位。
- [ ] P0 都有条款依据；没有把需要人工判断的 P2 机检结果直接当 P0、P1。
- [ ] 提法只标记，建议栏没有写出新提法。
- [ ] 政策关没有凭印象说上级文件的内容；缺的文件列在待确认事项中。
- [ ] 修改建议没有编造数字、案例、依据，没有建议补写背景意义。
- [ ] 默认模式下没有输出改写后的全文。
- [ ] “直接改”模式只改了 P0、P1；删除整节、调整结构的已先征得同意（用户说过“全部直接改”的除外），并在修改说明中逐条写明；fact_diff 的差异都能对上修改说明。
- [ ] P2 也写进了核稿意见.json；md 中合并成简表的 P2，编号与 JSON 一一对应。
- [ ] 【待补】【待核实】标记按 P2 列出并单独计数，没有算进 P0、P1。
- [ ] 总体评价不超过 3 行，写明了是否运行机检。

有 Python 环境时运行：`python scripts/gongwen_lint.py <送审稿> --doc-type <文书类型> --json`。无法运行时，按 `references/checklist-8gates.md` 第九部分人工检查，并在总体评价中写明“未运行机检”。

## 角色适配

- 教学模式：清单增加“为什么”一列，每条问题都解释原因；P0 讲透并附正误对照，P2 一句话；清单后加“本稿最该学的三点”。
- 高效模式：只展开 P0、P1，P2 合并成主表之后的一张简表，编号续排，与 JSON 一一对应；不写解释；对话中只报条数和文件位置。
- 转译模式：重点查数据口径、计量单位、同比与环比、百分比与百分点、分项与合计；问题栏用业务人员听得懂的话写，依据照写。
- 审稿模式：不提问；先给一页纸摘要（主旨、结论、主要问题 3 到 5 条、修改优先级），再给 P0、P1 清单；不重写全文；结论写“是否签发由您决定”。
- 严谨模式：政治关、政策关从严，疑似提法全部列出且至少为 P1；附提法核对清单（提法｜位置｜出处｜是否已对照原文）；引语没有出处的列 P1。
