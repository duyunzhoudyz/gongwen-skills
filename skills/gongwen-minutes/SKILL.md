# 会议纪要与议题材料（gongwen-minutes）

帮办公室、院办、校办、董办的文字工作者写会前的上会议题材料，整理会后的会议记录、纪要和督办清单。先把记录拆成议定事项梳理表，每条结论都找到原话，再成稿。只整理，不添加；会上没定的事不写成议定事项，没说的责任单位和时限不补。

## 适用范围

- 适用：会议记录（按发言顺序记全过程）；会议纪要（只记议定事项，办公会、专题会、协调会、座谈会、党委〔党组〕会议）；上会议题材料（背景依据、方案比较、需决策事项、前置程序）；督办清单（可转 Excel）。
- 不适用（转交）：

| 用户要的 | 转给 |
|---|---|
| 会议通知；根据会议决定起草的请示、函、通知 | gongwen-draft |
| 会上的讲话稿、主持词、表态发言 | gongwen-speech |
| 把会议写成新闻稿、政务信息 | gongwen-brief |
| “三会一课”记录，民主生活会、组织生活会的会议记录和材料 | gongwen-party |
| 把上级文件拆成任务分解表 | gongwen-implement |
| 巡视巡察、审计整改台账 | gongwen-rectify |
| 纪要成稿后查标点、格式、提法 | gongwen-review |
| 排成纪要格式的 Word | gongwen-format |
| 医院党委会、院长办公会议题（装有 gongwen-hospital 时） | gongwen-hospital |
| 国企“三重一大”议题、董事会议案和决议、总经理办公会纪要（装有 gongwen-soe 时） | gongwen-soe |
| 中小学教研活动记录、安全教育记录（装有 gongwen-k12 时） | gongwen-k12 |

行业包的转交规则：环境中装有上表行业包的（能看到该 skill，或交接卡路线中有它），表中这几类一律转交，不在本 skill 起草；党委会与总经理办公会记录在一起的，党委会纪要在本 skill 出，总经理办公会部分在起草说明中写明转交。没有装行业包的，本 skill 按单位画像和 `references/units.md` 对应小节照常处理，不拒绝。农村“四议两公开”中党员大会审议环节的记录由本 skill 整理。

能调用其他 skill 的环境直接调用；目标 skill 未安装或在网页环境的，按 `references/_shared/style/output-format.md` 第四部分转交：给交接卡、“新开对话粘贴 dist/prompts/<skill>.md 继续”的说明和安装命令。

不处理音频、视频。用户发来录音的，请用户先转成文字再发来，并说明收到文字后先拆议定事项梳理表、再出纪要或记录（教学模式讲明先后）；涉密或敏感会议的录音不要用联网转写工具。

## 开工检查

1. 保密（`references/_shared/guardrails.md` 第一条）：
   - 出现敏感信号时才在起草说明末尾提示一句，同一会话只说一次；材料带密级标识或“内部资料”“工作秘密”等标注的，立即停止，不复述、不摘录，告诉用户改用内网模型或删去相关内容后再发。
   - 出现身份证号、手机号、病案号、住院号、学号、住址、患者或学生、信访群众的真实姓名的，提醒脱敏；梳理表、记录、纪要一律改用“张某”“138****0000”，在起草说明“保密提示”中写明。
   - 涉及人事任免酝酿、纪律处分、未公开经营数据、投标报价的，不停止，在起草说明末尾提醒一次请用户确认允许在当前模型中处理。人事任免只记会议结论和程序，酝酿中的人选评价、考察反映、个人意见不进任何交付物（含一页纸、梳理表、纪要），只列议题和位置，起草说明写明未写入的原因。
2. 单位画像：工作目录有 `.gongwen/单位画像.md` 的先读，没有再找 `~/.gongwen/单位画像.md`；用户把画像贴在对话开头的按粘贴内容处理。再读 `references/_shared/profiles/units/` 下对应单位类型和 `references/units.md` 对应小节。没有画像时按 `references/_shared/profiles/roles.md` 第九节处理。
3. 定工作模式：

| 用户的话 | 模式 |
|---|---|
| “整理会议记录”“存档”“按发言顺序”“谁说的要对得上” | 记录 |
| “出纪要”“发给各科室”“印发”；只说“整理一下会议”、说不清用途的 | 纪要（起草说明写明记录与纪要的区别） |
| “上会材料”“议题”“三重一大”“党委会要研究” | 议题材料 |
| “督办”“列个表”“跟踪落实”“导成 Excel” | 督办清单 |

   纪要和督办清单常一起做；社区两委会议、居民会议按记录做。
4. 定角色模式：按 `references/_shared/profiles/roles.md` 第一节确定，本 skill 的差异见“角色适配”。党委（党组）会议、传达学习上级精神的议题叠加严谨模式。
5. 查材料，定首轮交付（`references/_shared/profiles/roles.md` 第十节）：有转写稿、笔记、记录本文字、议程或用户口述的会上内容之一的，任何模式都首轮直接成稿（纪要连同梳理表）。只在以下情形停下，回复开头说明属于哪种：只说开了会、没有任何会上内容的（情形②），只交纪要框架（会议概况和议定事项全部标【待补】）和“请补充的内容”清单，教学模式另用两三句讲清纪要（只记议定事项）与会议记录（按发言顺序记全过程）的区别；用户明确要先看一页纸或提纲的（情形③）；材料涉密的（情形④，按第1条）。
6. 以下要求不照办，说明原因，其余工作照常做（`references/_shared/guardrails.md` 第二条、第六条）：补写一次没有原始记录的会议的纪要或记录；把会上没定的事写进议定事项；倒签会议日期；在议题材料中写“已完成前置程序”却没有依据。教学模式下拒绝时同样讲清纪要与记录的区别。
7. 用户贴了交接卡的，按卡开工，卡上有的不再问（`references/_shared/style/output-format.md` 第四部分）。

## 工作流程一　会议纪要

### 第一步　任务卡

先填任务卡（高效模式只写进起草说明）：会议名称和类型、纪要用途（印发执行或存档）、发送范围、期号、角色模式；看不出的按默认值处理，写进所作假设，照常成稿。只问影响结构的事，最多 3 个，放在回复末尾，按此顺序取舍：纪要还是记录 → 党委会议还是行政会议（记录里看不出时）→ 发送范围。时间、地点、出席名单缺的不问，正文标【待补】。用户说“直接写”的不问。

### 第二步　议定事项梳理表

按 `references/decisions.md` 把记录拆成梳理表，列为 序号｜议题｜结论原话（位置）｜结论类型｜责任单位｜完成时限｜状态。
1. 判定“定了没有”：主持人作了结论性表态、记录写明表决结果或“会议同意”的才算定了。个人建议、“再看看”“回头再说”这类没有下一步的话、没有结论的讨论，结论类型记“未形成结论”，不进纪要正文，列入起草说明“未形成结论的事项”。
2. 结论类型按主持人原话归入同意、原则同意、暂缓、另行研究、退回修改、不同意、听取，不互换。当场附带调整的仍是同意，写“会议同意……，同时……”；原话有“原则上”“大方向可以”的才是原则同意。
3. 责任单位和时限只写记录中说到的。责任单位只取主持人原话点名或同段明确指代的，不按汇报单位、主管单位推定，未点名的正文不写，候选单位只放起草说明；“尽快”不改成日期，时限没说的不补，状态记“待补”。暂缓、另行研究的事项下指派了准备任务的（如“办公室先把车况摸清楚”），单列一行。
4. 转写存疑的数字、人名，梳理表状态记“待核实”；无单位的大数、带“点”的口语数字（如“一点五亿”）原词照录，不补转写稿没有的计量单位（如“元”）。

### 第三步　成稿

按 `references/minutes-writing.md` 写：
1. 结构按会议类型：例会按议题分列，专题会一条主线，协调会写清各方责任边界，座谈会归纳观点。
2. 标题下一行写期号（用户给了的）；导语一段写时间、地点、主持人、会议、议题，缺的标【待补】，不写背景意义；导语后另起一行按“出席：×××、×××；列席：×××；请假：×××”列完整名单（没有列席、请假的省略该项）。记录只写“周四”“上周”的，按今天推算为会议日期。
3. 提示语对号入座：认为、指出、强调、要求、议定的内容都要在记录里找得到；记录里没有的不补“会议强调”段。
   - 误：会议强调，各部门要提高政治站位，确保各项任务落地见效。（记录中没有）
   - 正：删去；主持人确有强调的，照原意写。
4. 议定事项一条一事：结论词＋事项＋责任单位＋时限。原则同意写出修改要求；暂缓写出原因或再议条件。
   - 误：会议同意档案室改造方案。（主持人原话“原则上同意，消防那块后勤科再找设计单位看看”）
   - 正：会议原则同意档案室改造方案，由后勤科会同设计单位完善消防设计。
5. 口语转书面只改说法，不改数字、主体、条件、态度强弱；记录中加引号的做法名称、本单位提法照写。
6. 默认做法：名单列在开头（导语后），正文后不再重复；名单只用用户给的，没有的写“出席：【待补：出席人员名单】”。GB/T 9704-2012 10.3 的文末名单写法可由用户指定改用，二选一，不两处并列。纪要只写议定事项和必要的会议情况；个人保留意见、不同意见只在会议明确要求记录时写入。记录有冲突、转写存疑的，正文照原词写，列入起草说明。党委会和行政会议的内容分成两份纪要。
7. 会上定的事与法规或上级规定明显冲突的（如决定收取未经批准的费用、要求基层每天报送工作照片），纪要不替会议改结论，照记录写，在起草说明“程序风险提示”中写明依据，建议会议重新研究。

### 第四步　自检

1. 逐条对账：纪要中每条议定事项都能在梳理表找到“已明确”的结论；正文的每个数字、日期、文件名都能在记录中找到。有 Python 时运行 `python scripts/fact_diff.py 原始记录.txt 正文.txt --ledger`，把“正文中有、台账中没有”的数字、日期、书名号逐条改为记录中的说法或删去。
2. 议定事项检查：`python scripts/minutes_check.py 正文.txt`，报出缺责任单位、缺时限、原则同意未写修改要求、暂缓未写条件、口语残留的条目，记录没说的缺项不补，列入起草说明待补；做了督办清单的加 `--list 督办清单.md` 对账，牵头与配合颠倒、时限挂到其他任务上都会报出。
3. 机检：`python scripts/gongwen_lint.py 正文.txt --doc-type 纪要`（记录、议题材料分别用 `会议记录`、`议题材料`，引擎只提示不报错）。P0 必改，P1 逐条判断，命中公文白名单的保留（`references/_shared/style/ai-tone.md` 第二部分）。ELM 要素缺失的，能确定的补写，不能确定的标【待补】；EVD 强评价缺数据的，补用户材料中的数据或改用不带强评价的写法，不得编造数据。
4. 不能运行脚本的，按本文“自检清单”逐项人工检查，起草说明写“未运行机检，已按人工清单检查”。

### 第五步　交付

1. 能写文件的：在当前工作目录建 `公文/<YYYYMMDD>-<简短标题>/`，写入 `正文.txt`、`议定事项梳理表.md`；用户粘贴的记录先把身份证号、手机号、病案号和患者、学生、群众的姓名换成代称（其他数字和日期不动），再存为 `原始记录.txt` 供对账，起草说明保密提示写明保存位置；有督办清单的另写 `督办清单.md`（和 xlsx）。对话中给出文件位置、议定事项几条和起草说明。
2. 网页环境：按 `references/_shared/style/output-format.md` 第三部分输出，梳理表、督办清单放在起草说明末尾，标题为“附：议定事项梳理表”“附：督办清单”。路线还有下一站（如 review、format）的，按第四部分输出更新后的交接卡和新开对话的说明；下一站是行业包、要接着起草另一部分的（如总经理办公会纪要），请用户同时粘贴该部分记录。
3. 起草说明只在对话中给出，不超过 5 行、每行一句：假设、待补（含记录没说的责任单位和时限）、待核实各一行，未形成结论的事项、程序风险提示（仍写依据）、修改说明、保密提示并入其余行；教学模式另附写作要点。回复中不写 skill 名，用描述性说法。

## 工作流程二　会议记录

按 `references/meeting-record.md` 整理：
1. 记录头写会议名称、时间、地点、主持人、出席、列席、缺席、记录人、议题，缺的标时间、地点、出席名单【待补】，其余缺项不写，汇总进起草说明。
2. 默认摘要记录：按议程和发言顺序，每人保留观点、理由、条件、数字；用户要“详细”的保留原句顺序，只删语气词。
3. 发言人对不上的保留“发言人1”之类的原标签，不按内容猜，起草说明待核实一行写明。
4. 不同意见、表决结果如实记录；转写存疑的（含无单位的大数、带“点”的口语数字）原词照录，不补转写稿没有的单位，起草说明待核实一行汇总。
5. 交付 `正文-会议记录.txt`；同时要纪要的，再按工作流程一出 `正文-纪要.txt`，共用一份梳理表。

## 工作流程三　上会议题材料

按 `references/agenda-material.md` 写：
1. 一题一议。结构：议题名称、汇报单位、会签部门意见、基本情况和依据、方案比较、需会议决策的事项、前置程序完成情况、附件。
2. 方案比较在正文中用“（一）方案一。……”分项写，不用表格；投入、周期、效果、风险、合规性只写材料里有的，没说的不写，关键项（如投入测算）缺了才标【待补】，不写“材料未提供”。风险高低、是否合规不由本 skill 判断。只有一个方案的不编第二个，可以与“维持现状”对照，起草说明提示补充备选方案。
3. 推荐意见只写汇报单位或用户给出的倾向和理由，照写，不改成两头都说的平衡话；材料没有的，写【待补：汇报单位推荐意见及理由】，不替汇报单位选方案（正误对照见 `references/agenda-material.md` 第二部分）。
4. 需决策事项写成能回答“同意或不同意”的句子：审议什么、同意列支多少、明确谁牵头。
5. 前置程序按单位类型逐项核对（`references/agenda-material.md` 第三部分，本单位议事规则优先），正文用“1. 公众参与：……”分项写，只写用户提供的完成情况：说了没做的写“未开展”“审查意见尚未出具”，没说的不写，不写成“已完成”。未经集体决策、前置程序未完成、准备先执行后补程序的，写进起草说明“程序风险提示”（`references/agenda-material.md` 第四部分）。对照表作起草说明附表。
6. 篇幅一般 1500～3000 字（工具约定），用户指定字数的按“输出规范”篇幅条；`--doc-type 议题材料` 机检后交付 `正文-议题材料.txt`。

## 工作流程四　督办清单

按 `references/supervision-list.md` 做：
1. 只从纪要取。列为 序号｜议定事项｜纪要位置｜责任单位｜配合单位｜完成时限｜办理状态｜备注。暂缓、不同意、只听取汇报的不进清单；暂缓、另行研究事项下有明确责任单位的准备任务（测算、补充材料），单列一行，议定事项栏写纪要原话。
2. 责任单位和时限逐字照纪要，纪要没写的，清单该格标【待补】。有 Python 时可运行 `python scripts/minutes_check.py 正文.txt --emit-list 督办清单.md` 生成草表，再逐行核对。
3. 新建清单状态一律“待办理”。更新进展时只改用户提供了进展的行，没有办结依据的不写“已办结”。
4. 转 Excel 按 `references/supervision-list.md` 第四部分运行 `scripts/md2xlsx.py`；不能运行或未生成文件的，交付 Markdown 表格。

## 输出规范

- 纪要、记录、议题材料的正文按 `references/_shared/style/output-format.md` 第一部分：纯文本，层次序数 一、（一）1.（1），数字按 GB/T 15835。
- 正文不出现【待核实】；【待补】只用于必须由用户提供的要素（时间、地点、出席名单、关键方案数据等），全篇一般不超过 3 处；记录没说的责任单位、时限等其余缺项不补不标，汇总进起草说明待补一行。程序风险、未形成结论的事项都写在起草说明里。
- 梳理表、督办清单、方案比较表、前置程序核对表可以用表格，只放在起草说明附表或单独文件中，正文不放表格。
- 篇幅：用户指定字数的，按 `references/_shared/guardrails.md` 第四条第2款以±10%为目标；素材撑不起的，纪要、记录只整理不添加，不补会上没有的内容、不为凑字数补段落，起草说明一句话说明篇幅差距，可附不超过 3 条补料建议；【待补】不计入字数。

## 自检清单

- [ ] 要素行按文种齐全并写在正文里（不放进起草说明）：标题、主送机关、落款、成文日期、附件说明；请示、报告另有发文字号、签发人。
- [ ] 每条议定事项都能在记录中找到主持人或会议的结论原话；个人建议、未定事项没有写成议定事项，已列入起草说明。
- [ ] 同意、原则同意、暂缓、另行研究没有混用；原则同意写了修改要求，暂缓写了原因或条件，会上没说的没有替会议补。
- [ ] 责任单位和时限都是原话点名的，没说的没有补，已列入起草说明；“尽快”没有被改成具体日期。
- [ ] 会议日期只给了星期几或“上周”的，已按今天推算；“月底前”等时限原样保留。
- [ ] 用户材料中加引号的做法名称、本单位提法原样保留；确需改写的已列入提法核对清单请用户确认。
- [ ] “会议认为”“会议强调”“会议要求”的内容都来自记录，没有凑格式的套话。
- [ ] 正文的数字、日期、文件名都能在记录中找到；转写存疑的已列入起草说明。
- [ ] 会议记录中发言归属与原标签一致，不同意见和表决结果没有删改。
- [ ] 议题材料只有一个方案时没有编第二个；推荐意见、风险、合规性只写材料里有的，材料没说的没有补，正文没有“材料未提供”这类话；前置程序只写了用户提供的完成情况，风险已写进起草说明；正文没有表格。
- [ ] 督办清单的事项、责任单位、时限与纪要逐条一致，没有纪要以外的事项。
- [ ] 党委会和行政会议的内容分开；患者、学生、群众已用代称，号码已脱敏。
- [ ] 用户指定字数的，篇幅在目标±10%内，或已在起草说明说明差距。
- [ ] 正文没有 Markdown、免责声明、AI 自述和【待核实】，【待补】不超过 3 处；起草说明不超过 5 行，待补、待核实各汇总一行。

## 角色适配

- 教学模式：梳理表、纪要和写作要点首轮一次交付；写作要点写纪要的结构安排（当作提纲说明）、纪要与记录的区别、本稿提示语为什么这样用、原则同意与同意的区别（用本稿一处正误对照）。
- 高效模式：梳理表、纪要、督办清单一次交付；对话中只报条数和文件位置；起草说明不展开讲解，程序风险提示每条仍写问题类型和依据条款，一条一行；多次会议的记录可以批量整理，每次会议一份纪要。
- 转译模式：接受零散笔记和口述；提问只问事实，如“这件事会上谁拍的板”“说没说时限”；梳理表的位置写到笔记段落；业务术语照用。
- 审稿模式分两种。一页纸：领导明确要先过目的（开工检查第5条情形③），先交议定事项每条一句、未形成结论的事项（只写议题和位置）、需要拍板的待确认点（责任不清、时限未说），不写人选评价、考察反映和个人意见，确认后再出正式纪要。纪要对照：拿已写好的纪要和记录来对照的，只列“纪要与记录不一致”清单（位置、纪要原文、记录原话、问题、建议），不重写；标点格式类问题建议另行核稿。
- 严谨模式：党委（党组）会议纪要、传达学习上级精神的议题、对外公开的会议信息，上级精神的名称和表述只用记录和用户提供的原文，缺的照记录原话写，起草说明请对照原文；附提法核对清单（提法、位置、出处、是否已对照原文）。
