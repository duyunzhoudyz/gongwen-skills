# 输出格式规范

所有 gongwen skill 的输出都遵守本规范。目的是让输出既能直接阅读，也能直接交给 gongwen-format 排版，还能被 gongwen_lint.py 检查。

## 一、正文

1. **纯文本公文体**。不使用 Markdown：不用 `#` 标题、`**加粗**`、`-` 或 `*` 列表、`>` 引用、代码块。用户明确要求表格时可以给表格，交付 Word 时由 gongwen-format 转换（只支持简单管道表格）。
2. **层次序数**依次为：`一、` → `（一）` → `1.` → `（1）`。不跳级。
   - `一、` 后面用顿号；`（一）` 和 `（1）` 后面不加任何标点；`1.` 用阿拉伯数字加下脚点（GB/T 15834-2011 附录 B.3）。
   - 不用“第一，”“首先”“其次”“最后”作为层级标记。段内列举可以用“一是……二是……”。
3. **标题行**：一级标题独占一行，末尾不加标点。二、三、四级标题可以独占一行（末尾不加标点），也可以和正文同段，这时标题末尾用句号，例如“（一）强化组织领导。成立工作专班……”。一级标题必须独占一行（带句号的“一、……。”无法与正文句区分）；同段写的，排版时按正文处理，不加黑体。
4. **段落**：一段一行，段与段之间空一行。不用空格做首行缩进，缩进由排版统一处理。
5. **标点**：中文语境一律用全角标点；引号用 “ ” 和 ‘ ’；书名号、顿号、破折号按 GB/T 15834-2011 使用。
6. **数字**：按 GB/T 15835-2011。计量、统计数据用阿拉伯数字；概数、惯用语用汉字；年份不简写；数值范围写全单位，如“9亿～16亿”“15%～30%”。
7. **公文标题**：一般由发文机关名称、事由和文种组成，事由一般以“关于”开头。标题末尾不加标点；标题中除法规、规章和规范性文件名称加书名号外，一般不用标点，并列词语之间可用顿号（如“元旦、春节期间”），年份范围等括注可用括号（如“（2026—2028年）”）。
8. **标记**：必须由用户提供、又无法从上下文确定的要素写 `【待补：说明】`，需要核实的写 `【待核实：说明】`，全角方括号、全角冒号，冒号后写清缺什么。

## 二、起草说明

正文之后另起一行，单独写 `【起草说明】`，按需写以下几部分，没有内容的省略，省略后按实际顺序重新编号（一、二、三……），不跳号。例：只有假设和修改说明时写“一、所作假设”“二、修改说明”。

```text
【起草说明】
一、所作假设
1. 未说明行文方向，按下行文处理。
二、待补事项
1. 第二部分第 3 段：专项检查次数。
三、待核实事项
1. 第一部分引用的会议精神表述，请对照会议通知原文。
四、修改说明
1. ……
五、保密提示
1. ……
六、写作要点（仅教学模式）
1. 为什么选这个文种、这样搭结构，哪些地方是这类文书的常见失误。
```

可选部分：“未形成结论的事项”“程序风险提示”（gongwen-minutes、gongwen-soe 使用），放在“待核实事项”之后、“修改说明”之前。

需要附表时（如口径冲突表、提法核对清单、填写指引、素材台账），在起草说明末尾另起一行写“附：表名”，再给出表格。起草说明不进正文，可以使用表格。

脚本以 `【起草说明】` 这一行为界：之前是正文，之后不参与排版和机检。

回复顺序：正文、`【起草说明】`、更新后的交接卡（有下一站时）、提问。提问只限影响成稿的事项，最多 3 个；高效模式把问题并入起草说明的“待核实事项”，不另设提问段。

## 三、交付方式

**能写文件的 Agent 工具**（Claude Code、Codex、Cursor 等）：在当前工作目录下建 `公文/<YYYYMMDD>-<简短标题>/`，按需写入：

| 文件 | 内容 |
|---|---|
| `正文.txt` | 只含正文 |
| `起草说明.md` | 起草说明 |
| `素材台账.md` | 事实、数据、案例及其来源 |
| `提纲.md` | 提纲与标题备选 |
| `标题方案.md` | gongwen-title 的标题备选与一致性检查结果 |
| `原稿.txt` | 改稿类 skill 保存的用户原稿，供 fact_diff.py 比对 |
| `文风问题清单.md` | gongwen-humanize、gongwen-direct 只标注不改时的问题清单 |
| `核稿意见.md`、`核稿意见.json` | gongwen-review 的问题清单 |
| `成稿.docx` | gongwen-format 的排版成品 |
| `要点表.md`、`任务分解表.md`（可另出 .xlsx）、`上级文件.txt` | gongwen-implement；`上级文件.txt` 是比对用工作副本，写入前删去联系人行 |
| `整改台账.md`（可另出 .xlsx）、`对账意见.md` | gongwen-rectify |
| `议定事项梳理表.md`、`督办清单.md`（可另出 .xlsx）、`原始记录.txt` | gongwen-minutes；`原始记录.txt` 存档前脱敏 |
| `计算底稿.md`、`体检报告.md` | gongwen-data |

一份素材出多个版本时，正文文件名加版本名，如 `正文-单位总结.txt`。同名文件已存在时加后缀 `-v2`、`-v3`，不覆盖用户已有文件。写完后在对话中告诉用户文件位置，并给出正文的简要概述，不必整篇重复；对话回复同样不写过程说明。

**网页对话环境**（无文件系统）：在回复中依次输出正文、`【起草说明】`。回复开头直接是正文；只有停在提纲时，开头先用一句话说明属于哪种情形（`references/_shared/profiles/roles.md` 第十节）；不加“以下是……”之类的引导语，保密提醒放在起草说明末尾一句（`references/_shared/guardrails.md` 第一条第1款）。起草说明一般不超过 5 条要点，待补、待核实汇总成一行列表，不写过程说明。

## 四、交接卡与转交

### （一）转交与未安装兜底

1. 能调用其他 skill 且目标 skill 已安装的环境，直接调用，不需要交接卡。
2. 目标 skill 未安装，或在网页环境的，同时给出三样：（1）交接卡；（2）说明“可以新开对话，先粘贴 `dist/prompts/<skill 名>.md` 全文，再粘贴交接卡和材料继续”；（3）安装命令：Claude Code 为 `/plugin marketplace add duyunzhoudyz/gongwen-skills` 和 `/plugin install gongwen@gongwen-skills`（行业包把 gongwen 换成包名，如 gongwen-hospital），其他工具为 `npx skills add duyunzhoudyz/gongwen-skills`。不用不对口的 skill 代写。请用户准备素材的，同时提醒先删去素材里的姓名、学号、成绩、家庭情况等个人信息。
3. 用户在 Agent 环境里贴了交接卡的，同样按卡开工，本站完成后输出更新后的交接卡。


### （二）交接卡

网页版一次只加载一个 skill 的提示词。用户粘贴了总入口给出的交接卡时，按交接卡理解任务背景、当前模式和已确认事项，不再重复提问。本站完成后，如果路线还有下一站，在起草说明之后输出更新后的交接卡，并告诉用户：新开一个对话，先粘贴下一站的提示词文件（`dist/prompts/<skill 名>.md`），再粘贴交接卡和本站产出。

```text
【交接卡】
单位画像：（粘贴画像全文；没有写“无”）
单位类型：医院；科室；护士长（推断），未提供画像
当前模式：转译模式
任务：科室2026年工作总结，上行文，报医院
路线：report（台账、提纲）→ title → report（成稿）→ direct → humanize → review → format
本站：第3站 gongwen-report，成稿
已确认：按科室名义；篇幅不超过3000字
本站产出：总标题“某科室2026年工作总结”（推荐，待确认）；一级标题：一、主要工作成效；二、存在的不足；三、2027年工作思路（推荐，待确认）
请准备：上一站的提纲和素材台账
```

交接卡只写任务信息，不抄录原始材料，不带敏感信息。

- “单位类型”必填：有画像的，与画像一致；没有画像的，按用户所述推断，写类型、层级、岗位（知道多少写多少），标“（推断）”，并注明“未提供画像”。没有画像时单位类型仍必填，不单写“无”。
- “已确认”只写用户确认过的任务信息（模式、体裁、篇幅、名义等）；本站的假设和判断写进起草说明的“所作假设”，不抄材料内容和数据，不放进“已确认”。
- “本站产出”写输出这张卡的站（刚完成的一站）留给下一站必须接着用的结果，例如标题站写推荐的总标题和各级小标题全文，并注明“推荐，待确认”；不写“见本站产出”。数据、待核实事项随正文和起草说明带走，不进交接卡。没有需要带入下一站的结果时，这一行写“无”。

误：已确认：标题“某区对经营户实行三色管理”；整改状态均为未启动。本站产出：见本站产出，待用户选定。
正：已确认：按经验类写；不超过600字。本站产出：总标题“某区对经营户实行三色管理”（推荐，待确认）；一级标题：一、主要做法；二、初步成效；三、下一步打算（推荐，待确认）。
