# 示例

三个端到端示例，按各 skill 的 SKILL.md 逐步执行得到。单位、人名、数据全部虚构；与评测材料重合的数字和日期已换掉，以 `tools/validate.py --eval-overlap` 为准。每个目录里的 `过程记录.md` 写明每一步问了用户什么、运行了哪条命令、脚本输出了什么。

几点约定：
- 示例按现行规则生成（2026年10月下旬）：总入口 gongwen 只判断文种、规划路线并转交，不起草；起草类 skill 在核心事实够用时首轮直接出稿，提问放在回复末尾；篇幅服从用户要求，素材不够时用文种常规的工作性表述补足，不新增事实、不注水。
- 运行环境按 Claude Code、22 个 skill 全部安装处理，目标 skill 直接调用，所以没有交接卡。网页提示词版一次只加载一个 skill，需要转交时按 `shared/style/output-format.md` 第四部分给交接卡、提示词说明和安装命令。
- 示例目录里的文件，对应对话中写入 `公文/<YYYYMMDD>-<简短标题>/` 的文件，这里去掉了日期目录一层。
- `.txt` 正文文件中，单独一行的【起草说明】之后是说明内容，机检和排版脚本读到这一行即停止。
- docx 内写的是标准字体名（仿宋_GB2312、方正小标宋简体等），在装有这些字体的电脑上打开显示正常。仓库不附带字体文件。
- 起草说明（假设、待补、待核实、修改说明，不超过5行）只在对话回复中给出，不单独存成文件，所以示例里没有 `起草说明.md`；各轮回复原文（含起草说明）写在 `过程记录.md`。
- 正文里不出现【待核实】，核实事项只写进起草说明的“待核实”一行；【待补】只留给缺了文书就不成立的要素，一般不超过3处。机检把【待补】计为 P2，提醒定稿前补齐。
- 成文日期用户没给的，写到年月、日留空（如“2026年12月　日”），由签发人按签发日填写，不替用户定日期。
- 下列机检数字为用当前版本脚本重跑的结果（2026年10月）。

## A　医院科室年终总结（转译模式）

- 输入：心内科科秘书的口语化工作记录（约730字，含1名患者的姓名和住院号）和一张指标表（缺2026年CMI、次均住院费用、上年同期平均住院日）；用户要求2000字左右。
- 步骤：gongwen-report 首轮一次交付素材台账、提纲和正文，回复里给出5行起草说明 → gongwen-title 出三套小标题方案并替换 → gongwen-format 排成材料版式 → fact_diff 台账对账。
- 效果：正文约1890字，落在2000字左右的目标区间内（1800～2200字）。材料里的事实和算出的数只够写约1300字，其余约600字用总结的常规工作性表述补足（各部分导语、术语简释、小结句、问题与打算的呼应句），没有新增事实，问题段没有自拟措施，也没有为凑字数补写下一步计划。台账60条，每个数字都标了出处；正文只有2处【待补】（CMI和次均住院费用、急诊PCI门球时间实际值），没有【待核实】；左心耳封堵“大概20来台”写“约20台”，复审通知文号等存疑事项只在起草说明的“待核实”一行；患者信息改为“张某”，住院号不写；成文日期写“2026年12月　日”，留给签发人填。机检 P0、P1 均为0，P2 2处就是那2处待补标记；check_docx P0、P1 均为0，P2 2项同为待补提醒；台账对账只列出新加的标记、结构用数和成文年月，没有台账以外的统计数据。
- 文件：`输入-心内科2026年工作记录.txt`、`输入-心内科主要指标表.csv`、`素材台账.md`、`提纲.md`、`正文.txt`、`标题方案.md`、`成稿.docx`、`过程记录.md`

## B　AI 稿体检（高效模式）

- 输入：一篇模拟 AI 起草的区教育局冬季校园安全检查通知，含段首评论语、“不是……而是……”、破折号、新八股词、Markdown 加粗、结尾号召，“建议各学校”“以上内容仅供参考”，发文字号“[2026]第12号”、日期虚位、序号“1、”、“3～5万元”，以及对家长“一律移交公安机关予以拘留”。
- 步骤：gongwen-direct → gongwen-humanize → gongwen-review（出核稿意见，再按 P0、P1 直接改）→ gongwen-format（红头成稿；送审稿加批注）。每一步都用 fact_diff 比对；各步骤的修改说明只在回复中给出，不附在文稿文件末尾。
- 效果：机检从 P0 5处、P1 31处、P2 2处降到全部为0；篇幅从1092字压到814字，所有数值未变。核稿意见8条（P0 3条、P1 3条、P2 2条），拘留表述核实后定为 P0 删去，没有补写替代要求，请用户决定。check_docx P0、P1、P2 均为0；8条核稿意见全部写成 Word 批注。
- 文件：`原稿.txt`、`1-direct改稿.txt`、`2-humanize改稿.txt`、`3-核稿意见.md`、`3-核稿意见.json`、`4-核改稿.txt`、`5-版式信息.json`、`5-成稿.docx`、`6-送审稿-批注.docx`、`前后对比.md`、`过程记录.md`

## C　文种判断：申请经费用函（教学模式）

- 输入：用户一句话，“我刚到区教育局办公室，领导让我写个东西报给区财政局，申请追加80万元校舍维修经费，该怎么写？”
- 步骤：gongwen 识别单位、角色、文种、行文方向四个维度，初判为函并转交 gongwen-draft（总入口不起草）→ gongwen-draft 首轮直接出稿，回复末尾提3个问题 → 用户补素材后，在原稿上修改 → 机检 → 总入口建简版画像 → gongwen-format 排成信函格式。
- 效果：区教育局与区财政局不相隶属，请求批准用函，标题写“关于商请……的函”，不写“关于申请……的请示”（《党政机关公文处理工作条例》第八条第（十四）项）。首轮稿只有结构和2处【待补】（维修项目及原因、联系人和电话），年初预算、资金渠道、附件这些素材缺的内容不用占位，改在回复末尾提问；补素材后改成终稿，只剩1处【待补】（联系电话）。三个项目预算合计与申请金额核对一致，用户说的“二小”“五小”“计财科”保留原称，不自行补全称，请用户核对。教学模式的写作要点附在回复里。机检（gongwen_lint、draft_check）终稿 P0、P1 均为0，P2 1处为待补标记；check_docx P0、P1 均为0，P2 1项为联系电话待补提醒；发文字号用户没给，成稿里不写占位，由用户领取后填。
- 文件：`正文.txt`、`版式信息.json`、`成稿.docx`、`过程记录.md`
