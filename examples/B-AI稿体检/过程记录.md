# 过程记录：AI 稿体检

> 本记录中的机检数字和脚本输出，是用当前版本脚本重跑的结果（2026年10月）。

路线：gongwen-direct → gongwen-humanize → gongwen-review（出核稿意见，再“直接改”）→ gongwen-format（红头成稿；送审稿加批注）

对应路线表 R12（AI 稿体检）加 R15（核稿意见写成批注）。原稿为模拟的 AI 起草稿，单位、人名、数据均为虚构。示例场景中的“今天”按稿中成文日期，即 2026年10月7日。

## 第1轮　用户提交原稿

> 用户：这是用 AI 写的冬季校园安全检查通知，读着一股 AI 味，口气也软。直接帮我改，今天要发，别解释太多。（附 原稿.txt）

模型：稿件中没有个人敏感信息，也没有“内部”“不公开”等字样，`secret_check.py` 无命中，不出保密提示。
> 判断：通知（下行文）｜区教育局，按基层（县〔市、区〕部门）处理｜高效模式（“直接改”“别解释太多”）｜路线：direct → humanize → review → format

改稿前先跑一次全量机检留底：`python scripts/gongwen_lint.py 原稿.txt --doc-type 通知`，P0 5处、P1 31处、P2 2处，正文1092字。

## 第2步　gongwen-direct（去防御腔）

1. 诊断：`gongwen_lint.py 原稿.txt --doc-type 通知 --checks defensive,residue --json`，P0 2处（免责句“以上内容仅供参考，请各学校结合实际情况调整”命中两条规则），P1 6处（加粗符号4处、“建议各学校”、“可以考虑”）。
2. 改写：删免责句1处；“建议各学校成立”“可以考虑通过”改为“要”2处；去掉加粗符号4处。“各学校可安排……经费”的“可”是授权，保留。拘留表述属法律依据问题，原稿已有的强制措施不删不改，列入转交。
3. 复检：`fact_diff.py 原稿.txt 1-direct改稿.txt` 无差异；`--checks defensive,residue` 复检 P0、P1、P2 均为0；全量机检 P0 3处、P1 25处、P2 2处，剩下的是 AI 腔、格式和数字问题，属转交事项。
4. 产出：1-direct改稿.txt（只含正文，不带起草说明）。

模型回复（开头直接贴改后全文，之后是起草说明）：

```text
【起草说明】
假设：按通知（下行文）、基层教育行政部门、高效模式处理。
修改：删免责句1处；“建议各学校成立”“可以考虑通过”改为“要”2处；去掉加粗符号4处；“各学校可安排……经费”的“可”是授权，保留。
转交：AI 句式8处和“打造”“赋能”“闭环”过密，发文字号、日期虚位、序号“1、”、“3～5万元”等格式数字问题，以及第四部分对家长“一律移交公安机关予以拘留”的法律依据问题，建议再去 AI 腔、再核稿。
待核实：原稿由 AI 生成，其中的数字、日期和检查安排请对照原始材料确认，本次改稿未核实真伪。
事实核对：数字、日期、发文字号均无差异。
```

## 第3步　gongwen-humanize（去 AI 腔）

1. 诊断：`gongwen_lint.py 1-direct改稿.txt --doc-type 通知 --checks style,residue`，P1 8处（段首评论语2处、破折号过密、“不是……而是……”、“拉通”“颗粒度”、结尾总结标签、号召式收尾），P2 1处（“赋能”“打造”“闭环”过密）。人工另查出：首段“随着冬季的到来……具有十分重要的意义”是宏大开头，第一部分小标题是口号式“重要意义”，两句“底线和生命线”“关键防线”是空泛总括、拔高句。
2. 改写（改写优先于删除，标题也要改）：评论语、翻案句、破折号句改成直接陈述；“打造”“赋能”“拉通”“颗粒度”换成实义动词；首段铺垫句和两句口号式意义表述没有事实和措施，删去；小标题“充分认识冬季校园安全检查的重要意义”改为“总体要求”；“以下几个方面”写明为“以下四个方面”；结尾复述和号召段整段是口号，删去；“闭环管理”属安全管理用语，保留一处。不插【待补】。
3. 复检：style、residue 两类 P1、P2 清零；`change_guard.py 1-direct改稿.txt 2-humanize改稿.txt --strict`：P0、P1 为0，P2 3处（小标题改写、“四个方面”、新增小标题，均已在说明中交代）；`fact_diff.py` 无事实差异，另提示1项“可能是序数或概数”，即新写的“四个方面”，与下列四项一致。篇幅853字，为上一稿1050字的81%，低于85%，逐项核对删去的都是口号和复述，事实与措施一项未少。
4. 产出：2-humanize改稿.txt（只含正文，即送审稿）。

模型回复（开头直接贴改后全文，之后是起草说明）：

```text
【起草说明】
修改：按通知、全文改写处理，共12处，例：“拉通……数据”改为“打通……数据”，“细化检查颗粒度”改为“细化检查内容”，“值得注意的是，部分学校……”改为“部分学校……”；第一部分小标题“充分认识……重要意义”改为“总体要求”。
删去：首段“随着冬季的到来……具有十分重要的意义”、两句口号式意义表述（“底线和生命线”“关键防线”）和结尾复述号召段，均无事实和措施；“以下几个方面”写明为“四个方面”。
保留：“闭环管理”用于隐患发现到销号的全流程，属安全管理用语，保留1处；改后853字，为上一稿的81%，少的都是口号和复述，事实与措施未少。
转交：发文字号、日期虚位、序号“1、”、“3～5万元”等格式数字问题，以及第四部分的拘留表述，建议再核稿。
事实核对：未发现差异；另有1项“四个方面”属表达调整，与下列四项一致。
```

## 第4步　gongwen-review（核稿，再直接改）

> 用户：再帮我从头核一遍，出个意见，我要拿给科长看。

1. 保密与隐私扫描：`gongwen_lint.py 2-humanize改稿.txt --checks privacy --json` 无命中。
2. 机检：`gongwen_lint.py 2-humanize改稿.txt --doc-type 通知 --json`，P0 3处、P1 16处、P2 1处。首段铺垫、“重要意义”小节已在上一步改掉，这一轮不再出现。
3. 八关审读后定级：P0 3条（发文字号、拘留表述、成文日期虚位），P1 3条，P2 2条，共8条。同一发文字号被 FMT-001、FMT-003 两条规则命中，合并为1条；12处“1、”（序数标点和越级）合并为1条；LEG-001 核实后由 P1 升为 P0；NUM-002 的“3～5万元”、2处日期虚位各列1条；联合检查组涉及其他部门职权（程序关）和联系人缺联系电话（文字关）按 P2 列出，由用户判断。
4. 产出：3-核稿意见.md、3-核稿意见.json。JSON 8条与 md 一一对应、顺序相同，每条 excerpt 都逐字取自送审稿，并在写入前检查过能唯一定位。

模型回复（对话中只报条数、最关键的几条和文件位置）：

```text
P0 3条：发文字号写法不对；第四部分对家长“一律移交公安机关予以拘留”，区教育局没有这项权限，必须删；成文日期编了虚位。另有 P1 3条、P2 2条。意见在 3-核稿意见.md，批注用 JSON 在 3-核稿意见.json。需要写成 Word 批注的可以继续让我处理。
```

> 用户：按 P0、P1 直接改吧，P2 我自己定。

5. 直接改：只改 P0、P1 共6条。删去标题下发文字号行，排版时写入版头；删去拘留表述，没有补写替代要求；成文日期和正文2处日期去虚位，只改写法，取值未动；“3～5万元”改为“3万～5万元”；12处“1、”依次改为“（一）（二）……”。P2 两条未改。
6. 复检：`change_guard.py 2-humanize改稿.txt 4-核改稿.txt`：CHG-001 仅1项，是发文字号移出正文，对应第1条；其余改动都有规则依据。`fact_diff.py` 差异1项，同为发文字号移出正文，日期去虚位、“3万～5万元”的写法已归一，数值未变。全量机检 P0、P1、P2 均为0，正文814字。
7. 产出：4-核改稿.txt（只含正文）。

模型回复（开头直接贴改后全文，之后是起草说明）：

```text
【起草说明】
修改：按核稿意见第1～6条改：删去标题下的发文字号行，排版时以“某区教发〔2026〕12号”写入版头；删去对家长“一律移交公安机关予以拘留”一句；成文日期和正文2处日期去掉虚位，只改写法，日期取值未动；“3～5万元”改为“3万～5万元”；12处“1、”依次改为“（一）（二）……”。
未改：第7、8条（P2）由您决定，即联合检查组是否已征求区应急管理局、区市场监管局意见，联系人后是否补联系电话。
待确认：第四部分第2项删去拘留表述后没有补写替代要求，如需对校门口停车提出要求，请告诉我具体做法。
事实核对：差异1项，是发文字号移出正文；日期去虚位和数值范围写法已归一，数值未变。
```

按路线表规则，review 之后、format 之前停下，等用户确认定稿：

> 用户：定稿了，套红头。印发机关是局办公室，今天印发。

## 第5步　gongwen-format（红头成稿和批注版）

1. 整理 5-版式信息.json：版式红头，发文机关标志“某区教育局文件”，发文字号按核稿意见改为“某区教发〔2026〕12号”，加盖印章，印发机关“某区教育局办公室”，印发日期按“今天”写为2026-10-07（脚本输出为“2026年10月7日”）。签发人、抄送、附件稿中没有，不写。
2. `build_docx.py 4-核改稿.txt --meta 5-版式信息.json -o 5-成稿.docx`：标题、主送、一级标题4段、二级标题12段、署名、成文日期均识别正确，标题自动分两行。回读检查 P0、P1、P2 均为0。
3. `check_docx.py 5-成稿.docx --strict`：P0 0项、P1 0项、P2 0项，可以交付。
4. 字体：本机缺仿宋_GB2312、楷体_GB2312、方正小标宋简体三款标准字体（`gw_fonts.py` 复查结果相同）。文档内写的是标准字体名，不用任何替代字体，也不打包字体；回复开头先告知用户本机打开看到的不是正式效果，请自行下载安装后重新打开核对，仿宋_GB2312、楷体_GB2312 向单位信息中心或办公室索取，方正小标宋简体是商业字体，使用需单位授权。
5. 批注版：核稿意见的 excerpt 取自送审稿，在终稿里已经改掉，直接批注到成稿上只能定位到2条（两条 P2），其余6条未定位。因此先把送审稿按同样的红头版式排成 docx（版式信息与成稿相同，只是不填发文字号），再运行 `annotate_docx.py 送审稿.docx 3-核稿意见.json`，8条全部定位，输出 6-送审稿-批注.docx。送审稿的发文字号写在标题下，build_docx 把它认作发文字号，移到版头，仍是“[2026]第12号”的原写法，批注第1条就挂在版头的这个文号上。送审稿 docx 本身是中间文件，不单独保存。

模型回复：

```text
【字体缺失】本机缺仿宋_GB2312、楷体_GB2312、方正小标宋简体。文件里写的是标准字体名，在装有这些字体的电脑上显示正常；在本机用 Word/WPS 打开会被自动换成别的字体，看到的不是正式效果，不能据此核对版式或打印。请自行下载安装后重新打开核对：仿宋_GB2312、楷体_GB2312 向单位信息中心或办公室索取；方正小标宋简体是商业字体，使用需单位授权。本工具不提供也不打包字体。

文件：5-成稿.docx（红头，加盖印章）、6-送审稿-批注.docx（核稿意见8条，全部写成批注）。
识别结果请核对：标题分两行；署名某区教育局；成文日期 2026年10月7日；印发机关某区教育局办公室，印发日期 2026年10月7日。
检查：P0、P1、P2 均为0，可以交付。
说明：成文日期沿用稿中的 10月7日，如实际签发日不同请告诉我；联系电话、抄送稿中没有，没有写入。
```
